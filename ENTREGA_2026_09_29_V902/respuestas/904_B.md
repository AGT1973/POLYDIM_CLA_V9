## Diagnóstico corregido

El problema es real, pero conviene precisar la causa: `malloc` y `free` son funciones *thread-safe*, no necesariamente protegidas por un único mutex global. En Windows, el CRT/heap subyacente puede introducir contención interna, y el asignador estándar puede escalar mal cuando muchos hilos realizan asignaciones pequeñas y frecuentes. `libgomp` no convierte cada `malloc` en una operación OpenMP atómica; la espera ocurre principalmente dentro del asignador y del sistema operativo.

La cifra de “70% esperando el lock” debe tratarse como un resultado experimental, no como una propiedad garantizada de MinGW/GCC 14.2. Debe confirmarse con un perfilador —por ejemplo WPA/ETW, Intel VTune o un muestreo de CPU— antes de atribuir todo el tiempo a un mutex del heap.

## Solución recomendada

La estrategia SOTA no debe ser únicamente “cambiar `malloc`”. El orden recomendado es:

1. Eliminar asignaciones dentro del bucle caliente.
2. Reservar memoria antes de entrar en `parallel for`.
3. Usar almacenamiento por hilo o por bloque.
4. Reutilizar buffers entre iteraciones.
5. Sustituir el asignador estándar solo cuando todavía exista presión significativa de asignación.

La documentación de OpenMP/libgomp incluye asignadores propios —`omp_alloc`, `omp_free`, `omp_init_allocator` y `OMP_ALLOCATOR`—, aunque el soporte concreto y sus ventajas dependen de la versión de GCC y del backend utilizado. cite[^1_1]

### Patrón que debe evitarse

```cpp
#pragma omp parallel for
for (long i = 0; i < n; ++i) {
    auto* p = static_cast<float*>(malloc(k * sizeof(float)));

    procesar(i, p);

    free(p);
}
```

Este patrón combina asignación, liberación y posible migración de memoria entre hilos en el camino crítico.

### Patrón preferible: reserva externa

```cpp
std::vector<float> workspace(
    static_cast<std::size_t>(n) * k
);

#pragma omp parallel for schedule(static)
for (long i = 0; i < n; ++i) {
    float* p = workspace.data() +
               static_cast<std::size_t>(i) * k;

    procesar(i, p);
}
```

Si el tamaño de `workspace` es demasiado grande, puede asignarse un bloque por hilo:

```cpp
#include <omp.h>
#include <vector>

const int threads = omp_get_max_threads();
std::vector<std::vector<float>> pool(
    threads, std::vector<float>(k)
);

#pragma omp parallel for schedule(static)
for (long i = 0; i < n; ++i) {
    const int tid = omp_get_thread_num();
    float* p = pool[tid].data();

    procesar(i, p);
}
```

Para evitar *false sharing*, las estructuras de control de cada hilo deben separarse al menos por una línea de caché:

```cpp
struct alignas(64) ThreadContext {
    std::vector<std::byte> buffer;
    std::size_t used = 0;
};
```

`alignas(64)` evita que los contadores o metadatos de hilos distintos compartan normalmente la misma línea de caché, pero no elimina la contención del asignador por sí solo. El `buffer` también debe tener una política clara de crecimiento y reutilización.

## mimalloc en Windows/MinGW

mimalloc es una alternativa razonable porque usa listas libres fragmentadas por páginas y rutas diferenciadas para operaciones locales y liberaciones concurrentes; su diseño busca reducir los puntos únicos de contención. La documentación también describe soporte para Windows, reemplazo dinámico del CRT y construcción compatible con MinGW. cite[^1_2]

### Opción A: usar la API de mimalloc

Es la opción más segura cuando se controla el código:

```cpp
#include <mimalloc.h>

#pragma omp parallel for
for (long i = 0; i < n; ++i) {
    void* p = mi_malloc(bytes);

    procesar(i, p);

    mi_free(p);
}
```

Es importante que memoria asignada con `mi_malloc` se libere con `mi_free`, y que memoria asignada con `malloc` se libere con `free`. No se deben mezclar heaps.

### Opción B: reemplazo global en Windows

Para interceptar llamadas del CRT, la documentación de mimalloc exige, entre otras condiciones:

- Usar el CRT dinámico (`/MD` o `/MDd`) cuando se compila con MSVC.
- Enlazar correctamente la DLL/import library de mimalloc.
- Distribuir `mimalloc.dll` junto con `mimalloc-redirect.dll`.
- Asegurar que mimalloc se carga suficientemente pronto.
- Verificar el reemplazo con `MIMALLOC_VERBOSE=1`.

En un flujo MinGW, la integración exacta depende de si el programa usa el CRT de Windows, `msvcrt`, `ucrt` o una capa de runtime compatible. Por eso, para MinGW suele ser más robusto utilizar explícitamente `mi_malloc`/`mi_free` o enlazar el reemplazo probado en un ejecutable mínimo antes de aplicarlo a toda la aplicación. La propia documentación advierte que el reemplazo global en Windows depende de cómo se haya enlazado el CRT. cite[^1_2]

### Configuración de arena

La opción:

```text
MIMALLOC_ARENA_EAGER_COMMIT=2
```

habilita la confirmación anticipada de arenas grandes únicamente en sistemas con *overcommit*. En Windows, si se desea activar explícitamente esta política, la documentación indica que puede probarse:

```text
MIMALLOC_ARENA_EAGER_COMMIT=1
```

El valor `2` no significa “máximo rendimiento en Windows”; es una política condicional. Además, la confirmación anticipada puede aumentar el compromiso virtual inicial y no sustituye la reducción de asignaciones. cite[^1_3]

Una configuración inicial para pruebas sería:

```bat
set MIMALLOC_VERBOSE=1
set MIMALLOC_SHOW_STATS=1
set MIMALLOC_ARENA_EAGER_COMMIT=1
programa.exe
```

Después debe compararse con:

```bat
set MIMALLOC_ARENA_EAGER_COMMIT=0
programa.exe
```

No conviene fijar `1` permanentemente sin medir consumo de memoria, fallos de página y tiempo de arranque.

## ThreadLocalPool correcto

Un pool por hilo es generalmente mejor que llamar al asignador externo en cada iteración. El pool debe:

- Ser propietario de sus bloques.
- Reutilizar memoria durante toda la región paralela.
- Crecer en bloques grandes, no byte a byte.
- Evitar liberar desde un hilo distinto al propietario.
- Aplicar una política para objetos grandes.
- Alinear los metadatos, no solo el puntero.
- Destruirse después de que termine la región OpenMP.

Ejemplo simplificado:

```cpp
#include <cstddef>
#include <memory>
#include <vector>

struct alignas(64) ThreadLocalPool {
    std::vector<std::byte> storage;
    std::size_t offset = 0;

    explicit ThreadLocalPool(std::size_t capacity)
        : storage(capacity) {}

    void* allocate(std::size_t bytes, std::size_t alignment = 64) {
        const std::size_t mask = alignment - 1;
        const std::size_t aligned =
            (offset + mask) & ~mask;

        if (aligned + bytes > storage.size())
            throw std::bad_alloc{};

        void* result = storage.data() + aligned;
        offset = aligned + bytes;
        return result;
    }

    void reset() noexcept {
        offset = 0;
    }
};
```

Uso:

```cpp
const int threads = omp_get_max_threads();
std::vector<ThreadLocalPool> pools;
pools.reserve(threads);

for (int t = 0; t < threads; ++t)
    pools.emplace_back(bytes_per_thread);

#pragma omp parallel for schedule(static)
for (long i = 0; i < n; ++i) {
    auto& pool = pools[omp_get_thread_num()];
    void* memory = pool.allocate(bytes_per_item, 64);

    procesar(i, memory);
}
```

Este ejemplo es apropiado para asignaciones temporales cuya vida termina antes de reutilizar el pool. No debe utilizarse si los objetos sobreviven a la región paralela o si otros hilos necesitan liberar individualmente esos objetos.

## Configuración de OpenMP

Con 100 o más hilos, el problema puede ser también de sobremultiplexación. En una máquina con menos procesadores lógicos, 100 hilos no proporcionan 100 vías reales de ejecución y pueden empeorar caché, frecuencia y latencia.

Pruebas iniciales:

```bat
set OMP_NUM_THREADS=32
set OMP_PROC_BIND=close
set OMP_PLACES=cores
set OMP_DYNAMIC=FALSE
set OMP_SCHEDULE=static
```

Luego comparar con:

```bat
set OMP_PROC_BIND=spread
set OMP_PLACES=threads
```

`libgomp` ofrece variables como `OMP_NUM_THREADS`, `OMP_PROC_BIND`, `OMP_PLACES`, `GOMP_CPU_AFFINITY` y `GOMP_SPINCOUNT` para controlar número, afinidad y espera de los hilos. cite[^1_1]

También conviene mantener una región paralela grande:

```cpp
#pragma omp parallel
{
    preparar_por_hilo();

    #pragma omp for schedule(static)
    for (long i = 0; i < n; ++i)
        procesar(i);

    #pragma omp for schedule(static)
    for (long i = 0; i < n; ++i)
        finalizar(i);
}
```

Crear y destruir repetidamente regiones paralelas añade una sobrecarga independiente de `malloc`.

La solución debería evaluarse con cuatro versiones:


| Variante | Asignador | Pool por hilo | Asignaciones en bucle |

| A | CRT estándar | No | Sí |
| B | CRT estándar | Sí | No |
| C | mimalloc | No | Sí |
| D | mimalloc | Sí | No |

Medir para 1, 2, 4, 8, 16, 32, 64 y el máximo razonable de hilos:

- Tiempo total.
- Tiempo dentro de `malloc`/`free`.
- Escalabilidad relativa.
- Fallos de página.
- Memoria residente y memoria comprometida.
- Uso de CPU.
- Distribución NUMA, si existe.
- Tiempo de espera en el heap.
- Efecto de `OMP_PROC_BIND`.

La afirmación “70% del tiempo en el lock” solo debe publicarse si el perfilador muestra explícitamente esa espera. Si el pool por hilo reduce el tiempo de ejecución más que mimalloc, el cuello principal era el patrón de asignación, no necesariamente el asignador de Windows.

### Recomendación final

Para V903/V904 usaría esta jerarquía:

1. `schedule(static)` y afinidad explícita.
2. Un único `parallel` persistente.
3. `ThreadLocalPool alignas(64)` o buffers indexados por hilo.
4. Cero `malloc/free` en el bucle caliente.
5. mimalloc como asignador secundario o global después de verificar compatibilidad con el CRT de MinGW.
6. Probar `MIMALLOC_ARENA_EAGER_COMMIT=1` y `=2`, sin asumir que `2` es la configuración óptima para Windows.
7. Validar con ETW/WPA y benchmarks de escalabilidad, no solo con el tiempo medio de una ejecución.

# Profundiza en mejoras y solucione sota

La mejora SOTA debe tratar el problema como una combinación de **diseño de memoria, afinidad, asignador y medición**. Cambiar `malloc` por mimalloc puede ayudar, pero si el bucle sigue asignando y liberando objetos pequeños en cada iteración, se conserva una parte importante del coste.

## Arquitectura recomendada

La ruta óptima para V903/V904 es:

```text
datos persistentes
        │
        ├── partición estática por hilo
        │       └── buffer reutilizable
        │
        ├── pool monotónico local
        │       └── reset() por bloque o iteración
        │
        └── mimalloc para objetos grandes o de vida larga
```

La política debe ser:

- Objetos temporales pequeños: `ThreadLocalPool`.
- Buffers de cada hilo: reservados una sola vez.
- Objetos que sobreviven a la región paralela: mimalloc o un pool global segmentado.
- Asignaciones grandes: asignador del sistema o mimalloc, según benchmark.
- Liberaciones: preferentemente por el mismo hilo que asignó.

Windows recomienda considerar *private heaps* para aplicaciones con asignaciones frecuentes; además, ETW/WPA permite capturar las pilas de asignación y comprobar dónde se produce realmente la contención. cite[^2_1]

## 1. Eliminar asignaciones del bucle

### Mala implementación

```cpp
#pragma omp parallel for
for (std::int64_t i = 0; i < n; ++i) {
    auto* tmp = new float[width];
    compute(i, tmp);
    delete[] tmp;
}
```


### Implementación recomendada

```cpp
struct alignas(64) Worker {
    std::vector<float> scratch;
    std::uint64_t iterations = 0;

    explicit Worker(std::size_t width)
        : scratch(width) {}
};

const int p = omp_get_max_threads();
std::vector<Worker> workers;
workers.reserve(p);

for (int t = 0; t < p; ++t)
    workers.emplace_back(width);

#pragma omp parallel for schedule(static)
for (std::int64_t i = 0; i < n; ++i) {
    Worker& w = workers[omp_get_thread_num()];
    compute(i, w.scratch.data());
    ++w.iterations;
}
```

Hay una condición importante: `schedule(static)` debe garantizar que una iteración no sea ejecutada simultáneamente por dos hilos. Si el cálculo usa varias fases, conviene mantener una única región paralela:

```cpp
#pragma omp parallel
{
    Worker& w = workers[omp_get_thread_num()];

    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < n; ++i)
        phase_a(i, w.scratch.data());

    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < n; ++i)
        phase_b(i, w.scratch.data());
}
```

Esto evita recrear equipos OpenMP y permite que cada hilo conserve su buffer caliente en caché.

## 2. Pool monotónico por hilo

Para objetos temporales de vida corta, un *arena allocator* monotónico es preferible a `malloc/free` repetido:

```cpp
class BumpPool {
public:
    explicit BumpPool(std::size_t capacity)
        : storage_(capacity) {}

    void* allocate(std::size_t bytes,
                   std::size_t alignment = 64) {
        const std::size_t mask = alignment - 1;
        const std::size_t start =
            (offset_ + mask) & ~mask;

        if (start > storage_.size() ||
            bytes > storage_.size() - start) {
            throw std::bad_alloc{};
        }

        void* result = storage_.data() + start;
        offset_ = start + bytes;
        return result;
    }

    void reset() noexcept {
        offset_ = 0;
    }

private:
    std::vector<std::byte> storage_;
    std::size_t offset_ = 0;
};
```

Uso por hilo:

```cpp
struct alignas(64) ThreadState {
    BumpPool pool;
    std::uint64_t count = 0;

    explicit ThreadState(std::size_t bytes)
        : pool(bytes) {}
};

std::vector<ThreadState> states;
states.reserve(p);
for (int t = 0; t < p; ++t)
    states.emplace_back(bytes_per_thread);

#pragma omp parallel for schedule(static)
for (std::int64_t i = 0; i < n; ++i) {
    auto& state = states[omp_get_thread_num()];

    auto* tmp = static_cast<float*>(
        state.pool.allocate(width * sizeof(float), 64)
    );

    compute(i, tmp);
    ++state.count;
}
```

Si el pool se reinicia por iteración, el reset debe ejecutarse únicamente cuando no queden objetos vivos:

```cpp
#pragma omp parallel
{
    auto& state = states[omp_get_thread_num()];

    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < n; ++i) {
        state.pool.reset();
        process_with_temporaries(i, state.pool);
    }
}
```

Si el algoritmo tiene objetos que cruzan iteraciones, el reset debe hacerse por bloque, después de completar el bloque, no por iteración.

## 3. Usar los allocators de OpenMP

GCC 14/libgomp incluye allocators predefinidos como `omp_pteam_mem_alloc` y `omp_thread_mem_alloc`. En libgomp, los espacios de baja latencia pueden terminar mapeándose al espacio de memoria normal en plataformas donde no existe un backend específico; por eso no debe asumirse que `omp_thread_mem_alloc` equivale automáticamente a un pool sin locks. cite[^2_2]

Ejemplo en C/C++:

```cpp
#include <omp.h>

#pragma omp parallel
{
    int* local = static_cast<int*>(
        omp_alloc(1024 * sizeof(int), omp_thread_mem_alloc)
    );

    if (!local)
        abort();

    use(local);

    omp_free(local, omp_thread_mem_alloc);
}
```

Para un allocator con `pool_size`:

```cpp
omp_alloctrait_t traits[] = {
    {omp_atk_access, omp_atv_thread},
    {omp_atk_pool_size, 64 * 1024 * 1024},
    {omp_atk_alignment, 64}
};

omp_allocator_handle_t allocator =
    omp_init_allocator(
        omp_default_mem_space,
        3,
        traits
    );
```

La especificación OpenMP define que un allocator con acceso `thread` está destinado al hilo que lo solicitó, mientras que `pteam` puede ser usado por los hilos de la misma región paralela. También define `pool_size` como límite del almacenamiento asociado al allocator. cite[^2_3]

Sin embargo, en Windows/MinGW esta ruta debe evaluarse con cuidado:

- La implementación puede caer en el allocator general.
- `pool_size` no necesariamente significa un pool eficiente en libgomp.
- El soporte de algunas cláusulas OpenMP puede estar incompleto.
- El allocator no reemplaza automáticamente todas las llamadas de `malloc`.

Por ello, para una solución controlada, un pool explícito por hilo suele ser más predecible.

## 4. mimalloc: configuración avanzada

mimalloc usa heaps locales por hilo y listas separadas para liberaciones locales y remotas. Su diseño desplaza las liberaciones realizadas por otro hilo hacia una lista diferida del heap propietario, reduciendo la necesidad de bloquear inmediatamente el camino de asignación. cite[^2_4]

La versión actual de mimalloc documenta *first-class heaps*. En mimalloc v3, estos heaps pueden utilizarse desde distintos hilos y crean estructuras locales bajo demanda, evitando que todas las asignaciones pasen por un único lock. cite[^2_5]

### Heap por dominio de trabajo

```cpp
#include <mimalloc.h>

struct HeapOwner {
    mi_heap_t* heap = nullptr;

    HeapOwner()
        : heap(mi_heap_new()) {}

    ~HeapOwner() {
        if (heap)
            mi_heap_destroy(heap);
    }

    HeapOwner(const HeapOwner&) = delete;
    HeapOwner& operator=(const HeapOwner&) = delete;
};
```

Con mimalloc v3, un heap puede utilizarse de forma compartida:

```cpp
HeapOwner owner;

#pragma omp parallel
{
    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < n; ++i) {
        void* p = mi_heap_malloc(owner.heap, bytes);
        process(i, p);
        mi_free(p);
    }
}
```

Aunque mimalloc v3 puede gestionar heaps compartidos de forma más eficiente, esto no significa que una asignación por iteración sea gratis. En general, el pool monotónico sigue siendo superior si los objetos son temporales y tienen tamaños previsibles.

### Estrategia híbrida

```cpp
#pragma omp parallel
{
    ThreadState& state = states[omp_get_thread_num()];

    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < n; ++i) {
        void* p;

        if (bytes <= SMALL_OBJECT_LIMIT) {
            p = state.pool.allocate(bytes, 64);
        } else {
            p = mi_malloc_aligned(bytes, 64);
        }

        process(i, p);

        if (bytes > SMALL_OBJECT_LIMIT)
            mi_free(p);
    }
}
```

Una partición inicial razonable para probar es:

- Hasta 256 o 512 bytes: pool local.
- Entre 512 bytes y 64 KiB: pool local por bloque.
- Más de 64 KiB: mimalloc.
- Objetos de vida larga: heap dedicado o mimalloc global.

Los límites deben determinarse mediante mediciones del workload real.

## 5. Arenas y `MIMALLOC_ARENA_EAGER_COMMIT`

`MIMALLOC_ARENA_EAGER_COMMIT` controla la confirmación anticipada de arenas grandes. El valor `2` es condicional para sistemas con *overcommit*; no debe interpretarse como una configuración universalmente óptima para Windows. cite[^2_6]

Benchmark mínimo:

```bat
set MIMALLOC_VERBOSE=1
set MIMALLOC_SHOW_STATS=1
set MIMALLOC_ARENA_EAGER_COMMIT=0
benchmark.exe

set MIMALLOC_ARENA_EAGER_COMMIT=1
benchmark.exe

set MIMALLOC_ARENA_EAGER_COMMIT=2
benchmark.exe
```

Debe registrarse:

- Tiempo de arranque.
- Memoria comprometida.
- Memoria residente.
- Fallos de página.
- Tiempo total.
- Tiempo de asignación.
- Rendimiento después del calentamiento.

El modo eager commit puede mejorar la latencia de la primera asignación y reducir fallos de confirmación posteriores, pero también puede comprometer memoria que nunca se llegue a tocar. En un sistema Windows sin overcommit equivalente al de Linux, la interpretación del valor `2` merece especial cuidado.

## 6. Alineación y false sharing

Este diseño es insuficiente:

```cpp
std::vector<std::atomic<std::uint64_t>> counters;
```

Aunque cada contador pertenezca a un hilo distinto, varios pueden caer en la misma línea de caché.

Usar:

```cpp
struct alignas(64) PaddedCounter {
    std::atomic<std::uint64_t> value{0};
};

std::vector<PaddedCounter> counters(p);
```

Pero hay dos matices:

1. `alignas(64)` alinea el inicio del objeto, no garantiza siempre que un objeto grande no comparta líneas en todos los escenarios.
2. En procesadores con líneas de 128 bytes o en arquitecturas futuras, 64 puede no ser el tamaño efectivo óptimo.

Para Windows x86-64, 64 bytes es una hipótesis razonable, pero debe validarse con el hardware objetivo. Para buffers numéricos, también importa la alineación SIMD:

```cpp
float* p = static_cast<float*>(
    mi_malloc_aligned(bytes, 64)
);
```

La alineación mejora el acceso vectorizado, pero no corrige una mala distribución de trabajo ni la contención del heap.

## 7. Afinidad y número real de hilos

“100 hilos” no equivale a “100 unidades de ejecución”. Si la máquina tiene menos núcleos lógicos, se produce sobremultiplexación. Probar más hilos puede empeorar:

- Contención del asignador.
- Presión sobre la caché.
- Cambios de contexto.
- Consumo energético.
- Frecuencia turbo.
- Ancho de banda de memoria.

Configuración inicial:

```bat
set OMP_DYNAMIC=FALSE
set OMP_PROC_BIND=spread
set OMP_PLACES=cores
set OMP_SCHEDULE=static
```

Para tareas con mucha reutilización de caché:

```bat
set OMP_PROC_BIND=close
set OMP_PLACES=cores
```

Para una aplicación de memoria, comparar `close` y `spread` es esencial. `close` puede favorecer caché; `spread` puede distribuir mejor el ancho de banda.

También se debe comparar:

```text
1, 2, 4, 8, 16, 32, 64, P
```

donde $P$ es el número de procesadores lógicos disponibles. Si el rendimiento deja de escalar antes de 100 hilos, añadir más hilos no resuelve el problema.

## 8. Partición por bloques

Un `parallel for` por elemento puede generar demasiada granularidad. Usar bloques reduce accesos a metadatos y permite resetear el pool por bloque:

```cpp
const std::int64_t block = 4096;
const std::int64_t blocks =
    (n + block - 1) / block;

#pragma omp parallel for schedule(static)
for (std::int64_t b = 0; b < blocks; ++b) {
    auto& state = states[omp_get_thread_num()];
    state.pool.reset();

    const std::int64_t begin = b * block;
    const std::int64_t end =
        std::min(begin + block, n);

    for (std::int64_t i = begin; i < end; ++i) {
        process(i, state.pool);
    }
}
```

El tamaño de bloque debe medirse. Bloques demasiado pequeños aumentan overhead; bloques demasiado grandes reducen el balanceo. Para `schedule(static)`, empezar con 1.024–16.384 elementos suele ser una buena exploración, pero no es una regla universal.

## 9. Diagnóstico con ETW/WPA

Antes de afirmar que existe un “malloc lock global”, capturar:

- Stacks de `malloc`, `free`, `RtlAllocateHeap`, `RtlFreeHeap`.
- Esperas en locks.
- Fallos de página.
- Cambios de contexto.
- Uso de CPU por hilo.
- Tiempo en regiones OpenMP.
- Accesos remotos NUMA cuando estén disponibles.

Microsoft recomienda el trazado ETW de heap mediante Windows Performance Recorder y el análisis de las pilas de asignación en Windows Performance Analyzer. cite[^2_1]

Una matriz de experimentos adecuada es:


| Prueba | Asignador | Pool | Hilos | Propósito |
| :-- | :-- | --: | --: | :-- |
| A | CRT | No | 1–P | Línea base |
| B | CRT | Sí | 1–P | Medir efecto del diseño |
| C | mimalloc | No | 1–P | Medir efecto del asignador |
| D | mimalloc | Sí | 1–P | Solución híbrida |
| E | mimalloc + eager commit | Sí | 1–P | Medir confirmación |
| F | OpenMP allocator | Sí | 1–P | Medir soporte libgomp |

El resultado clave no es solo el tiempo absoluto, sino:

$$
S(P)=\frac{T(1)}{T(P)}
$$

y la eficiencia:

$$
E(P)=\frac{S(P)}{P}
$$

Si la variante D reduce las asignaciones pero no mejora el tiempo, el cuello probablemente está en ancho de banda, false sharing, afinidad o balanceo, no en el heap.

## Solución SOTA propuesta

Para el caso descrito, propondría esta implementación final:

1. `parallel` persistente.
2. `schedule(static)` con bloques.
3. `OMP_PROC_BIND=close` y `spread` evaluados separadamente.
4. Un `ThreadLocalPool` por hilo, alineado a 64 bytes.
5. Reservas hechas antes de la región paralela.
6. `reset()` por bloque, nunca `free()` por objeto temporal.
7. mimalloc únicamente para objetos grandes o de vida larga.
8. `mi_heap_t` por dominio de trabajo cuando existan muchas asignaciones persistentes.
9. `MIMALLOC_ARENA_EAGER_COMMIT=0`, `1` y `2` comparados empíricamente.
10. ETW/WPA para confirmar el origen de la espera.
11. ASan/Application Verifier en una configuración de validación, no durante el benchmark final.
12. Publicar la mejora únicamente junto con hardware, número de hilos, tamaño de datos, afinidad y distribución de asignaciones.

La conclusión técnica más importante es que la solución dominante no es simplemente **“mimalloc + `alignas(64)`**. Es **“cero asignaciones pequeñas en el camino caliente, memoria temporal propiedad del hilo, afinidad controlada y mimalloc como segunda línea”**.

# Incompatibilidad Parcial de OpenMP 5.2 Allocators en GCC 14.2 MinGW:Busca las mejoras y solucione sota para el siguiente tema

Diagnóstico: La especificación OpenMP 5.2 introduce omp_allocator_t, pero la distribución MinGW64 GCC 14.2 carece de la biblioteca libgomp de asignadores privados integrada.
Brecha / Risk: El uso del pragma \#pragma omp parallel for allocator(thread_alloc) causa errores de enlazador (undefined reference to omp_init_allocator).
Solución SOTA V904: Implementación de un cortafuegos por macros \#if \_OPENMP >= 202111 \&\& defined(\_OPENMP_ALLOCATORS) con fallback a asignadores por arena atómicos lock-free.

El diagnóstico necesita una corrección importante: **GCC 14.2/libgomp sí documenta `omp_init_allocator` y los allocators predefinidos**. El problema en MinGW64 no debe describirse automáticamente como “falta la biblioteca de asignadores privados”. Lo más probable es una combinación de versión real del runtime, headers inconsistentes, enlace incorrecto con `-fopenmp`, una distribución MinGW incompleta o uso de una sintaxis que GCC 14.2 todavía no implementa.

GCC 14.2 lista `omp_init_allocator` en su API y documenta `omp_thread_mem_alloc`, `omp_pteam_mem_alloc`, `omp_alloc` y `omp_free`; al mismo tiempo, su tabla de OpenMP 5.2 marca algunas características de allocators como no implementadas. cite cite[^3_1][^3_2]

## Diagnóstico exacto

Hay tres conceptos que no deben mezclarse:


| Elemento | Situación esperable en GCC 14.2 |
| :-- | :-- |
| `omp_allocator_handle_t` | Disponible en headers OpenMP |
| `omp_init_allocator` | API de libgomp documentada |
| `omp_thread_mem_alloc` | Allocator predefinido documentado |
| Todos los modificadores OpenMP 5.2 | No necesariamente implementados |
| `uses_allocators` 5.2 completo | Parcial |
| Backend físico separado por hilo | Dependiente de libgomp y plataforma |
| Un allocator propietario tipo mimalloc | No forma parte de libgomp |

La especificación OpenMP define la firma de `omp_init_allocator` como:

```cpp
omp_allocator_handle_t omp_init_allocator(
    omp_memspace_handle_t memspace,
    int ntraits,
    const omp_alloctrait_t traits[]
);
```

Esa firma está documentada en la referencia de OpenMP 5.2. cite[^3_3]

Por tanto, este error:

```text
undefined reference to omp_init_allocator
```

normalmente indica un problema de compilación o enlace, no necesariamente ausencia conceptual de soporte.

## Primera corrección: verificar headers y runtime

Compilar y enlazar siempre con `-fopenmp`:

```bash
g++ -std=c++20 -O3 -fopenmp test_alloc.cpp -o test_alloc.exe
```

No es suficiente compilar el archivo con OpenMP y enlazar después sin la opción:

```bash
g++ -std=c++20 -O3 -fopenmp -c test_alloc.cpp
g++ test_alloc.o -o test_alloc.exe
```

La segunda línea debe incluir también:

```bash
g++ test_alloc.o -fopenmp -o test_alloc.exe
```

Verificar qué GCC se está utilizando:

```bash
g++ --version
g++ -v
g++ -print-file-name=libgomp.dll.a
g++ -print-file-name=libgomp-1.dll
```

Comprobar que headers y runtime pertenecen al mismo toolchain:

```bash
g++ -E -dM -x c++ -fopenmp nul | findstr OPENMP
```

En Linux/MSYS2 se puede usar:

```bash
g++ -E -dM -x c++ -fopenmp /dev/null | grep OPENMP
```

El valor esperado para GCC 14 es normalmente:

```cpp
_OPENMP == 202011
```

Eso corresponde a OpenMP 5.1, no a 5.2. Una implementación puede incorporar partes de 5.2 sin que `_OPENMP` cambie a `202111`.

Esta es una debilidad del firewall propuesto:

```cpp
#if _OPENMP >= 202111
```

En GCC 14.2 esa condición puede ser falsa aunque algunas APIs de allocators estén disponibles. Por tanto, **no se debe detectar el soporte solo mediante `_OPENMP`**.

## Firewall correcto

La macro `_OPENMP_ALLOCATORS` no es una macro estándar garantizada por OpenMP ni una detección fiable de libgomp. Si se usa, debe ser una macro propia definida por el sistema de compilación después de ejecutar una prueba real.

### Cabecera portable

```cpp
#pragma once

#include <cstddef>
#include <cstdlib>

#if defined(_OPENMP)
  #include <omp.h>
#endif

#ifndef PROJECT_HAS_OMP_ALLOCATORS
  #define PROJECT_HAS_OMP_ALLOCATORS 0
#endif

#if PROJECT_HAS_OMP_ALLOCATORS
  #define PROJECT_OMP_ALLOCATOR_AVAILABLE 1
#else
  #define PROJECT_OMP_ALLOCATOR_AVAILABLE 0
#endif
```

No conviene escribir directamente:

```cpp
#if _OPENMP >= 202111 && defined(_OPENMP_ALLOCATORS)
```

porque:

- `_OPENMP_ALLOCATORS` no es una macro portable.
- GCC 14 puede reportar `_OPENMP == 202011`.
- La presencia del header no garantiza que el enlace funcione.
- La compilación y el runtime pueden pertenecer a instalaciones diferentes.

## Implementación con tres niveles

La arquitectura recomendada no es binaria “OpenMP sí/no”, sino de tres niveles:

```text
Nivel 1: omp_thread_mem_alloc
Nivel 2: pool monotónico por hilo
Nivel 3: malloc/mimalloc como fallback
```


### API unificada

```cpp
#pragma once

#include <cstddef>
#include <cstdlib>
#include <new>

#if defined(_OPENMP)
#include <omp.h>
#endif

#ifndef PROJECT_HAS_OMP_ALLOCATORS
#define PROJECT_HAS_OMP_ALLOCATORS 0
#endif

class ThreadAllocator {
public:
    static void* allocate(std::size_t bytes,
                          std::size_t alignment = alignof(std::max_align_t)) {
#if PROJECT_HAS_OMP_ALLOCATORS
        void* p = omp_aligned_alloc(
            bytes,
            alignment,
            omp_thread_mem_alloc
        );

        if (p != nullptr)
            return p;
#endif

        void* p = nullptr;

#if defined(_WIN32)
        p = _aligned_malloc(bytes, alignment);
        if (!p)
            throw std::bad_alloc{};
#else
        if (posix_memalign(&p, alignment, bytes) != 0)
            throw std::bad_alloc{};
#endif

        return p;
    }

    static void deallocate(void* p) noexcept {
        if (!p)
            return;

#if PROJECT_HAS_OMP_ALLOCATORS
        // Solo usar omp_free si se conoce el allocator de origen.
        // La implementación completa debe guardar ese origen.
#endif

#if defined(_WIN32)
        _aligned_free(p);
#else
        std::free(p);
#endif
    }
};
```

Este ejemplo muestra el principio, pero no debe mezclar memoria de `omp_alloc` con `_aligned_free`. En producción, cada asignación debe guardar su backend:

```cpp
enum class AllocationBackend : unsigned char {
    omp,
    fallback
};

struct Allocation {
    void* ptr;
    AllocationBackend backend;
};
```

Una alternativa más simple es no usar `omp_alloc` para objetos individuales y encapsular únicamente pools propios.

## Pool lock-free: corrección del diseño

La expresión “arena atómica lock-free” puede ser engañosa. Un pool por hilo **no necesita operaciones atómicas** en su camino caliente. Si solo el propietario modifica `offset`, el camino ideal es:

```text
thread-local owner
    └── load offset
    └── align
    └── add
    └── return pointer
```

Introducir `std::atomic` en cada asignación puede empeorar el rendimiento.

### Pool local al hilo

```cpp
#include <cstddef>
#include <cstdint>
#include <memory>
#include <vector>

class LocalArena {
public:
    explicit LocalArena(std::size_t capacity)
        : storage_(capacity) {}

    LocalArena(const LocalArena&) = delete;
    LocalArena& operator=(const LocalArena&) = delete;

    void* allocate(std::size_t bytes,
                   std::size_t alignment = 64) {
        const std::size_t mask = alignment - 1;
        const std::size_t begin =
            (offset_ + mask) & ~mask;

        if (begin > storage_.size() ||
            bytes > storage_.size() - begin) {
            return nullptr;
        }

        void* result = storage_.data() + begin;
        offset_ = begin + bytes;
        return result;
    }

    void reset() noexcept {
        offset_ = 0;
    }

private:
    std::vector<std::byte> storage_;
    std::size_t offset_ = 0;
};
```

Uso:

```cpp
#pragma omp parallel
{
    thread_local LocalArena arena(8 * 1024 * 1024);

    #pragma omp for schedule(static)
    for (long long i = 0; i < n; ++i) {
        void* temporary = arena.allocate(bytes, 64);

        if (!temporary) {
            // Fallback explícito para objetos que excedan el arena.
            temporary = fallback_allocate(bytes, 64);
        }

        process(i, temporary);
    }
}
```

El problema de este ejemplo es que un `thread_local` con capacidad grande se crea por hilo y puede ocultar el coste de memoria. En una implementación real, la capacidad debe configurarse según el número de hilos y el tamaño del problema.

### Arena con bloques y lista lock-free

Solo se necesita una estructura lock-free si un hilo puede solicitar bloques de la arena de otro hilo. El patrón recomendado es:

- Fast path: bloque local sin atómicos.
- Slow path: tomar un bloque nuevo de una lista MPSC/MPMC.
- Liberación remota: lista diferida por propietario.
- Recolección: realizada por el propietario.

No se debe usar un CAS global para cada objeto pequeño:

```cpp
// Evitar este patrón para cada asignación:
global_offset.fetch_add(bytes, std::memory_order_relaxed);
```

Aunque `fetch_add` sea lock-free en sentido formal, todos los hilos siguen compitiendo por la misma línea de caché. Eso sustituye un mutex por una línea de caché caliente.

## Pragma `allocator`: compatibilidad real

El código siguiente no debe habilitarse solo porque `_OPENMP` exista:

```cpp
#pragma omp parallel for allocator(thread_alloc)
for (...) {
}
```

Además, `thread_alloc` no es necesariamente un identificador predefinido válido. La API estándar usa handles como:

```cpp
omp_thread_mem_alloc
```

y las cláusulas dependen del constructo y de la versión implementada.

Para el camino portable:

```cpp
#pragma omp parallel for
for (long long i = 0; i < n; ++i) {
    // Allocation through the project abstraction.
}
```

Para el camino OpenMP condicionado:

```cpp
#if PROJECT_HAS_FULL_OMP_ALLOCATORS
#pragma omp parallel for
for (long long i = 0; i < n; ++i) {
    void* p = omp_alloc(bytes, omp_thread_mem_alloc);
    work(i, p);
    omp_free(p, omp_thread_mem_alloc);
}
#else
#pragma omp parallel for
for (long long i = 0; i < n; ++i) {
    void* p = fallback_thread_arena_allocate(bytes);
    work(i, p);
    fallback_thread_arena_free(p);
}
#endif
```

En la práctica, la asignación manual dentro del cuerpo suele ser más portable que depender de cláusulas nuevas del pragma.

## Riesgo de ABI y headers incompatibles

No se debe copiar manualmente `omp.h` desde otra instalación. `omp.h` y `libgomp` deben proceder del mismo GCC.

Casos peligrosos:

```text
Header de GCC 14.2 + libgomp de GCC 11
Header MinGW + libgomp LLVM
Compilador UCRT64 + DLL MINGW64
Biblioteca estática de una instalación + DLL de otra
```

El error puede aparecer en compilación, enlace o ejecución. La solución SOTA es aislar el toolchain mediante:

- MSYS2 UCRT64 completo.
- MinGW-w64 GCC completo de una sola versión.
- Contenedor reproducible.
- CMake toolchain file.
- Prueba CI que compile, enlace y ejecute un allocator mínimo.


## Fallback recomendado para V904

La ruta de fallback debe ser determinista:

```cpp
#if PROJECT_HAS_FULL_OMP_ALLOCATORS
    using allocator_mode = omp_mode;
#elif defined(PROJECT_USE_MIMALLOC)
    using allocator_mode = mimalloc_mode;
#else
    using allocator_mode = local_arena_mode;
#endif
```

Orden recomendado:

1. `ThreadLocalArena` propio para temporales.
2. mimalloc para objetos grandes o persistentes.
3. `omp_thread_mem_alloc` solo cuando la prueba de configuración haya confirmado su disponibilidad y comportamiento.
4. CRT como último fallback.

No recomendaría un fallback “lock-free global” para todas las asignaciones. El diseño correcto es:

```text
local arena: no lock, no atomic
global block source: CAS solo al pedir un bloque
remote free: cola por propietario
large allocation: mimalloc
```

## Solución SOTA V904 final

La implementación recomendada es:

```cpp
#if defined(PROJECT_HAS_OMP_ALLOCATORS) && \
    PROJECT_HAS_OMP_ALLOCATORS && \
    defined(PROJECT_HAS_OMP_INIT_ALLOCATOR) && \
    PROJECT_HAS_OMP_INIT_ALLOCATOR

    // OpenMP allocator path

#elif defined(PROJECT_USE_MIMALLOC)

    // mimalloc path

#else

    // Per-thread monotonic arena path

#endif
```

Con estas reglas:

- No usar `_OPENMP >= 202111` como única detección.
- No asumir que `_OPENMP_ALLOCATORS` es una macro estándar.
- Detectar APIs mediante `try_compile`.
- Añadir `-fopenmp` tanto al enlace como a la compilación.
- Verificar que `omp.h`, `libgomp.dll.a` y `libgomp-1.dll` pertenecen al mismo GCC.
- Evitar `allocator(thread_alloc)` si la implementación concreta no ha sido probada.
- Preferir un pool por hilo sin atómicos en el camino rápido.
- Reservar bloques globalmente solo en el camino lento.
- Usar mimalloc para las asignaciones que realmente necesiten un heap general.
- Mantener una prueba de compatibilidad en CI para cada distribución MinGW.

La corrección principal al diagnóstico es que GCC 14.2 no carece necesariamente de `libgomp` allocators: documenta la API, pero su cobertura de OpenMP 5.2 es parcial y el empaquetado MinGW puede introducir incompatibilidades. Por eso, la solución robusta no es una macro basada únicamente en la versión de OpenMP, sino **detección por compilación/enlace más un fallback por arenas locales**.

# Profundiza en mejoras y solucione sota

La solución SOTA debe evolucionar de “cambiar el allocator” a un **sistema jerárquico de memoria**: asignación estática cuando sea posible, pool por hilo para temporales, arenas por equipo OpenMP para datos compartidos y mimalloc para objetos grandes o de vida larga. Con esto se elimina la mayoría de llamadas al heap en el camino crítico, que es donde realmente se obtiene la mejora.

## Diseño SOTA recomendado

```text
Nivel 0: stack / registros
    temporales pequeños y fijos

Nivel 1: ThreadLocalPool
    temporales por hilo, reset por bloque

Nivel 2: pteam arena
    datos compartidos dentro de una región parallel

Nivel 3: mimalloc
    objetos grandes, persistentes o de tamaño variable

Nivel 4: VirtualAlloc / private heap
    reservas enormes y control explícito de regiones
```

La configuración final debe evitar que cada iteración ejecute `malloc` y `free`.

## 1. Solución principal: pool por hilo + bloques

Esta es la variante que priorizaría para V903/V904:

```cpp
#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <new>
#include <omp.h>
#include <vector>

class MonotonicPool {
public:
    explicit MonotonicPool(std::size_t capacity)
        : memory_(capacity) {}

    MonotonicPool(const MonotonicPool&) = delete;
    MonotonicPool& operator=(const MonotonicPool&) = delete;

    void reset() noexcept {
        offset_ = 0;
    }

    void* allocate(std::size_t bytes,
                   std::size_t alignment = 64) {
        const std::size_t mask = alignment - 1;
        const std::size_t begin =
            (offset_ + mask) & ~mask;

        if (begin > memory_.size() ||
            bytes > memory_.size() - begin) {
            throw std::bad_alloc{};
        }

        void* ptr = memory_.data() + begin;
        offset_ = begin + bytes;
        return ptr;
    }

private:
    std::vector<std::byte> memory_;
    std::size_t offset_ = 0;
};

struct alignas(64) ThreadContext {
    MonotonicPool pool;
    std::uint64_t processed = 0;

    explicit ThreadContext(std::size_t capacity)
        : pool(capacity) {}
};
```

Uso con bloques:

```cpp
const std::int64_t block_size = 4096;
const std::int64_t block_count =
    (n + block_size - 1) / block_size;

const int thread_count = omp_get_max_threads();
std::vector<ThreadContext> contexts;
contexts.reserve(thread_count);

for (int t = 0; t < thread_count; ++t)
    contexts.emplace_back(pool_bytes_per_thread);

#pragma omp parallel for schedule(static)
for (std::int64_t block = 0;
     block < block_count;
     ++block) {
    ThreadContext& ctx =
        contexts[omp_get_thread_num()];

    ctx.pool.reset();

    const std::int64_t begin = block * block_size;
    const std::int64_t end =
        std::min(begin + block_size, n);

    for (std::int64_t i = begin; i < end; ++i) {
        void* temporary =
            ctx.pool.allocate(bytes_per_item, 64);

        process(i, temporary);
        ++ctx.processed;
    }
}
```


### Por qué mejora

- `reset()` es una operación constante.
- No se invoca `free()` por objeto.
- Cada hilo escribe en su propia región.
- Se reduce la contaminación de caché.
- Se amortiza el coste de reserva.
- La liberación completa ocurre al destruir los contextos.

El tamaño del bloque debe medirse. Un bloque muy pequeño aumenta overhead; uno muy grande puede producir desequilibrio. Deben probarse, al menos, 1.024, 4.096, 16.384 y 65.536 elementos.

## 2. Evitar una limitación del pool simple

El pool anterior no devuelve memoria individualmente. Eso es correcto solo si los objetos:

- Mueren antes del `reset()`.
- No escapan del hilo.
- No se almacenan para usarse en otra fase.
- No son liberados individualmente.

Si un objeto debe sobrevivir, usar un segundo camino:

```cpp
if (lifetime == Temporary) {
    ptr = ctx.pool.allocate(size, 64);
} else {
    ptr = mi_malloc_aligned(size, 64);
}
```

Regla estricta:

```text
mi_malloc / mi_free
malloc / free
omp_alloc / omp_free
```

No mezclar pares de asignación y liberación.

## 3. mimalloc como segunda línea

mimalloc ya usa heaps locales por hilo y mecanismos de liberación diferida para reducir la interferencia entre hilos. Su documentación también expone *first-class heaps*, útiles para agrupar objetos por dominio y destruirlos en conjunto. cite cite[^4_1][^4_2]

Para objetos persistentes:

```cpp
#include <mimalloc.h>

struct PersistentObject {
    void* data;
    std::size_t size;

    explicit PersistentObject(std::size_t bytes)
        : data(mi_malloc_aligned(bytes, 64)),
          size(bytes) {
        if (!data)
            throw std::bad_alloc{};
    }

    ~PersistentObject() {
        mi_free(data);
    }

    PersistentObject(const PersistentObject&) = delete;
    PersistentObject& operator=(const PersistentObject&) = delete;
};
```

Para un dominio de trabajo completo:

```cpp
mi_heap_t* heap = mi_heap_new();

#pragma omp parallel for schedule(static)
for (std::int64_t i = 0; i < n; ++i) {
    void* object =
        mi_heap_malloc_aligned(heap, object_size, 64);

    process(i, object);
    mi_free(object);
}

mi_heap_destroy(heap);
```

En una aplicación real, no conviene crear y destruir heaps dentro del bucle. El heap debe vivir como mínimo durante toda la fase de trabajo.

Si el objeto se libera en otro hilo, mimalloc puede manejar la liberación remota, pero el diseño preferible sigue siendo que el hilo propietario libere sus objetos o que se use una cola de retorno por propietario.

## 4. Colas de liberación por propietario

Para objetos que cruzan hilos, una mejora importante es no ejecutar el `free` directamente en el consumidor. En su lugar:

```cpp
struct alignas(64) RemoteFreeQueue {
    std::mutex mutex;
    std::vector<void*> pending;
};
```

El consumidor coloca el puntero en la cola del propietario; el propietario libera o recicla los objetos en lotes.

En aplicaciones de alto rendimiento, puede sustituirse `std::mutex` por:

- Cola SPSC si existe un único productor.
- Cola MPSC si existen varios productores.
- Batching de liberaciones.
- Índices atómicos separados de los datos.
- Reutilización de nodos.

La idea es que una liberación remota no bloquee el camino de asignación local.

## 5. Usar los allocators de OpenMP con criterio

GCC 14.2 documenta `OMP_ALLOCATOR`, que permite seleccionar el allocator por defecto y configurar traits como `alignment`, `access`, `pool_size`, `fallback` y `partition`. Los allocators `omp_pteam_mem_alloc` y `omp_thread_mem_alloc` están asociados a memoria de baja latencia, aunque el mapeo físico depende de libgomp y de la plataforma. cite[^4_3]

Ejemplo:

```bat
set OMP_ALLOCATOR=omp_thread_mem_alloc
```

Con traits:

```bat
set OMP_ALLOCATOR=omp_low_lat_mem_space:alignment=64,pool_size=67108864
```

Debe probarse, no asumirse, que esta configuración supera a un pool explícito. La razón es que libgomp puede implementar esos espacios con el backend general del host. El benchmark debe comparar:

```text
OMP_ALLOCATOR ausente
omp_default_mem_alloc
omp_thread_mem_alloc
omp_pteam_mem_alloc
pool explícito por hilo
mimalloc
pool explícito + mimalloc
```

Para memoria usada por todo el equipo de una región paralela:

```cpp
#pragma omp parallel
{
    void* shared_temp =
        omp_alloc(bytes, omp_pteam_mem_alloc);

    use_shared_temp(shared_temp);

    omp_free(shared_temp, omp_pteam_mem_alloc);
}
```

La semántica `pteam` está diseñada para memoria accesible por los hilos que pertenecen al mismo equipo de la región paralela. cite[^4_4]

## 6. Crear una sola región paralela

Evitar:

```cpp
for (int phase = 0; phase < phases; ++phase) {
    #pragma omp parallel for
    for (...) {
        ...
    }
}
```

Preferir:

```cpp
#pragma omp parallel
{
    ThreadContext& ctx =
        contexts[omp_get_thread_num()];

    for (int phase = 0; phase < phases; ++phase) {
        #pragma omp for schedule(static)
        for (std::int64_t i = 0; i < n; ++i) {
            process_phase(i, phase, ctx.pool);
        }

        #pragma omp barrier
    }
}
```

La región persistente conserva:

- Buffers locales.
- Heaps locales.
- Estado de cálculo.
- Afinidad.
- Caché caliente.

También evita crear repetidamente equipos de 100 o más hilos.

## 7. Afinidad y topología

Probar estas configuraciones por separado:

```bat
set OMP_DYNAMIC=FALSE
set OMP_PLACES=cores
set OMP_PROC_BIND=close
```

```bat
set OMP_DYNAMIC=FALSE
set OMP_PLACES=cores
set OMP_PROC_BIND=spread
```

`close` suele favorecer reutilización de caché; `spread` puede distribuir mejor la presión sobre memoria. Ninguna es universalmente superior.

La matriz de hilos debe estar limitada por la máquina:

```text
1, 2, 4, 8, 16, 32, 64, número de procesadores lógicos
```

Si el procesador tiene 32 hilos lógicos, ejecutar con 100 hilos puede medir sobremultiplexación, no escalabilidad. La aplicación debe informar siempre:

- Número de núcleos físicos.
- Número de procesadores lógicos.
- `OMP_NUM_THREADS`.
- `OMP_PLACES`.
- `OMP_PROC_BIND`.
- Tamaño total del dataset.
- Tamaño y distribución de las asignaciones.


## 8. Windows: private heap y VirtualAlloc

Si se necesita un heap independiente del heap por defecto, Windows permite crear *private heaps*. La documentación de Microsoft recomienda considerar heaps privados cuando una aplicación realiza asignaciones frecuentes. cite[^4_5]

Sin embargo, no hay que convertir cada hilo en un heap de Windows automáticamente. El coste de mantener demasiados heaps puede aumentar el consumo de memoria y fragmentar el espacio virtual.

Recomendación:

- Private heap por grupo de trabajo o NUMA node.
- Pool monotónico por hilo encima de ese heap.
- Reservas grandes mediante `VirtualAlloc`.
- No llamar a `VirtualAlloc` por objeto.

Para regiones enormes y persistentes:

```cpp
void* region = VirtualAlloc(
    nullptr,
    region_size,
    MEM_RESERVE | MEM_COMMIT,
    PAGE_READWRITE
);
```

La granularidad debe ser megabytes, no bytes. `VirtualAlloc` es una herramienta de reserva regional, no un reemplazo directo de `malloc`.

## 9. `MIMALLOC_ARENA_EAGER_COMMIT`

Probar explícitamente:

```bat
set MIMALLOC_ARENA_EAGER_COMMIT=0
```

```bat
set MIMALLOC_ARENA_EAGER_COMMIT=1
```

```bat
set MIMALLOC_ARENA_EAGER_COMMIT=2
```

El valor `2` es condicional para sistemas con *overcommit*; no debe etiquetarse como “modo rápido de Windows”. La configuración eager puede reducir latencia de confirmación, pero aumenta el compromiso virtual y puede provocar mayor presión de memoria. cite[^4_6]

Registrar:

- Commit size.
- Working set.
- Faults.
- Tiempo de arranque.
- Tiempo después del calentamiento.
- Rendimiento durante el pico.
- Fragmentación.

Microsoft recomienda utilizar VMMap y Windows Performance Toolkit para separar fugas de memoria virtual, fugas de heap y crecimiento normal del working set. cite[^4_7]

## 10. Diagnóstico formal con WPR/WPA

Para demostrar la hipótesis de contención:

```bat

```

Reiniciar el programa y capturar:

```bat

```

El criterio de aceptación no debe ser “mimalloc es más rápido”, sino:

```text
- menos muestras en RtlAllocateHeap/RtlFreeHeap
- menos tiempo en espera
- menos asignaciones por elemento
- mejor escalabilidad al aumentar hilos
- mismo resultado numérico
- memoria comprometida aceptable
```


## 11. Benchmark profesional

Usar al menos estas variantes:


| ID | Diseño |
| :-- | :-- |
| A | CRT + `malloc/free` por iteración |
| B | CRT + buffer reservado |
| C | CRT + pool por hilo |
| D | mimalloc global |
| E | mimalloc + pool por hilo |
| F | OpenMP `omp_thread_mem_alloc` |
| G | OpenMP `omp_pteam_mem_alloc` |
| H | pool por hilo + mimalloc para objetos grandes |

Ejecutar cada caso:

- 5 veces en calentamiento.
- 10 veces medidas.
- Con los mismos datos.
- Con afinidad fija.
- Con la misma frecuencia y política de energía.
- Sin incluir compilación.
- Separando tiempo de reserva inicial y tiempo de procesamiento.

Métricas:

$$
S(P)=\frac{T(1)}{T(P)}
$$

$$

$$

Además:

```text
allocaciones / elemento
bytes asignados / elemento
tiempo en malloc/free
tiempo de barreras
cache misses
branch misses
page faults
working set
commit size
```

Si B o C ya eliminan la mayor parte del tiempo, mimalloc es una optimización secundaria. Si D mejora incluso después de eliminar las asignaciones pequeñas, el problema incluye objetos persistentes, liberaciones remotas o fragmentación.

## Solución final recomendada

Para este caso concreto, la configuración SOTA que implementaría es:

```text
1. Una región #pragma omp parallel persistente.
2. Partición estática en bloques.
3. ThreadContext alignas(64) por hilo.
4. Pool monotónico por hilo para temporales.
5. Reset del pool por bloque.
6. Buffers preasignados antes del parallel.
7. mimalloc para objetos grandes o que sobreviven al bloque.
8. Colas de liberación por propietario para objetos remotos.
9. omp_pteam_mem_alloc solo para temporales compartidos del equipo.
10. OMP_PROC_BIND=close y spread comparados.
11. OMP_DYNAMIC=FALSE.
12. WPR/WPA para confirmar la espera real.
13. Eager commit medido con 0, 1 y 2.
14. Benchmark con escalabilidad hasta el número físico y lógico de hilos.
```

La mejora más importante no es `alignas(64)` ni `MIMALLOC_ARENA_EAGER_COMMIT=2` de forma aislada. Es **cambiar el modelo de propiedad y de vida de la memoria**: cada hilo obtiene un espacio reutilizable, los objetos temporales no se liberan individualmente y solo las asignaciones que realmente necesitan un allocator general llegan a mimalloc o al heap de Windows.

# Overhead de Desplazamiento por Offsets Múltiples en Sparse Rolling Interaction (SRI):Busca las mejoras y solucione sota para el siguiente tema

Diagnóstico: Procesar múltiples desplazamientos esparsos (p,q,r)(p, q, r)(p,q,r) en CliffordNet genera ramificaciones (branches) en el bucle principal que rompen la canalización SIMD.
Brecha / Cuello de Botella: Caída en la eficiencia del pipeline SIMD de la CPU a \<40%< 40%\<40% de utilización del FMA.
Solución SOTA V904: Desenrollado plano de bucles (Loop Unrolling) y máscaras de vectorización explícitas (\_mm512_mask_blend_ps).

El cuello de botella descrito no debe resolverse únicamente con “desenrollar y usar `_mm512_mask_blend_ps`”. En SRI, la mejora dominante consiste en **separar las rutas por desplazamiento, regularizar los datos y aplicar máscaras solo cuando sean necesarias**. La máscara elimina ramas del código, pero no hace que una operación esparsa sea gratuita; Intel advierte que el *masking* puede ser más lento que la ruta no enmascarada y que el *merge masking* puede introducir dependencias sobre el destino. cite[^5_1]

## Diagnóstico preciso

Supongamos una actualización:

$$
y_i =
\alpha_p x_{i+p}
+\alpha_q x_{i+q}
+\alpha_r x_{i+r}
$$

Una implementación problemática suele ser:

```cpp
for (int i = 0; i < n; ++i) {
    float value = 0.0f;

    if (valid(i + p))
        value += alpha_p * x[i + p];

    if (valid(i + q))
        value += alpha_q * x[i + q];

    if (valid(i + r))
        value += alpha_r * x[i + r];

    y[i] = value;
}
```

Las causas de la baja utilización de FMA son:

- Ramas dentro del bucle.
- Máscaras distintas en cada iteración.
- Índices irregulares.
- Cargas que no son contiguas.
- Dependencias entre acumulaciones.
- Baja intensidad aritmética.
- Coste de gather superior al de FMA.
- Colisiones o aliasing que impiden la vectorización.
- Desenrollado excesivo que aumenta presión de registros.

`_mm512_mask_blend_ps` selecciona elementos de dos vectores con una máscara `__mmask16`; la máscara no es un vector de `float`, sino un registro de predicación AVX-512. cite[^5_2]

## Solución SOTA: tres rutas

La implementación debe dividir el cálculo en tres zonas:

```text
Zona interior:
    todos los offsets válidos y accesos contiguos

Zona de frontera:
    uno o más offsets salen del rango

Zona irregular:
    índices verdaderamente esparsos o variables
```


### 1. Interior sin máscaras

Si `p`, `q` y `r` son constantes, el interior puede procesarse sin condiciones:

```cpp
const int begin = std::max({-p, -q, -r, 0});
const int end = std::min({n - p, n - q, n - r, n});

#pragma omp parallel for schedule(static)
for (int i = begin; i < end; ++i) {
    y[i] =
        alpha_p * x[i + p] +
        alpha_q * x[i + q] +
        alpha_r * x[i + r];
}
```

Este cambio es más importante que poner una máscara en todas las iteraciones. El compilador puede vectorizar la región interior con cargas regulares y FMA.

Con garantías de no aliasing:

```cpp
void sri_inner(
    const float* __restrict x,
    float* __restrict y,
    int begin,
    int end,
    int p,
    int q,
    int r,
    float alpha_p,
    float alpha_q,
    float alpha_r
) {
    #pragma omp simd aligned(x, y:64)
    for (int i = begin; i < end; ++i) {
        y[i] =
            alpha_p * x[i + p] +
            alpha_q * x[i + q] +
            alpha_r * x[i + r];
    }
}
```

El `aligned(x, y:64)` solo debe usarse si la alineación está realmente garantizada. Una promesa falsa puede producir errores o penalizaciones.

## 2. Ruta AVX-512 explícita

Para la zona interior:

```cpp
#include <immintrin.h>

void sri_avx512_inner(
    const float* __restrict x,
    float* __restrict y,
    int begin,
    int end,
    int p,
    int q,
    int r,
    float alpha_p,
    float alpha_q,
    float alpha_r
) {
    const __m512 vp = _mm512_set1_ps(alpha_p);
    const __m512 vq = _mm512_set1_ps(alpha_q);
    const __m512 vr = _mm512_set1_ps(alpha_r);

    int i = begin;

    for (; i + 16 <= end; i += 16) {
        __m512 acc = _mm512_setzero_ps();

        __m512 xp = _mm512_loadu_ps(x + i + p);
        __m512 xq = _mm512_loadu_ps(x + i + q);
        __m512 xr = _mm512_loadu_ps(x + i + r);

        acc = _mm512_fmadd_ps(xp, vp, acc);
        acc = _mm512_fmadd_ps(xq, vq, acc);
        acc = _mm512_fmadd_ps(xr, vr, acc);

        _mm512_storeu_ps(y + i, acc);
    }

    for (; i < end; ++i) {
        y[i] =
            alpha_p * x[i + p] +
            alpha_q * x[i + q] +
            alpha_r * x[i + r];
    }
}
```

Compilación GCC/MinGW:

```bat
g++ -O3 -march=skylake-avx512 -mfma -mavx512f ...
```

Para binarios portables, no se debe compilar todo el programa suponiendo AVX-512. Usar despacho por CPU:

```cpp
if (__builtin_cpu_supports("avx512f")) {
    sri_avx512(...);
} else if (__builtin_cpu_supports("avx2")) {
    sri_avx2(...);
} else {
    sri_scalar(...);
}
```

En Windows/MinGW también puede usarse `__attribute__((target("avx512f,fma")))` para aislar la función AVX-512.

## 3. Máscara únicamente en la frontera

La máscara es adecuada para el final del rango o para una frontera pequeña. No debe generarse dinámicamente en cada elemento.

```cpp
static inline __mmask16 tail_mask(int count) {
    if (count <= 0) return 0;
    if (count >= 16) return 0xFFFF;
    return static_cast<__mmask16>((1u << count) - 1u);
}
```

Carga y cálculo enmascarado:

```cpp
int remaining = end - i;
__mmask16 k = tail_mask(remaining);

__m512 xp = _mm512_maskz_loadu_ps(k, x + i + p);
__m512 xq = _mm512_maskz_loadu_ps(k, x + i + q);
__m512 xr = _mm512_maskz_loadu_ps(k, x + i + r);

__m512 acc = _mm512_setzero_ps();
acc = _mm512_mask3_fmadd_ps(xp, vp, acc, k);
acc = _mm512_mask3_fmadd_ps(xq, vq, acc, k);
acc = _mm512_mask3_fmadd_ps(xr, vr, acc, k);

_mm512_mask_storeu_ps(y + i, k, acc);
```

Siempre que sea posible, usar *zero masking* para evitar dependencia del destino. Intel señala que el *merge masking* puede conservar valores previos del registro y crear una dependencia adicional; el *zero masking* elimina esa dependencia. cite[^5_1]

Para el tail, también puede ser mejor ejecutar un bucle escalar de hasta 15 elementos. La máscara no siempre compensa el coste de preparar y ejecutar una iteración AVX-512 parcial.

## `_mm512_mask_blend_ps`: cuándo usarlo

La forma correcta es:

```cpp
__m512 result =
    _mm512_mask_blend_ps(mask, vector_a, vector_b);
```

Para cada lane:

- `mask = 0`: se selecciona `vector_a`.
- `mask = 1`: se selecciona `vector_b`.

Ejemplo:

```cpp
__m512 old_value = _mm512_loadu_ps(y + i);
__m512 new_value = _mm512_add_ps(old_value, contribution);

__m512 merged =
    _mm512_mask_blend_ps(valid_mask, old_value, new_value);

_mm512_storeu_ps(y + i, merged);
```

Pero si lo que se desea es calcular solo los lanes válidos, suele ser mejor usar una operación *write-masked*:

```cpp
_mm512_mask_storeu_ps(y + i, valid_mask, new_value);
```

o una FMA enmascarada:

```cpp
acc = _mm512_mask3_fmadd_ps(xp, vp, acc, valid_mask);
```

Usar `mask_blend` para cada contribución puede introducir más instrucciones de movimiento y mezcla que una operación directamente enmascarada. `_mm512_mask_blend_ps` es especialmente útil cuando se seleccionan dos resultados ya calculados; no es necesariamente la mejor primitiva para evitar una carga inválida.

## Cuatro alternativas para fronteras

### A. Padding

La opción más rápida suele ser añadir halo o padding:

```text
[p p p p] [datos válidos] [r r r r]
```

Entonces todas las cargas son válidas y el núcleo no necesita máscaras:

```cpp
y[i] = alpha_p * padded_x[i + p]
     + alpha_q * padded_x[i + q]
     + alpha_r * padded_x[i + r];
```

El padding debe contener un valor neutro adecuado:

- Cero para una suma.
- Identidad para un producto.
- Valor específico para una operación saturada.
- Valor de borde si SRI define condiciones periódicas o reflectantes.

El padding suele ser superior a las máscaras si el borde representa una fracción pequeña y conocida del trabajo.

### B. Separación interior/frontera

```cpp
process_interior_without_masks();
process_left_boundary_scalar();
process_right_boundary_scalar();
```

Es la opción más sencilla y generalmente muy eficaz.

### C. Máscara en la última vectorización

Adecuada cuando solo hay un tail o una frontera reducida.

### D. Índices clamped

```cpp
int j = std::min(std::max(i + p, 0), n - 1);
```

No es recomendable dentro del hot loop: introduce `min/max`, dependencia de índices y accesos potencialmente irregulares.

## Offset múltiple: desenrollado correcto

Un desenrollado plano puede procesar varios vectores por iteración:

```cpp
for (; i + 64 <= end; i += 64) {
    __m512 a0 = _mm512_loadu_ps(x + i + p);
    __m512 a1 = _mm512_loadu_ps(x + i + 16 + p);
    __m512 a2 = _mm512_loadu_ps(x + i + 32 + p);
    __m512 a3 = _mm512_loadu_ps(x + i + 48 + p);

    __m512 b0 = _mm512_loadu_ps(x + i + q);
    __m512 b1 = _mm512_loadu_ps(x + i + 16 + q);
    __m512 b2 = _mm512_loadu_ps(x + i + 32 + q);
    __m512 b3 = _mm512_loadu_ps(x + i + 48 + q);

    __m512 c0 = _mm512_loadu_ps(x + i + r);
    __m512 c1 = _mm512_loadu_ps(x + i + 16 + r);
    __m512 c2 = _mm512_loadu_ps(x + i + 32 + r);
    __m512 c3 = _mm512_loadu_ps(x + i + 48 + r);

    __m512 y0 = _mm512_mul_ps(a0, vp);
    __m512 y1 = _mm512_mul_ps(a1, vp);
    __m512 y2 = _mm512_mul_ps(a2, vp);
    __m512 y3 = _mm512_mul_ps(a3, vp);

    y0 = _mm512_fmadd_ps(b0, vq, y0);
    y1 = _mm512_fmadd_ps(b1, vq, y1);
    y2 = _mm512_fmadd_ps(b2, vq, y2);
    y3 = _mm512_fmadd_ps(b3, vq, y3);

    y0 = _mm512_fmadd_ps(c0, vr, y0);
    y1 = _mm512_fmadd_ps(c1, vr, y1);
    y2 = _mm512_fmadd_ps(c2, vr, y2);
    y3 = _mm512_fmadd_ps(c3, vr, y3);

    _mm512_storeu_ps(y + i,      y0);
    _mm512_storeu_ps(y + i + 16, y1);
    _mm512_storeu_ps(y + i + 32, y2);
    _mm512_storeu_ps(y + i + 48, y3);
}
```

Pero cuatro vectores desenrollados no son automáticamente mejores. El código usa muchos registros:

- 12 vectores de entrada.
- 4 acumuladores.
- 3 coeficientes.
- Registros temporales.
- Direcciones y máscaras.

Si la CPU no tiene suficientes registros físicos o el compilador derrama registros a la pila, el rendimiento cae. Probar unroll de 2 y 4:

```text
unroll 1: menor presión de registros
unroll 2: normalmente buen equilibrio
unroll 4: mayor ocultación de latencia
unroll 8: alto riesgo de spills
```

La profundidad del desenrollado debe decidirse con ensamblador y contadores de rendimiento, no por intuición.

## SRI realmente esparso: no usar gather por defecto

Si `p`, `q` y `r` son constantes, las cargas anteriores siguen siendo contiguas aunque los desplazamientos sean diferentes. Eso es favorable.

Si cada posición tiene índices independientes:

```cpp
x[index_p[i]]
x[index_q[i]]
x[index_r[i]]
```

entonces el problema cambia. AVX-512 puede usar gather:

```cpp
__m512i indices =
    _mm512_loadu_si512(index_p + i);

__m512 values =
    _mm512_i32gather_ps(indices, x, sizeof(float));
```

Pero gather suele ser mucho más caro que cargas contiguas si los datos no están en caché o no son cercanos. Las optimizaciones preferidas son:

1. Ordenar índices por localidad.
2. Agrupar desplazamientos iguales.
3. Convertir índices en deltas.
4. Construir listas por patrón `(p,q,r)`.
5. Reordenar nodos para mejorar localidad.
6. Procesar por tiles.
7. Usar gather solo en la cola verdaderamente irregular.

## Agrupación por patrón de offsets

Si cada interacción usa una combinación distinta:

```text
(p, q, r) = (1, 4, 8)
(p, q, r) = (1, 5, 8)
(p, q, r) = (2, 4, 9)
```

no conviene ejecutar todo en un solo bucle con `if`. Construir buckets:

```cpp
struct InteractionGroup {
    int p;
    int q;
    int r;
    std::vector<int> indices;
};
```

Después:

```cpp
for (const auto& group : groups) {
    process_group(group.p, group.q, group.r,
                  group.indices.data(),
                  group.indices.size());
}
```

Cada grupo tiene offsets constantes y puede usar una ruta especializada sin ramas internas. El coste de agrupar se amortiza si el patrón se reutiliza durante varias iteraciones.

Para un número pequeño y fijo de patrones, generar kernels especializados:

```cpp
template<int P, int Q, int R>
void sri_kernel(...);
```

o usar despacho por tabla de funciones.

## Layout de datos

El layout puede ser más importante que la intrínseca usada.

### AoS problemático

```cpp
struct Node {
    float value;
    int index;
    float weight;
    char flags;
};
```

Esto mezcla datos usados y no usados.

### SoA preferible

```cpp
struct InteractionSoA {
    float* value;
    float* weight;
    int* index_p;
    int* index_q;
    int* index_r;
};
```

Beneficios:

- Cargas homogéneas.
- Mejor vectorización.
- Menos ancho de memoria.
- Menos campos arrastrados a caché.
- Más facilidad para usar máscaras.

Si `p`, `q` y `r` son constantes por lote, no almacenar tres índices por elemento: almacenar el lote y sus offsets.

## Control de aliasing

El compilador puede evitar vectorizar si sospecha que `x` y `y` se solapan:

```cpp
void kernel(
    const float* __restrict x,
    float* __restrict y
);
```

También se puede usar:

```cpp
#pragma omp simd aligned(x, y:64) \
    linear(i:1)
```

No marcar `restrict` si existe alias real. La versión optimizada debe conservar una ruta segura si el contrato no garantiza independencia.

## Reducir la presión de máscaras

No calcular máscaras lane por lane:

```cpp
for (int i = 0; i < n; ++i) {
    __mmask16 mask = ...;
}
```

Preferir:

```cpp
for (i = interior_begin;
     i + 16 <= interior_end;
     i += 16) {
    // sin máscaras
}

if (i < interior_end) {
    // una única máscara de tail
}
```

Si hay un patrón periódico de validez, precomputar las máscaras:

```cpp
alignas(64) static constexpr std::uint16_t masks[] = {
    0xFFFF, 0xFFFE, 0xFFFC, 0xFFF8
};
```

Para máscaras variables por interacción, guardar una máscara compacta de 16 bits por tile en vez de reconstruirla con comparaciones.

## FMA: expectativas realistas

Una utilización de FMA inferior al 40% no siempre significa que el código tenga demasiadas ramas. SRI puede estar limitado por:

- Ancho de banda de memoria.
- Latencia de loads.
- Gather.
- Cachés.
- Dependencias de acumulación.
- Pocas operaciones aritméticas por byte.
- Front-end.
- Frecuencia reducida de AVX-512.
- Downclock por instrucciones vectoriales anchas.

Medir por separado:

```text
FP_ARITH_INST_RETIRED.512B_PACKED_SINGLE
FP_ARITH_INST_RETIRED.256B_PACKED_SINGLE
L1D/L2/LLC misses
MEM bandwidth
BR_MISP_RETIRED
uops_issued
uops_executed
cycle_activity.stalls_l1d_pending
```

Los nombres exactos de los contadores dependen de la microarquitectura. El rendimiento debe compararse contra el techo de memoria y contra el techo FMA de la CPU, no solo contra una cifra absoluta de utilización.

Además, AVX-512 puede reducir la frecuencia del procesador en ciertas generaciones. Una versión AVX2 bien diseñada puede superar a AVX-512 si el kernel es principalmente de memoria o si el downclock es importante.

## Implementación SOTA recomendada

La ruta final sería:

```text
1. Agrupar interacciones por patrón (p,q,r).
2. Convertir AoS a SoA.
3. Precalcular límites válidos.
4. Añadir padding/halo cuando sea semánticamente posible.
5. Ejecutar el interior sin ramas ni máscaras.
6. Usar AVX-512 FMA con cargas contiguas.
7. Desenrollar por 2 o 4 vectores.
8. Aplicar zero-masking solo en tails o fronteras.
9. Usar mask_blend únicamente para seleccionar resultados ya calculados.
10. Ejecutar frontera escalar si tiene pocos elementos.
11. Reservar gather para la región irregular.
12. Añadir __restrict y alineación solo con garantías reales.
13. Despachar AVX-512, AVX2 y scalar según la CPU.
14. Medir FMA, ancho de banda, branch misses y frecuencia.
```


### Pseudocódigo final

```cpp
for (const Pattern& pattern : patterns) {
    const int begin = pattern.valid_begin;
    const int end   = pattern.valid_end;

    // Interior: sin ramas y sin máscaras.
    sri_avx512_unrolled<2>(
        x, y,
        begin, end,
        pattern.p,
        pattern.q,
        pattern.r,
        pattern.alpha_p,
        pattern.alpha_q,
        pattern.alpha_r
    );

    // Tail: máscara única o scalar.
    sri_tail_masked_or_scalar(
        x, y,
        end, pattern.n,
        pattern.p,
        pattern.q,
        pattern.r
    );
}
```

La corrección más importante de la propuesta V904 es cambiarla de:

```text
desenrollado + mask_blend en todo el bucle
```

a:

```text
especialización por patrón
+ interior sin máscaras
+ desenrollado moderado
+ máscaras solo en frontera
+ padding cuando sea viable
+ gather únicamente para la parte realmente irregular
```

Esa arquitectura tiene muchas más probabilidades de elevar la utilización efectiva de FMA que aplicar `_mm512_mask_blend_ps` indiscriminadamente dentro del bucle principal.

# Profundiza en mejoras y solucione sota

La siguiente mejora SOTA debe centrarse en **regularizar el flujo de datos antes de escribir intrínsecas**. El objetivo no es maximizar el número de `_mm512_mask_blend_ps`, sino lograr que la mayoría de las iteraciones ejecuten cargas contiguas, FMA sin máscara y un número pequeño de ramas fuera del hot loop.

## Arquitectura V904 refinada

La ruta recomendada es:

```text
preprocesamiento de patrones
        ↓
clasificación interior / frontera / irregular
        ↓
kernel AVX-512 sin máscara para interior
        ↓
kernel AVX-512 desenrollado 2× o 4×
        ↓
tail enmascarado o escalar
        ↓
kernel scalar/gather para residuos irregulares
```

Intel recomienda separar los problemas de alineación, trip count, remainder, gather, presión de registros y dependencias; no existe una única directiva que resuelva todos esos casos. También recomienda revisar los patrones de acceso y migrar de AoS a SoA cuando el layout perjudica la vectorización. cite[^6_1]

## 1. Reestructurar SRI por patrones

Si cada interacción usa offsets variables, el error de diseño es procesarlas juntas:

```cpp
for (int i = 0; i < n; ++i) {
    if (kind[i] == 0) {
        ...
    } else if (kind[i] == 1) {
        ...
    } else {
        ...
    }
}
```

Eso introduce una rama por elemento. Mejor construir grupos:

```cpp
struct PatternGroup {
    int p;
    int q;
    int r;
    float alpha_p;
    float alpha_q;
    float alpha_r;
    std::vector<int> indices;
};
```

Después, cada grupo ejecuta un kernel especializado:

```cpp
for (const PatternGroup& g : groups) {
    sri_pattern_kernel(
        x,
        y,
        g.indices.data(),
        g.indices.size(),
        g.p,
        g.q,
        g.r,
        g.alpha_p,
        g.alpha_q,
        g.alpha_r
    );
}
```

Si los índices de `g.indices` son consecutivos o pueden reordenarse, el kernel puede convertirse en una secuencia de cargas regulares. Si no son consecutivos, aún se elimina la rama de patrón del bucle principal.

La agrupación tiene un coste de preprocesamiento. Es rentable cuando los mismos patrones se reutilizan en varias pasadas de SRI. Si los offsets cambian en cada iteración, usar agrupación por lotes y amortizar el coste durante varios pasos.

## 2. Separar interior y frontera

Para offsets constantes:

```cpp
int begin = std::max({0, -p, -q, -r});
int end   = std::min({n, n - p, n - q, n - r});
```

El interior queda libre de comprobaciones:

```cpp
#pragma omp parallel for simd schedule(simd:static)
for (int i = begin; i < end; ++i) {
    y[i] = alpha_p * x[i + p]
         + alpha_q * x[i + q]
         + alpha_r * x[i + r];
}
```

El modificador `schedule(simd:static)` puede asegurar que los chunks asignados sean adecuados para la longitud vectorial; Intel recomienda esta forma cuando el bucle está paralelizado y vectorizado simultáneamente. cite[^6_1]

La frontera se procesa por separado:

```cpp
for (int i = 0; i < begin; ++i)
    sri_scalar_boundary(i);

for (int i = end; i < n; ++i)
    sri_scalar_boundary(i);
```

Si la frontera representa menos del 1–5% del trabajo, esta ruta escalar suele ser mejor que enmascarar todo el cálculo.

## 3. Kernel AVX-512 con desenrollado controlado

```cpp
#include <immintrin.h>

template<int Unroll>
void sri_avx512(
    const float* __restrict x,
    float* __restrict y,
    int begin,
    int end,
    int p,
    int q,
    int r,
    float alpha_p,
    float alpha_q,
    float alpha_r
) {
    const __m512 vp = _mm512_set1_ps(alpha_p);
    const __m512 vq = _mm512_set1_ps(alpha_q);
    const __m512 vr = _mm512_set1_ps(alpha_r);

    int i = begin;
    constexpr int W = 16;
    constexpr int step = Unroll * W;

    for (; i + step <= end; i += step) {
        __m512 a[Unroll];
        __m512 b[Unroll];
        __m512 c[Unroll];
        __m512 acc[Unroll];

        #pragma unroll
        for (int u = 0; u < Unroll; ++u) {
            const int j = i + u * W;

            a[u] = _mm512_loadu_ps(x + j + p);
            b[u] = _mm512_loadu_ps(x + j + q);
            c[u] = _mm512_loadu_ps(x + j + r);

            acc[u] = _mm512_mul_ps(a[u], vp);
            acc[u] = _mm512_fmadd_ps(b[u], vq, acc[u]);
            acc[u] = _mm512_fmadd_ps(c[u], vr, acc[u]);

            _mm512_storeu_ps(y + j, acc[u]);
        }
    }

    for (; i + W <= end; i += W) {
        __m512 acc = _mm512_mul_ps(
            _mm512_loadu_ps(x + i + p), vp);

        acc = _mm512_fmadd_ps(
            _mm512_loadu_ps(x + i + q), vq, acc);

        acc = _mm512_fmadd_ps(
            _mm512_loadu_ps(x + i + r), vr, acc);

        _mm512_storeu_ps(y + i, acc);
    }

    for (; i < end; ++i) {
        y[i] = alpha_p * x[i + p]
             + alpha_q * x[i + q]
             + alpha_r * x[i + r];
    }
}
```

En producción, probar `Unroll=1`, `2` y `4`. Una plantilla con arrays locales puede incrementar la presión de registros; revisar el ensamblador para verificar que no aparecen stores/loads temporales a la pila.

Intel Advisor identifica el *register spilling* y recomienda reducir el factor de desenrollado o dividir el bucle cuando todos los registros vectoriales están ocupados. cite[^6_1]

## 4. No usar `mask_blend` como reemplazo universal

`_mm512_mask_blend_ps(k, a, b)` selecciona `a` cuando el bit es cero y `b` cuando es uno. No es una operación de “ejecutar solo los lanes válidos”; calcula el blend entre dos vectores. cite[^6_2]

Usarlo así:

```cpp
result = _mm512_mask_blend_ps(mask, old_value, new_value);
```

es correcto si ambos vectores ya existen.

Para operaciones parciales, suele ser mejor:

```cpp
acc = _mm512_mask3_fmadd_ps(value, coefficient, acc, mask);
```

Para almacenar solo lanes válidos:

```cpp
_mm512_mask_storeu_ps(dst, mask, acc);
```

Para cargar con ceros en lanes inválidos:

```cpp
__m512 value =
    _mm512_maskz_loadu_ps(mask, src);
```


### Regla práctica

| Situación | Primitiva preferida |
| :-- | :-- |
| Seleccionar dos resultados completos | `_mm512_mask_blend_ps` |
| Calcular solo lanes válidos | FMA enmascarada |
| Cargar lanes válidos y poner cero al resto | `_mm512_maskz_loadu_ps` |
| Escribir solo lanes válidos | `_mm512_mask_storeu_ps` |
| Tail muy pequeño | Scalar |
| Interior completo | Sin máscara |

Esto evita introducir blends adicionales en el núcleo FMA.

## 5. Tail y máscaras

Para 1–15 elementos restantes:

```cpp
int remaining = end - i;

if (remaining >= 8) {
    __mmask16 mask =
        static_cast<__mmask16>((1u << remaining) - 1u);

    __m512 acc = _mm512_maskz_loadu_ps(
        mask, x + i + p);

    acc = _mm512_mask3_fmadd_ps(
        _mm512_maskz_loadu_ps(mask, x + i + q),
        vq,
        acc,
        mask
    );

    acc = _mm512_mask3_fmadd_ps(
        _mm512_maskz_loadu_ps(mask, x + i + r),
        vr,
        acc,
        mask
    );

    _mm512_mask_storeu_ps(y + i, mask, acc);
} else {
    for (; i < end; ++i)
        y[i] = alpha_p * x[i + p]
             + alpha_q * x[i + q]
             + alpha_r * x[i + r];
}
```

No fijar `8` como regla universal. El umbral debe compararse:

```text
tail escalar
tail AVX-512 enmascarado
tail AVX2
```

Intel indica que un remainder vectorizado puede ser ineficiente si contiene pocas iteraciones y que, en esos casos, una cola escalar puede resultar mejor. cite[^6_1]

## 6. Padding y halo

Cuando la semántica lo permita, añadir un halo es normalmente superior al masking:

```cpp
struct PaddedField {
    int halo;
    int n;
    std::vector<float> data;

    float* interior() {
        return data.data() + halo;
    }
};
```

El kernel trabaja sobre el área interior y no necesita validar:

```cpp
float* x0 = field.interior();

for (int i = 0; i < n; i += 16) {
    __m512 acc = _mm512_mul_ps(
        _mm512_loadu_ps(x0 + i + p),
        vp
    );

    acc = _mm512_fmadd_ps(
        _mm512_loadu_ps(x0 + i + q),
        vq,
        acc
    );

    acc = _mm512_fmadd_ps(
        _mm512_loadu_ps(x0 + i + r),
        vr,
        acc
    );

    _mm512_storeu_ps(y + i, acc);
}
```

El halo debe actualizarse de forma explícita antes de la fase SRI. Para condiciones periódicas, el halo puede copiar los extremos; para condiciones de borde constantes, puede llenarse con el valor correspondiente.

## 7. SoA y precomputación de pesos

Si cada interacción contiene índice y peso:

```cpp
struct Interaction {
    int index;
    float weight;
};
```

es mejor separar:

```cpp
struct InteractionSoA {
    int* index;
    float* weight;
};
```

El kernel puede cargar pesos de forma vectorial y reducir ancho de memoria. Si los pesos son constantes por patrón, mantenerlos en registros:

```cpp
const __m512 vp = _mm512_set1_ps(alpha_p);
```

Si los pesos cambian por elemento, organizar los pesos por grupo y por tile:

```text
weights[p][tile][lane]
weights[q][tile][lane]
weights[r][tile][lane]
```

Esto transforma parte del acceso irregular en acceso secuencial.

## 8. Índices: eliminar gather cuando sea posible

Intel recomienda revisar si un acceso detectado como gather es realmente:

- Unit stride.
- Constant stride.
- Uniform.
- Vertical invariant.

Si el acceso es regular, el código debe reestructurarse para que el compilador lo vea como tal. Intel también recomienda SoA para reducir accesos ineficientes. cite[^6_1]

En vez de:

```cpp
value = x[index[i]];
```

para cada lane, intentar:

```cpp
const int base = tile_base;
const int offset = lane_pattern[lane];
value = x[base + offset];
```

o reordenar los datos a:

```text
tile 0: lanes consecutivos
tile 1: lanes consecutivos
tile 2: lanes consecutivos
```

Si el gather es inevitable:

- Agrupar índices cercanos.
- Ordenar por página o línea de caché.
- Procesar tiles pequeños.
- Mantener la tabla de índices en caché.
- Evitar mezclar gather y scatter en el mismo hot loop.
- Separar contribuciones por localidad.


## 9. Evitar dependencia entre acumulaciones

Si la operación acumula muchos términos:

```cpp
acc += contribution_0;
acc += contribution_1;
acc += contribution_2;
...
```

hay una cadena de dependencia. Separar acumuladores:

```cpp
__m512 acc0 = _mm512_setzero_ps();
__m512 acc1 = _mm512_setzero_ps();

acc0 = _mm512_fmadd_ps(x0, w0, acc0);
acc1 = _mm512_fmadd_ps(x1, w1, acc1);

acc0 = _mm512_fmadd_ps(x2, w2, acc0);
acc1 = _mm512_fmadd_ps(x3, w3, acc1);

__m512 result = _mm512_add_ps(acc0, acc1);
```

Esto puede ocultar latencia, pero aumenta registros. Ajustar el número de acumuladores según el microprocesador.

## 10. OpenMP correctamente combinado con SIMD

Extraer llamadas OpenMP del bucle:

```cpp
#pragma omp parallel
{
    const int tid = omp_get_thread_num();

    #pragma omp for simd schedule(static)
    for (int i = begin; i < end; ++i) {
        ...
    }
}
```

No ejecutar `omp_get_thread_num()` dentro del hot loop. Intel señala que las llamadas OpenMP dentro del bucle pueden impedir la vectorización efectiva y recomienda moverlas a la región exterior. cite[^6_1]

Para GCC:

```bat
g++ -O3 -march=native -fopenmp -mfma ^
    -fopt-info-vec-optimized ^
    -fopt-info-vec-missed ^
    -fsave-optimization-record ^
    sri.cpp -o sri.exe
```

GCC documenta `-fopt-info-vec-missed` para informar oportunidades fallidas de vectorización; también permite generar un registro de optimización en formato JSON comprimido. cite[^6_3]

Interpretar especialmente mensajes como:

```text
not vectorized: possible aliasing
not vectorized: control flow in loop
not vectorized: unsupported data-type
not vectorized: bad loop form
not vectorized: vectorization is not profitable
```

No usar `#pragma omp simd` para ocultar dependencias reales. Si existe dependencia, reformular el algoritmo o usar `reduction`, `safelen` o privatización solo cuando sea correcto.

## 11. Despacho por ISA

Crear tres rutas:

```text
SRI scalar
SRI AVX2 + FMA
SRI AVX-512 + FMA
```

Ejemplo:

```cpp
using Kernel = void(*)(const float*, float*, int, int, int, int, int,
                       float, float, float);

Kernel select_kernel() {
    if (__builtin_cpu_supports("avx512f") &&
        __builtin_cpu_supports("fma")) {
        return sri_avx512_dispatch;
    }

    if (__builtin_cpu_supports("avx2") &&
        __builtin_cpu_supports("fma")) {
        return sri_avx2_dispatch;
    }

    return sri_scalar;
}
```

No asumir que AVX-512 siempre gana. Si el kernel está limitado por memoria, AVX2 puede ofrecer una frecuencia más alta y un rendimiento total superior.

## 12. Diagnóstico que debe acompañar V904

Medir tres techos:

### Techo de control

```text
branch misses
branch instructions
mis-predicted branches
```


### Techo de memoria

```text
L1D misses
L2 misses
LLC misses
memory bandwidth
load/store stalls
```


### Techo aritmético

```text
FP32 FMA retired
vector width used
cycles with backend pressure
register spills
```

La utilización FMA inferior al 40% no demuestra por sí sola que las ramas sean la única causa. Puede indicar que cada FMA espera una carga irregular o que el kernel ya está limitado por ancho de banda.

## Plan de experimentos

| Variante | Cambio |
| :-- | :-- |
| A | Kernel scalar con ramas |
| B | Interior/frontera separado |
| C | Interior AVX-512 automático |
| D | AVX-512 explícito sin máscara |
| E | D + unroll 2 |
| F | D + unroll 4 |
| G | D + padding |
| H | D + agrupación por patrón |
| I | D + SoA |
| J | D + gather solo en irregular |

Medir:

- Tiempo total.
- Tiempo de preprocesamiento.
- Tiempo del kernel.
- FMA retiradas.
- Branch misses.
- Gather ejecutados.
- Loads/stores.
- Spills.
- Frecuencia efectiva.
- Ancho de banda.
- Consumo energético si importa.

La variante SOTA no es necesariamente la que tenga la mayor utilización FMA. Debe minimizar el tiempo total manteniendo la precisión y el consumo aceptables.

## Implementación final recomendada

```text
1. Preagrupar por (p,q,r).
2. Reordenar índices para aumentar localidad.
3. Usar SoA.
4. Crear halo/padding cuando la semántica lo permita.
5. Calcular límites interior y frontera una sola vez.
6. Ejecutar el interior con cargas contiguas sin máscara.
7. Usar FMA AVX-512 y desenrollado 2× inicialmente.
8. Probar 4× solo si no hay spills.
9. Usar zero-masked FMA para tails moderados.
10. Usar scalar para tails pequeños.
11. Reservar mask_blend para selección entre resultados completos.
12. Evitar gather mediante reordenamiento; usarlo solo en residuos.
13. Mover llamadas OpenMP fuera del bucle.
14. Verificar `restrict`, alineación y dependencias.
15. Comparar AVX2 contra AVX-512 por posible reducción de frecuencia.
16. Confirmar todo con `-fopt-info-vec` y contadores de hardware.
```

La corrección central de V904 queda así:

```text
No:
ramas → mask_blend por elemento → gather generalizado

Sí:
agrupación → padding/interior regular
       → FMA sin máscara
       → desenrollado 2×/4× validado
       → máscara solo en tail
       → scalar/gather únicamente para excepciones
```

Con esa estructura, la máscara deja de ser un sustituto costoso del control de flujo y pasa a ser una herramienta localizada para los casos donde realmente aporta valor.

# Penalización de Tráfico NUMA en Sistemas Multi-Socket / CPUS Heterogéneas:Busca las mejoras y solucione sota para el siguiente tema

Diagnóstico: Asignar memoria para tensores masivos en el hilo principal (Master Thread) provoca que el nodo NUMA local al master atienda las solicitudes de todos los demás núcleos.
Brecha / Cuello de Botella: Saturación del bus Inter-Socket (QPI/UPI/Infinity Fabric) reduciendo el throughput a \<30%< 30%\<30% del límite físico.
Solución SOTA V904: Estrategia First-Touch obligatoria dentro de la región paralela e inicialización del tensor por el hilo que lo procesará.

La solución SOTA correcta no es solo “hacer first-touch”. En sistemas multi-socket y CPU heterogéneas, hay que combinar **first-touch, afinidad estable, partición por nodo, distribución de páginas y correspondencia entre hilo, datos y memoria**. Si solo se inicializa en paralelo pero los hilos después migran o `schedule(dynamic)` rompe la localidad, el beneficio puede desaparecer.

## Diagnóstico preciso

`malloc` o `VirtualAlloc` reservan principalmente espacio virtual. Las páginas físicas suelen asociarse cuando se escriben por primera vez. Si el hilo master inicializa todo el tensor, esas páginas quedan normalmente asociadas al nodo cercano a ese hilo; después, los demás sockets realizan accesos remotos.

En NUMA, cada nodo tiene procesadores y memoria local conectados mediante una interconexión coherente. El acceso al nodo local suele tener menor latencia y mayor ancho de banda efectivo que el acceso remoto. Windows permite consultar la topología, asignar memoria con un nodo preferido y verificar el nodo físico de las páginas mediante `QueryWorkingSetEx`. cite[^7_1]

Pero hay tres matices importantes:

- First-touch depende del primer acceso físico a cada página, no del hilo que llamó a `malloc`.
- `first-touch` no corrige una afinidad incorrecta.
- Si varios hilos acceden a la misma página durante la inicialización, el propietario de esa página puede no corresponder a la partición posterior.


## Arquitectura SOTA

```text
descubrir topología NUMA
        ↓
fijar hilos a nodos / grupos
        ↓
particionar tensor por páginas
        ↓
first-touch paralelo con la misma partición del cálculo
        ↓
procesar localmente con schedule(static)
        ↓
reducir comunicación entre sockets
```

La regla central es:

```text
quien inicializa la página debe ser, idealmente,
el mismo hilo o nodo que la consumirá principalmente.
```

OpenMP define `OMP_PLACES` y `OMP_PROC_BIND` para expresar los lugares de ejecución y evitar que los hilos se muevan libremente. `spread` distribuye los hilos entre los lugares disponibles; `close` los mantiene más próximos al hilo padre. cite[^7_2]

## 1. First-touch correcto

### Patrón incorrecto

```cpp
std::vector<float> tensor(elements);

#pragma omp parallel for
for (int i = 0; i < work; ++i) {
    compute(i, tensor.data());
}
```

El constructor puede haber escrito o puesto a cero todo el `vector` desde el hilo principal. En ese caso, la fase paralela ya empieza con páginas colocadas en el nodo del master.

### Patrón correcto

```cpp
std::vector<float> tensor(elements);

#pragma omp parallel for schedule(static)
for (std::int64_t i = 0; i < elements; ++i) {
    tensor[i] = 0.0f;
}
```

La inicialización debe cubrir toda la memoria que se utilizará, y debe mantener la misma distribución que la fase de cálculo:

```cpp
#pragma omp parallel
{
    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < elements; ++i)
        tensor[i] = initial_value(i);

    #pragma omp barrier

    #pragma omp for schedule(static)
    for (std::int64_t i = 0; i < work; ++i)
        process(i, tensor.data());
}
```

La barrera es necesaria si todos los hilos deben observar la inicialización completa antes de continuar.

## 2. Alinear la partición con las páginas

No basta con dividir por número de elementos; hay que evitar que una página sea compartida entre particiones NUMA.

Con una página de 4 KiB:

```cpp
constexpr std::size_t page_bytes = 4096;
constexpr std::size_t elements_per_page =
    page_bytes / sizeof(float);
```

Para particionar por páginas:

```cpp
const std::size_t pages =
    (elements + elements_per_page - 1) /
    elements_per_page;

#pragma omp parallel for schedule(static)
for (std::size_t page = 0; page < pages; ++page) {
    const std::size_t begin =
        page * elements_per_page;
    const std::size_t end =
        std::min(begin + elements_per_page, elements);

    for (std::size_t i = begin; i < end; ++i)
        tensor[i] = initial_value(i);
}
```

Esto evita que un límite de chunk divida innecesariamente una página entre dos hilos. Para tensores grandes y acceso secuencial, puede ser útil usar bloques de varias páginas, por ejemplo 2 MiB, si el sistema y la configuración de páginas grandes lo permiten.

## 3. La afinidad debe fijarse antes del first-touch

Configuración inicial:

```bat
set OMP_DYNAMIC=FALSE
set OMP_PROC_BIND=spread
set OMP_PLACES=cores
```

En un sistema donde cada socket debe recibir una parte uniforme del trabajo:

```bat
set OMP_PROC_BIND=spread
set OMP_PLACES=numa_domains
```

`numa_domains` no está soportado de forma idéntica por todos los runtimes; conviene consultar `omp_get_num_places()` y `omp_get_place_num_procs()` al inicio.

Para explorar:

```cpp
#pragma omp parallel proc_bind(spread)
{
    ...
}
```

o:

```cpp
#pragma omp parallel proc_bind(close)
{
    ...
}
```

Usar `spread` para distribuir trabajo entre sockets y `close` para una segunda región que reutilice intensamente datos locales. La elección depende de si el cuello es ancho de banda agregado, caché o comunicación.

Si `OMP_PROC_BIND=false`, el runtime puede mover los hilos entre lugares, rompiendo la correspondencia entre páginas y consumidores. cite[^7_2]

## 4. Evitar `schedule(dynamic)` en la fase NUMA

Este patrón es peligroso:

```cpp
#pragma omp parallel for schedule(dynamic)
for (int i = 0; i < n; ++i)
    process(i, tensor);
```

El hilo que inicializó una región puede no ser el que luego la procese. Además, `dynamic` puede llevar hilos a páginas remotas.

Preferir:

```cpp
#pragma omp parallel for schedule(static)
for (int block = 0; block < blocks; ++block)
    process_block(block);
```

Si el trabajo es irregular, usar bloques grandes y una cola dinámica por nodo, no una cola global para todos los sockets:

```text
socket 0 → cola local 0 → memoria local 0
socket 1 → cola local 1 → memoria local 1
```

El robo de trabajo entre nodos debe ser una excepción, no el camino normal.

## 5. Partición explícita por NUMA node

Para tensores masivos, la solución más controlable es asignar una región por nodo:

```cpp
struct NumaShard {
    void* base = nullptr;
    std::size_t bytes = 0;
    unsigned short node = 0;
};
```

En Windows, `VirtualAllocExNuma` permite indicar el nodo preferido para una región. Sin embargo, la función no garantiza por sí sola que todas las páginas físicas terminen en ese nodo: reserva o compromete el espacio virtual y el sistema puede recurrir a otro nodo si el preferido no tiene páginas disponibles. cite[^7_1]

Ejemplo conceptual:

```cpp
#include <windows.h>
#include <stdexcept>

void* allocate_numa(std::size_t bytes,
                    unsigned short node) {
    void* ptr = VirtualAllocExNuma(
        GetCurrentProcess(),
        nullptr,
        bytes,
        MEM_RESERVE | MEM_COMMIT,
        PAGE_READWRITE,
        node
    );

    if (!ptr)
        throw std::bad_alloc{};

    return ptr;
}
```

Después de reservar cada shard, realizar first-touch desde los hilos vinculados al mismo nodo:

```cpp
#pragma omp parallel
{
    const int tid = omp_get_thread_num();
    const int node = thread_to_node(tid);

    float* shard =
        static_cast<float*>(shards[node].base);

    #pragma omp for schedule(static)
    for (std::int64_t i = 0;
         i < shard_elements[node];
         ++i) {
        shard[i] = initial_value(node, i);
    }
}
```

La función `thread_to_node` no debe suponerse a partir del número de hilo. Debe construirse usando la topología real del sistema.

## 6. Topología Windows y processor groups

En máquinas con más de 64 procesadores lógicos, hay que considerar processor groups. Las APIs antiguas de afinidad pueden no representar correctamente una topología moderna con nodos que abarcan varios grupos. Microsoft recomienda las APIs extendidas, como `GetLogicalProcessorInformationEx`, `GetNumaProcessorNodeEx`, `GetNumaNodeProcessorMaskEx` y `SetThreadGroupAffinity`. cite[^7_1]

No usar una tabla simplista como:

```cpp
node = cpu_id / cores_per_socket;
```

En CPU heterogéneas o sistemas con varios grupos, la relación puede no ser lineal. Obtener:

- Número real de nodos NUMA.
- Procesadores de cada nodo.
- Grupo de cada procesador.
- Núcleos físicos.
- SMT siblings.
- Capacidad relativa de los núcleos.

`SetThreadIdealProcessorEx` solo ofrece una sugerencia al scheduler; no equivale necesariamente a una afinidad estricta. Además, en Windows recientes puede modificar el grupo primario del hilo al grupo del procesador ideal. cite[^7_3]

## 7. CPU heterogénea: P-cores, E-cores y NUMA

En una CPU híbrida, no basta con distinguir sockets. Los núcleos pueden tener:

- Diferente rendimiento por ciclo.
- Diferente ancho de ejecución.
- Diferente frecuencia.
- Diferente capacidad de ancho de banda efectivo.
- Diferentes preferencias del scheduler.

Para cargas de memoria:

```text
P-cores → bloques con mayor intensidad o menor latencia
E-cores → bloques independientes y throughput sostenido
```

Pero no asignar simplemente mitad del tensor a P-cores y mitad a E-cores. Medir capacidad por núcleo y repartir proporcionalmente:

$$
w_i = \frac{C_i}{\sum_j C_j}
$$

donde $C_i$ es la capacidad medida del grupo de núcleos. La partición de memoria debe usar los mismos pesos para el first-touch y para el procesamiento.

En CPU heterogénea, también puede ser preferible limitar la ejecución a P-cores si:

- El algoritmo tiene sincronizaciones frecuentes.
- La latencia domina.
- E-cores saturan un controlador de memoria compartido.
- El runtime OpenMP no expresa bien la topología híbrida.


## 8. Layout: tensor por shards, no un bloque monolítico

Un tensor global puede obligar a todos los sockets a acceder a regiones remotas. Para SRI o redes con interacción local, usar shards:

```cpp
struct TensorShard {
    float* data;
    std::size_t rows;
    std::size_t cols;
    int owner_node;
};
```

Cada shard contiene:

- Datos propios del nodo.
- Halo para dependencias vecinas.
- Buffers temporales locales.
- Acumuladores locales.
- Cola de actualizaciones remotas.

La fase de cálculo usa el shard local:

```text
shard local → acceso local
halo → comunicación explícita
resultado → reducción local
```

En lugar de permitir que cada hilo escriba directamente en datos de otro socket, acumular localmente y reducir por lotes.

## 9. Halo exchange en lugar de accesos remotos repetidos

Para una dependencia entre nodos:

```text
Nodo 0: [datos propios] [halo derecho]
Nodo 1: [halo izquierdo] [datos propios]
```

Estrategia:

1. Procesar el interior local.
2. Empaquetar los valores de frontera.
3. Copiar halos una vez.
4. Procesar las regiones cercanas al borde.
5. Reducir resultados.

Esto cambia muchos accesos remotos pequeños por una transferencia contigua y amortizada. Es especialmente útil cuando SRI usa offsets limitados `p`, `q`, `r`.

## 10. Interleave como alternativa, no como sustituto

Si todos los sockets acceden uniformemente a todo el tensor, first-touch por propietario puede no ser ideal. En ese caso, distribuir páginas de forma intercalada puede aumentar el ancho de banda agregado:

```text
página 0 → nodo 0
página 1 → nodo 1
página 2 → nodo 2
...
```

Usar interleave cuando:

- El acceso es global y uniforme.
- No existe un propietario claro.
- Todos los sockets recorren todo el tensor.
- La replicación es demasiado costosa.

Usar first-touch cuando:

- Cada hilo trabaja principalmente en su shard.
- Hay una partición espacial clara.
- Las escrituras son locales.
- Se puede mantener la afinidad.

No mezclar una estrategia de interleave con una expectativa de localidad estricta por hilo.

## 11. Replicación de datos de solo lectura

Si un tensor o tabla se lee desde todos los sockets y es relativamente pequeño, replicarlo por nodo puede ser mejor que pagar tráfico remoto continuamente:

```text
tabla_global → copia nodo 0
             → copia nodo 1
             → copia nodo 2
```

Coste:

$$
M_{\text{total}} = N_{\text{nodos}} \times M_{\text{copia}}
$$

La replicación es atractiva si:

- Los datos son de solo lectura.
- La tabla cabe razonablemente en memoria.
- El tráfico remoto se repite muchas veces.
- La copia se amortiza durante numerosas iteraciones.

Para datos modificables, usar reducción o actualización por propietario, no escrituras simultáneas remotas.

## 12. Page size y TLB

Tensores masivos pueden sufrir tanto por tráfico remoto como por fallos de TLB. Considerar páginas grandes si la plataforma y las políticas de seguridad lo permiten:

- Reducen entradas de página necesarias.
- Disminuyen page walks.
- Mejoran recorridos secuenciales grandes.
- Pueden reducir overhead de first-touch.

Pero las páginas grandes reducen la granularidad de colocación. Una página de 2 MiB no puede repartirse con la misma precisión que páginas de 4 KiB. Si una página grande contiene datos usados por varios sockets, puede aumentar el tráfico remoto.

Regla:

```text
página pequeña → mejor granularidad NUMA
página grande → menor presión TLB
```

Elegir según el patrón de acceso.

## 13. Verificar la colocación física

No asumir que first-touch funcionó. En Windows:

- `QueryWorkingSetEx` puede indicar el nodo de las páginas residentes.
- WPR/WPA puede ayudar a analizar fallos de página y actividad del sistema.
- Intel VTune puede mostrar accesos remotos y ancho de banda por socket.
- AMD uProf puede mostrar tráfico entre nodos y utilización de controladores de memoria.

Microsoft documenta un ejemplo que reserva con `VirtualAllocExNuma`, toca cada página y luego consulta su ubicación física con `QueryWorkingSetEx`. cite[^7_4]

Comprobar:

```text
% de páginas en nodo esperado
% de lecturas remotas
% de escrituras remotas
bandwidth por socket
UPI/Infinity Fabric traffic
latencia media
page faults durante warm-up
```


## 14. Benchmark correcto

Comparar estas variantes:


| Variante | Inicialización | Afinidad | Distribución |
| :-- | :-- | :-- | :-- |
| A | Master thread | Libre | Nodo del master |
| B | First-touch paralelo | Libre | Variable |
| C | First-touch paralelo | `spread` | Por socket |
| D | Shards explícitos | Fija | Local por nodo |
| E | Interleave | Fija | Balance global |
| F | Shards + halos | Fija | Local con comunicación |
| G | Datos replicados | Fija | Lecturas locales |

Medir:

- Tiempo de inicialización.
- Tiempo de warm-up.
- Tiempo de cálculo.
- Bandwidth total.
- Bandwidth por socket.
- Tráfico inter-socket.
- Latencia de memoria local/remota.
- Page faults.
- Working set.
- Escalabilidad al añadir sockets.
- Variación entre ejecuciones.

El resultado “menos de 30% del límite físico” debe separarse en:

```text
límite de memoria local
límite de memoria agregado
límite del interconnect
límite del controlador de memoria
```

Si el algoritmo es remoto por diseño, reducir UPI puede bajar el throughput total. El objetivo no es minimizar tráfico remoto a cualquier precio, sino maximizar rendimiento total manteniendo la comunicación necesaria.

## Solución SOTA V904

La implementación recomendada sería:

```text
1. Detectar nodos, grupos y procesadores reales.
2. Fijar OMP_PROC_BIND y OMP_PLACES antes de crear regiones.
3. Crear un shard por NUMA node.
4. Reservar cada shard con VirtualAllocExNuma o allocator NUMA-aware.
5. Ejecutar first-touch dentro de una región paralela.
6. Usar la misma partición estática en inicialización y cálculo.
7. Alinear cortes con páginas.
8. Mantener schedule(static).
9. Evitar dynamic y work stealing entre sockets.
10. Usar halos para dependencias de frontera.
11. Replicar tablas pequeñas de solo lectura.
12. Intercalar páginas solo cuando el acceso sea global.
13. Usar páginas grandes únicamente tras validar la granularidad NUMA.
14. Verificar colocación con QueryWorkingSetEx y contadores de hardware.
15. Rebalancear P-cores/E-cores según capacidad medida.
```


### Esqueleto final

```cpp
initialize_topology();
configure_thread_affinity();

std::vector<NodeShard> shards =
    allocate_shards_per_numa_node();

#pragma omp parallel proc_bind(spread)
{
    const int tid = omp_get_thread_num();
    const int node = topology.node_of_thread(tid);

    NodeShard& shard = shards[node];

    #pragma omp for schedule(static)
    for (std::size_t i = 0;
         i < shard.elements;
         ++i) {
        shard.data[i] = initial_value(node, i);
    }

    #pragma omp barrier

    #pragma omp for schedule(static)
    for (std::size_t block = 0;
         block < shard.blocks;
         ++block) {
        process_local_block(shard, block);
    }

    exchange_halos(shards, node);
}
```

La mejora esencial es pasar de:

```text
master allocates and initializes everything
→ every socket reads remote pages
```

a:

```text
topology-aware partition
→ affinity
→ first-touch by owner
→ static local processing
→ explicit halo/reduction
```

First-touch es obligatorio para V904, pero no suficiente. La solución realmente SOTA es **first-touch + afinidad + partición por nodo + comunicación explícita de halos + verificación física de las páginas**.

# Profundiza en mejoras y solucione sota

La mejora SOTA debe convertir NUMA en una propiedad explícita del algoritmo, no en una consecuencia accidental del scheduler. First-touch es necesario, pero la solución completa exige **ownership por nodo, afinidad real, partición por páginas, shards locales y comunicación explícita**.

## Objetivo técnico

El diseño debe cumplir esta relación:

```text
hilo → nodo NUMA → shard de memoria → bloques de trabajo
```

Si el hilo que procesa un bloque cambia de nodo, o si el bloque fue inicializado por otro socket, se rompe la localidad.

La arquitectura recomendada es:

```text
topología
  ↓
mapeo hilo/nodo
  ↓
reserva por nodo
  ↓
first-touch por propietario
  ↓
procesamiento estático local
  ↓
halo/reducción entre nodos
```

En Windows, un nodo NUMA puede estar asociado a un processor group; en equipos con más de 64 procesadores lógicos, no se debe asumir que una máscara de afinidad simple representa toda la máquina. Microsoft documenta `GetNumaNodeProcessorMaskEx` y `SetThreadGroupAffinity` para manejar esa topología. cite[^8_1]

## 1. Detectar la topología real

No calcular el nodo con:

```cpp
node = cpu_id / cores_per_socket;
```

Esto falla en:

- Processor groups.
- Nodos NUMA asimétricos.
- CPU híbridas.
- Nodos que cruzan grupos.
- Máquinas virtuales.
- Configuraciones con SMT irregular.

Construir una tabla:

```cpp
struct CpuInfo {
    WORD group;
    BYTE processor;
    BYTE numa_node;
    bool is_smt;
    bool is_performance_core;
};

struct NumaNodeInfo {
    BYTE node;
    std::vector<CpuInfo> cpus;
    std::size_t memory_bytes;
};
```

La tabla debe obtenerse con:

- `GetLogicalProcessorInformationEx`.
- `GetNumaHighestNodeNumber`.
- `GetNumaNodeProcessorMaskEx`.
- `GetActiveProcessorGroupCount`.
- `GetActiveProcessorCount`.
- `GetNumaProcessorNodeEx`.

En Windows, `GetNumaNodeProcessorMaskEx` recupera la máscara de un nodo independientemente del processor group donde se encuentre. cite[^8_2]

## 2. Afinidad estricta, no solo preferencia

`SetThreadIdealProcessorEx` expresa un procesador ideal, pero no siempre constituye una restricción dura. Para garantizar que el hilo no abandone el grupo, usar `SetThreadGroupAffinity`. Esta API restringe el hilo a los procesadores de un único processor group. cite[^8_3]

Pseudocódigo:

```cpp
void bind_thread_to_cpu(WORD group, KAFFINITY mask) {
    GROUP_AFFINITY affinity{};
    affinity.Group = group;
    affinity.Mask = mask;

    if (!SetThreadGroupAffinity(
            GetCurrentThread(),
            &affinity,
            nullptr)) {
        throw std::system_error(
            GetLastError(),
            std::system_category()
        );
    }
}
```

En una aplicación OpenMP, no es suficiente fijar el hilo master. Hay que fijar los trabajadores creados por el runtime o utilizar un runtime que respete `OMP_PLACES` y `OMP_PROC_BIND`.

Configuración inicial:

```bat
set OMP_DYNAMIC=FALSE
set OMP_PROC_BIND=spread
set OMP_PLACES=cores
```

Si el runtime soporta lugares NUMA:

```bat
set OMP_PLACES=numa_domains
set OMP_PROC_BIND=spread
```

El nombre `numa_domains` y su interpretación pueden depender del runtime; por eso debe imprimirse la topología observada por OpenMP.

## 3. Sharding por nodo

No usar un único tensor monolítico si el algoritmo tiene una partición natural. Crear un shard por nodo:

```cpp
struct NodeTensor {
    float* data = nullptr;
    std::size_t elements = 0;
    std::size_t bytes = 0;
    int node = -1;
};
```

Si el tensor global tiene `N` elementos y hay `K` nodos:

```cpp
std::size_t base = N / K;
std::size_t rem  = N % K;

for (int node = 0; node < K; ++node) {
    shards[node].elements =
        base + (node < static_cast<int>(rem));
}
```

Los límites deben alinearse, preferiblemente, a una cantidad entera de páginas:

```cpp
constexpr std::size_t page_size = 4096;
constexpr std::size_t floats_per_page =
    page_size / sizeof(float);
```

En tensores con acceso por bloques, alinear a 2 MiB puede reducir la presión de TLB, pero reduce la precisión de colocación. No activar páginas grandes sin medir el impacto sobre la distribución NUMA.

## 4. Reservar en el nodo correcto

Windows proporciona `VirtualAllocExNuma` para reservar o comprometer una región con un nodo NUMA preferido. La función permite indicar el nodo físico preferido para la memoria. cite[^8_4]

```cpp
void* allocate_on_node(
    std::size_t bytes,
    unsigned short node
) {
    void* p = VirtualAllocExNuma(
        GetCurrentProcess(),
        nullptr,
        bytes,
        MEM_RESERVE | MEM_COMMIT,
        PAGE_READWRITE,
        node
    );

    if (!p)
        throw std::bad_alloc{};

    return p;
}
```

Esto debe combinarse con first-touch. La reserva NUMA no debe considerarse una garantía absoluta si el nodo está sin memoria o si el sistema decide satisfacer la petición desde otro nodo.

Liberación:

```cpp
VirtualFree(ptr, 0, MEM_RELEASE);
```

Para `VirtualAllocExNuma`, reservar regiones grandes por shard, nunca una región por elemento.

## 5. First-touch por shard

La inicialización debe ejecutarse dentro de una región paralela y mantener la misma relación hilo/nodo que el cálculo:

```cpp
#pragma omp parallel
{
    const int tid = omp_get_thread_num();
    const int node = topology.node_of_thread(tid);

    NodeTensor& shard = shards[node];

    #pragma omp for schedule(static)
    for (std::size_t i = 0;
         i < shard.elements;
         ++i) {
        shard.data[i] = initial_value(node, i);
    }

    #pragma omp barrier

    #pragma omp for schedule(static)
    for (std::size_t block = 0;
         block < block_count(shard);
         ++block) {
        process_block(shard, block);
    }
}
```

Hay una limitación en este ejemplo: una región OpenMP no garantiza por sí sola que el conjunto de hilos asignados a un shard coincida exactamente con su nodo. La versión robusta debe ejecutar una región o subregión por partición NUMA, o usar una asignación explícita de bloques:

```cpp
#pragma omp parallel
{
    int tid = omp_get_thread_num();
    int node = worker_map[tid];

    for (std::size_t block = tid;
         block < shards[node].blocks;
         block += workers_per_node[node]) {
        initialize_block(shards[node], block);
    }
}
```

La fase de cálculo debe usar el mismo mapeo.

## 6. Evitar que el constructor toque todo

Este patrón puede destruir la estrategia:

```cpp
std::vector<float> tensor(elements, 0.0f);
```

Aunque la memoria se asigne antes, la inicialización puede ejecutarse completamente desde el hilo master.

Preferir una reserva sin inicialización seguida de first-touch paralelo:

```cpp
float* tensor = static_cast<float*>(
    _aligned_malloc(elements * sizeof(float), 64)
);

#pragma omp parallel for schedule(static)
for (std::size_t i = 0; i < elements; ++i)
    tensor[i] = 0.0f;
```

En Windows, `_aligned_malloc` no ofrece por sí mismo control NUMA. Para un control estricto por nodo, combinar `VirtualAllocExNuma` con first-touch.

## 7. La misma partición en todas las fases

No basta con inicializar estáticamente y luego procesar dinámicamente:

```cpp
#pragma omp parallel for schedule(static)
for (...) initialize(...);

#pragma omp parallel for schedule(dynamic)
for (...) process(...);
```

La segunda fase puede mover el trabajo a otros hilos y producir tráfico remoto. Preferir:

```cpp
#pragma omp parallel
{
    const int tid = omp_get_thread_num();

    #pragma omp for schedule(static)
    for (std::size_t i = 0; i < n; ++i)
        initialize(i);

    #pragma omp barrier

    #pragma omp for schedule(static)
    for (std::size_t i = 0; i < n; ++i)
        process(i);
}
```

Para cargas irregulares, usar una cola por NUMA node:

```text
queue[^8_0] → hilos del nodo 0 → shard 0
queue[^8_1] → hilos del nodo 1 → shard 1
```

El robo de trabajo entre nodos debe activarse solo cuando la cola local esté agotada y debe contabilizarse como una operación remota.

## 8. Halo exchange

Si cada shard necesita datos de sus vecinos, evitar lecturas remotas repetidas:

```text
nodo 0: interior + halo derecho
nodo 1: halo izquierdo + interior + halo derecho
nodo 2: halo izquierdo + interior
```

Flujo:

1. Procesar interior local.
2. Empaquetar fronteras en buffers contiguos.
3. Copiar los halos.
4. Esperar la finalización del intercambio.
5. Procesar la frontera local.

Ejemplo:

```cpp
#pragma omp parallel
{
    const int node = worker_node();

    process_interior(shards[node]);

    #pragma omp barrier

    if (node > 0)
        copy_left_halo(shards[node - 1], shards[node]);

    if (node + 1 < node_count)
        copy_right_halo(shards[node], shards[node + 1]);

    #pragma omp barrier

    process_boundary(shards[node]);
}
```

En producción, sustituir el ejemplo por buffers de comunicación por nodo y una sincronización mínima. La barrera global puede reemplazarse por eventos o fases por vecino si las dependencias lo permiten.

## 9. Acceso remoto: replicar o particionar

Para tablas de solo lectura usadas por todos los sockets:

```text
tabla global pequeña → replicar por nodo
```

Para tensores grandes que cada nodo procesa en su zona:

```text
tensor → particionar por shard
```

Para datos globales leídos uniformemente por todos:

```text
tensor → interleave por páginas
```

La estrategia depende de la matriz de accesos:


| Patrón | Estrategia |
| :-- | :-- |
| Propietario claro por región | First-touch + shards |
| Lectura uniforme desde todos los nodos | Interleave o replicación |
| Datos pequeños de solo lectura | Replicación |
| Dependencia vecina | Shards + halos |
| Escrituras globales | Reducción por nodo |
| Acceso completamente irregular | Reordenamiento + buckets por nodo |

Interleave puede ofrecer más ancho de banda agregado cuando todos los sockets recorren todo el tensor, pero es inferior a first-touch cuando el cálculo es local por partición.

## 10. Páginas y granularidad

First-touch opera a nivel de página, no de elemento. Si dos hilos de sockets distintos escriben dentro de la misma página, el propietario de la página no representa limpiamente a ninguno de los dos.

Solución:

```text
asignar bloques de trabajo >= una página
alinear comienzos y finales a páginas
evitar false sharing entre nodos
```

Para un `float`:

```cpp
constexpr std::size_t page_elements = 4096 / sizeof(float);
```

Para bloques más grandes:

```cpp
constexpr std::size_t block_elements =
    (2 * 1024 * 1024) / sizeof(float);
```

El tamaño de 2 MiB solo es una opción de prueba. Si se usan páginas grandes, la distribución NUMA debe medirse porque una sola página grande puede contener datos de varios consumidores.

## 11. CPU heterogénea

En sistemas con P-cores y E-cores:

- No mapear hilos solo por número lógico.
- Detectar grupos de rendimiento.
- Asignar más bloques a P-cores si el trabajo no es uniforme.
- No asumir que todos los hilos tienen la misma capacidad de memoria.
- Medir throughput por núcleo y por nodo.

Partición ponderada:

```cpp
double total_capacity = 0.0;

for (const auto& cpu : cpus)
    total_capacity += cpu.capacity;

for (auto& node : nodes) {
    node.work_fraction =
        node.capacity / total_capacity;
}
```

First-touch debe usar exactamente las mismas fracciones que el cálculo. Si el P-core procesa 2× más bloques que un E-core, el tensor debe distribuirse con ese mismo criterio.

En cargas con barreras frecuentes, suele ser preferible desactivar E-cores para la fase crítica si producen desequilibrio. En cargas independientes y de alto throughput, pueden ser beneficiosos.

## 12. Verificación de páginas

No afirmar que first-touch funcionó solo porque la inicialización fue paralela.

Verificar:

- Nodo físico de las páginas.
- Tráfico remoto.
- Bandwidth por socket.
- Page faults durante el warm-up.
- Tiempo de acceso local contra remoto.
- Distribución del working set.

`QueryWorkingSetEx` permite consultar información de las páginas residentes y comprobar el nodo NUMA de asignación; Microsoft muestra este procedimiento junto con `VirtualAllocExNuma`. cite[^8_5]

El informe debería incluir una tabla como:


| Nodo | Páginas esperadas | Páginas locales | Páginas remotas | % local |
| --: | --: | --: | --: | --: |
| 0 | 100% | ... | ... | ... |
| 1 | 100% | ... | ... | ... |

## 13. Instrumentación por hilo

Registrar temporalmente:

```cpp
struct ThreadStats {
    std::uint64_t local_blocks = 0;
    std::uint64_t remote_blocks = 0;
    std::uint64_t bytes_read = 0;
    std::uint64_t bytes_written = 0;
    int node = -1;
    int group = -1;
};
```

Cada hilo debe informar:

```text
thread_id
processor group
logical processor
NUMA node
tipo de core
bloques locales
bloques remotos
```

Esto detecta inmediatamente:

- Hilos migrados.
- Shards mal asignados.
- Desequilibrio entre nodos.
- E-cores procesando regiones destinadas a P-cores.
- Robos de trabajo excesivos.

## Solución SOTA V904 final

```text
1. Descubrir topología NUMA y processor groups.
2. Construir mapa hilo → CPU → grupo → nodo.
3. Fijar affinity antes de tocar el tensor.
4. Crear un shard alineado a páginas por nodo.
5. Reservar cada shard con VirtualAllocExNuma o allocator NUMA-aware.
6. Ejecutar first-touch paralelo desde los hilos propietarios.
7. Usar la misma partición estática durante el cálculo.
8. Mantener una región parallel persistente.
9. Sustituir accesos remotos repetidos por halos.
10. Replicar tablas pequeñas de solo lectura.
11. Interleave solo para acceso global uniforme.
12. Usar colas locales por nodo para trabajo irregular.
13. Limitar el work stealing entre sockets.
14. Repartir P-cores/E-cores según capacidad medida.
15. Verificar colocación con QueryWorkingSetEx y contadores de hardware.
16. Comparar páginas normales frente a grandes.
```

El patrón final es:

```cpp
discover_topology();

bind_openmp_workers();

for (node : numa_nodes) {
    shard[node] =
        allocate_on_node_aligned(node, shard_bytes[node]);
}

#pragma omp parallel proc_bind(spread)
{
    int node = worker_node();

    first_touch_owned_pages(
        shard[node],
        static_partition(node)
    );

    #pragma omp barrier

    process_local_interior(
        shard[node],
        static_partition(node)
    );

    exchange_halos(node);

    process_local_boundary(
        shard[node]
    );
}
```

La diferencia fundamental frente al diseño original es:

```text
No:
master inicializa tensor global
→ todos los sockets acceden remoto

Sí:
topología
→ afinidad
→ shard por nodo
→ first-touch por propietario
→ cálculo estático local
→ halo/reducción explícita
```

El resultado esperado no debe medirse solo como reducción del tráfico UPI/Infinity Fabric. El criterio correcto es **mayor ancho de banda útil por socket, menor latencia efectiva, menor porcentaje de accesos remotos y mejor escalabilidad al añadir nodos**, manteniendo el mismo resultado numérico.

# Overhead de TLS (\_\_declspec(thread) / thread_local!) con Cientos de Hilos:Busca las mejoras y solucione sota para el siguiente tema

Diagnóstico: Mantener estructuras RefCell\<CString> y pools de buffers aislados en TLS para 100+100+100+ hilos incrementa el footprint estático y retrasa la creación de hilos.
Brecha / Riesgo: Latencia acumulada en la creación y destrucción de hilos en cada iteración del bucle principal.
Solución SOTA V904: Patrón Persistent Thread Pool instanciado una sola vez en el arranque de la aplicación (top of the call-stack).

La solución SOTA es eliminar la creación y destrucción repetida de equipos de trabajo, pero también reducir el TLS estático a un **contexto por worker persistente**, no mantener grandes estructuras `thread_local` globales. El patrón recomendado es:

```text
crear workers una vez
→ inicializar contexto por worker una vez
→ reutilizar buffers y estados
→ ejecutar muchas fases
→ destruir al apagar la aplicación
```

OpenMP suele reutilizar equipos internos entre regiones, pero crear y entrar repetidamente en regiones paralelas aún implica sincronización, gestión de equipos y activación de workers. La reutilización de hilos persistentes evita gran parte de ese coste. cite[^9_1]

## Diagnóstico refinado

El problema no es que una lectura de `thread_local` sea necesariamente cara. El coste principal aparece cuando el objeto TLS contiene:

- `RefCell<CString>` o equivalentes con construcción dinámica.
- `std::vector` o pools que reservan memoria al primer uso.
- Destructores que liberan buffers al terminar el hilo.
- Muchos objetos TLS grandes.
- Inicialización dinámica por worker.
- Creación/destrucción repetida de hilos o equipos OpenMP.

En Windows, `thread_local` y `__declspec(thread)` proporcionan almacenamiento por hilo; Microsoft recomienda `thread_local` en C++ moderno. Para DLL cargadas dinámicamente, `__declspec(thread)` tiene limitaciones y Microsoft recomienda usar la API `TlsAlloc`/`TlsSetValue` si el módulo puede cargarse mediante `LoadLibrary`. cite[^9_2]

La afirmación correcta es:

```text
TLS pequeño y trivial ≠ cuello de botella importante
TLS grande con constructores, asignaciones y destructores
+ workers efímeros = alto overhead acumulado
```


## Diseño SOTA

Separar tres niveles de estado:

### Estado global

Vive durante toda la aplicación:

```cpp
struct RuntimeState {
    Config config;
    Tables immutable_tables;
    WorkerPool pool;
};
```


### Estado por worker

Vive mientras exista el worker:

```cpp
struct alignas(64) WorkerContext {
    std::uint32_t worker_id;
    std::uint32_t numa_node;

    ScratchArena scratch;
    StringBuffer strings;
    Metrics metrics;

    void reset_for_job() noexcept {
        scratch.reset();
        strings.reset();
        metrics.reset();
    }
};
```


### Estado de la tarea

No debe almacenarse en TLS:

```cpp
struct Job {
    const Input* input;
    Output* output;
    std::size_t begin;
    std::size_t end;
};
```

La tarea se pasa explícitamente al worker. Esto evita que el contexto TLS se convierta en una dependencia oculta.

## 1. Pool persistente manual

Para obtener control completo sobre afinidad, NUMA y buffers:

```cpp
class PersistentPool {
public:
    explicit PersistentPool(std::size_t count)
        : workers_(count) {}

    void start() {
        for (std::size_t i = 0; i < workers_.size(); ++i) {
            workers_[i].id = i;
            workers_[i].thread =
                std::jthread([this, i](std::stop_token stop) {
                    worker_loop(i, stop);
                });
        }
    }

    void submit(Job job) {
        {
            std::lock_guard lock(mutex_);
            jobs_.push_back(job);
        }
        condition_.notify_all();
    }

    void stop() {
        for (auto& worker : workers_)
            worker.thread.request_stop();

        condition_.notify_all();
    }

private:
    struct Worker {
        std::size_t id = 0;
        WorkerContext context;
        std::jthread thread;
    };

    void worker_loop(
        std::size_t id,
        std::stop_token stop
    ) {
        WorkerContext& ctx = workers_[id].context;

        initialize_worker_once(id, ctx);

        while (!stop.stop_requested()) {
            Job job;

            {
                std::unique_lock lock(mutex_);
                condition_.wait(lock, [&] {
                    return stop.stop_requested() ||
                           !jobs_.empty();
                });

                if (stop.stop_requested())
                    break;

                job = jobs_.back();
                jobs_.pop_back();
            }

            ctx.reset_for_job();
            process(job, ctx);
        }

        shutdown_worker(id, ctx);
    }

    std::vector<Worker> workers_;
    std::vector<Job> jobs_;
    std::mutex mutex_;
    std::condition_variable condition_;
};
```

Este ejemplo representa la arquitectura, pero una cola global con `notify_all()` no es la mejor implementación para cientos de hilos. Para V904 se debe evolucionar a:

```text
cola local por worker
+ cola por NUMA node
+ work stealing limitado
+ notificación dirigida
```


## 2. No crear un worker por iteración

Evitar:

```cpp
for (...) {
    std::vector<std::thread> threads;
    launch_workers(threads);
    execute(threads);
    join_workers(threads);
}
```

Preferir:

```cpp
Runtime runtime;
runtime.start_workers();

for (const JobBatch& batch : batches)
    runtime.execute(batch);

runtime.shutdown();
```

La destrucción se realiza una sola vez. Los pools de buffers también permanecen vivos y se reutilizan.

Microsoft documenta que un pool de threads puede configurarse con un mínimo y máximo iguales para mantener threads persistentes durante toda la vida del pool. cite[^9_3]

## 3. Usar el Thread Pool de Windows

Si no se necesita una afinidad NUMA extremadamente específica, el Thread Pool de Windows evita implementar la gestión básica de workers.

La API relevante incluye:

```text
CreateThreadpool
SetThreadpoolThreadMinimum
SetThreadpoolThreadMaximum
CreateThreadpoolWork
SubmitThreadpoolWork
WaitForThreadpoolWorkCallbacks
CloseThreadpool
```

Microsoft documenta `CreateThreadpoolWork` para crear trabajos reutilizables y `SetThreadpoolThreadMinimum/Maximum` para controlar el número de threads persistentes. cite[^9_4]

Esqueleto:

```cpp
PTP_POOL pool = CreateThreadpool(nullptr);

SetThreadpoolThreadMaximum(pool, worker_count);
SetThreadpoolThreadMinimum(pool, worker_count);

TP_CALLBACK_ENVIRON env;
InitializeThreadpoolEnvironment(&env);
SetThreadpoolCallbackPool(&env, pool);

PTP_WORK work = CreateThreadpoolWork(
    callback,
    context,
    &env
);

SubmitThreadpoolWork(work);
WaitForThreadpoolWorkCallbacks(work, FALSE);
```

Para SRI/NUMA, el pool de Windows puede ser insuficiente si no permite mapear cada worker al nodo esperado. En ese caso, preferir un pool propio o combinar el pool con una inicialización de contexto controlada.

## 4. TLS mínimo y trivial

Evitar:

```cpp
thread_local std::string tls_string;
thread_local std::vector<std::byte> tls_buffer;
thread_local RefCell<CString> tls_refcell;
```

Aunque sean cómodos, pueden ejecutar construcción dinámica y destrucción por hilo.

Preferir:

```cpp
struct WorkerIndex {
    std::uint32_t value = 0;
};

thread_local WorkerIndex tls_index;
```

Un objeto TLS pequeño, trivial y sin destructor reduce el coste. El almacenamiento grande debe vivir en el pool:

```cpp
std::vector<WorkerContext> contexts;
```

El worker obtiene su contexto mediante un índice estable:

```cpp
WorkerContext& context_for_worker(std::uint32_t id) {
    return contexts[id];
}
```

La preferencia SOTA es que el hot loop reciba `WorkerContext&` explícitamente:

```cpp
process(job, context);
```

en lugar de consultar TLS repetidamente.

## 5. Índice TLS en lugar de estructuras TLS

Si se necesita acceder desde capas profundas de la pila, guardar únicamente un identificador:

```cpp
thread_local std::uint32_t current_worker_id =
    std::numeric_limits<std::uint32_t>::max();
```

Inicialización:

```cpp
void worker_entry(std::uint32_t id) {
    current_worker_id = id;
    worker_loop(id);
}
```

Acceso:

```cpp
WorkerContext& current_context() {
    return global_runtime.context(
        current_worker_id
    );
}
```

Esto mantiene TLS pequeño. El contexto principal sigue estando en memoria controlada por `Runtime`.

Para código compilado como DLL cargada dinámicamente, usar `TlsAlloc`:

```cpp
DWORD tls_index = TlsAlloc();

void set_context(WorkerContext* ctx) {
    TlsSetValue(tls_index, ctx);
}

WorkerContext* get_context() {
    return static_cast<WorkerContext*>(
        TlsGetValue(tls_index)
    );
}
```

Microsoft describe este patrón: se reserva un índice con `TlsAlloc`, cada thread almacena su puntero con `TlsSetValue` y libera su memoria antes de terminar. cite[^9_5]

## 6. `RefCell<CString>`: reemplazar el patrón

Si el objetivo es reutilizar una cadena temporal, no guardar el objeto completo en TLS. Usar un buffer monotónico por worker:

```cpp
class StringBuffer {
public:
    explicit StringBuffer(std::size_t capacity)
        : storage_(capacity) {}

    void reset() noexcept {
        used_ = 0;
    }

    char* allocate(std::size_t bytes) {
        if (bytes > storage_.size() - used_)
            grow(bytes);

        char* result =
            reinterpret_cast<char*>(storage_.data() + used_);

        used_ += bytes;
        return result;
    }

private:
    void grow(std::size_t required) {
        const std::size_t new_size =
            std::max(storage_.size() * 2,
                     used_ + required);

        storage_.resize(new_size);
    }

    std::vector<std::byte> storage_;
    std::size_t used_ = 0;
};
```

Uso:

```cpp
void process(Job job, WorkerContext& ctx) {
    ctx.strings.reset();

    char* text = ctx.strings.allocate(256);
    format_result(text, 256, job);

    emit(text);
}
```

Esto evita:

- Construcción repetida de `CString`.
- Reservas por llamada.
- Liberaciones por thread.
- Uso compartido de un objeto mutable.
- Dependencia de un `RefCell` o wrapper de mutabilidad.

Si se requiere un resultado persistente, copiarlo a un objeto de salida propietario al finalizar la tarea.

## 7. Buffers de tamaño variable

No permitir que todos los workers hagan `resize` simultáneamente durante el hot path. Inicializar capacidades durante el arranque:

```cpp
for (auto& context : contexts) {
    context.scratch.reserve(scratch_bytes);
    context.strings.reserve(string_bytes);
}
```

Si ocasionalmente se supera la capacidad:

- Crecer solo el buffer del worker.
- Registrar un contador de overflow.
- Realizar un segundo benchmark con capacidad corregida.
- No proteger el buffer con un mutex si pertenece a un solo worker.

Una política útil:

```cpp
if (required > capacity) {
    overflow_count.fetch_add(1,
                             std::memory_order_relaxed);
    slow_path_allocate(required);
}
```

El contador permite detectar que el pool elegido es demasiado pequeño.

## 8. Persistencia de OpenMP

Para código que ya utiliza OpenMP, mantener la región paralela:

```cpp
#pragma omp parallel
{
    WorkerContext& ctx =
        contexts[omp_get_thread_num()];

    initialize_context_once(ctx);

    while (!shutdown) {
        wait_for_phase();

        ctx.reset_for_job();

        #pragma omp for schedule(static)
        for (std::int64_t i = 0; i < n; ++i)
            process(i, ctx);

        #pragma omp barrier
    }
}
```

El patrón exacto de un `while` alrededor de `omp for` exige una coordinación cuidadosa; en muchos casos es más seguro usar una región persistente con una cola de fases y barreras bien definidas, o un pool manual.

La idea importante es:

```text
una región paralela de larga vida
no muchas regiones que crean y destruyen equipos
```

OpenMP define que una región paralela crea un equipo cuyos threads permanecen constantes durante esa región; los runtimes también suelen reutilizar equipos entre regiones, pero no debe dependerse únicamente de esa optimización para diseñar el sistema. cite cite[^9_6][^9_7]

## 9. NUMA y contexto por worker

El contexto debe conocer su NUMA node:

```cpp
struct alignas(64) WorkerContext {
    std::uint32_t worker_id;
    std::uint16_t numa_node;
    std::uint16_t processor_group;

    NumaScratch scratch;
    StringBuffer strings;
    Metrics metrics;
};
```

Inicializar los buffers del worker desde el mismo hilo que los usará:

```cpp
void initialize_worker_once(
    std::uint32_t id,
    WorkerContext& ctx
) {
    bind_worker_to_topology(id);

    ctx.worker_id = id;
    ctx.numa_node = node_of_worker(id);
    ctx.scratch.initialize_on_current_node();
    ctx.strings.reserve(string_capacity);
}
```

Esto combina el patrón de threads persistentes con first-touch. Si los contextos se construyen completamente desde el master, el pool de cada worker puede terminar en la memoria NUMA equivocada.

## 10. Alineación y false sharing

No almacenar contadores de muchos workers en una estructura compacta:

```cpp
std::vector<WorkerStats> stats;
```

si cada worker modifica campos próximos. Preferir:

```cpp
struct alignas(64) WorkerStats {
    std::uint64_t jobs = 0;
    std::uint64_t bytes = 0;
    std::uint64_t overflows = 0;
};
```

Separar:

- Estado de control.
- Estadísticas modificadas.
- Buffers de datos.
- Flags de sincronización.

Un `WorkerContext` enorme también puede perjudicar la caché si todos los contextos se recorren desde el master. Alinear no significa que todos los campos deban estar en una única estructura gigante; dividir por hot/cold data puede ser mejor:

```cpp
struct alignas(64) WorkerHot {
    ScratchArena scratch;
    std::uint32_t id;
};

struct WorkerCold {
    Metrics metrics;
    Diagnostics diagnostics;
};
```


## 11. Cola global frente a colas locales

Una cola global protegida por mutex puede convertirse en el siguiente cuello de botella:

```text
TLS eliminado
→ lock de la cola global saturado
```

Para cientos de workers:

```text
NUMA node 0:
  local queue 0
  local queue 1
NUMA node 1:
  local queue 2
  local queue 3
```

Política:

1. Publicar trabajo en la cola del nodo propietario.
2. Consumir primero de la cola local.
3. Robar de otra cola del mismo nodo.
4. Robar entre nodos solo si no hay trabajo local.
5. Contabilizar el robo remoto.

El scheduler debe respetar la afinidad de datos. Un pool persistente mal diseñado puede mantener vivos los threads pero provocar más acceso remoto que un pool efímero.

## 12. Ciclo de vida correcto

Orden de apagado:

```text
1. Detener la producción de tareas.
2. Esperar a que terminen los jobs.
3. Señalizar shutdown.
4. Despertar workers.
5. Ejecutar cleanup por worker.
6. Unir workers.
7. Liberar contextos.
8. Liberar índices TLS.
9. Destruir tablas globales.
```

No destruir buffers globales mientras un worker pueda ejecutar código que los use.

Para TLS dinámico, Microsoft muestra que cada hilo debe liberar la memoria asociada antes de terminar y que el índice global se libera al finalizar el proceso. cite[^9_5]

## 13. Qué evitar

```text
thread_local std::string grande
thread_local std::vector con resize implícito
thread_local objetos con destructores complejos
crear/join workers en cada iteración
parallel for corto repetido miles de veces
cola global con mutex para todos los trabajos
work stealing entre sockets sin control
inicializar buffers por worker desde el master
guardar punteros a objetos TLS después de que termina el hilo
```

Además, `thread_local` no debe utilizarse para comunicar resultados entre tareas. El worker puede ejecutar múltiples trabajos durante su vida; el estado debe reiniciarse explícitamente al comenzar cada job.

## Implementación final recomendada

```cpp
class Runtime {
public:
    void start(std::size_t workers) {
        contexts_.resize(workers);

        for (std::size_t i = 0; i < workers; ++i) {
            threads_.emplace_back(
                [this, i](std::stop_token token) {
                    bind_worker(i);
                    initialize_context(i);

                    worker_loop(i, token);

                    destroy_context(i);
                }
            );
        }
    }

    void execute(const Batch& batch) {
        submit_partitioned(batch);
        wait_batch_complete();
    }

    void shutdown() {
        request_stop();
        wake_all_workers();

        for (auto& thread : threads_)
            thread.join();

        threads_.clear();
        contexts_.clear();
    }

private:
    std::vector<WorkerContext> contexts_;
    std::vector<std::jthread> threads_;
};
```

Hot path:

```cpp
void process(Job job, WorkerContext& ctx) {
    ctx.scratch.reset();
    ctx.strings.reset();

    for (std::size_t i = job.begin;
         i < job.end;
         ++i) {
        process_item(i, ctx.scratch, ctx.strings);
    }
}
```

La recomendación final para V904 es:

```text
1. Crear el pool persistente en el arranque.
2. Crear un WorkerContext por worker, no un objeto TLS grande.
3. Mantener TLS solo para worker_id o un puntero pequeño.
4. Inicializar buffers y pools una única vez.
5. Hacer first-touch desde el worker propietario.
6. Reutilizar el contexto entre jobs con reset barato.
7. Usar colas locales por NUMA node.
8. Mantener afinidad fija.
9. Destruir todos los workers solo al apagar la aplicación.
10. Medir startup, first-job y steady-state por separado.
```

La transformación clave es:

```text
No:
thread_local RefCell<CString> + pool nuevo
por cada ciclo y cada worker

Sí:
pool persistente
→ WorkerContext estable
→ TLS mínimo
→ buffers reutilizados
→ reset O(1)
→ destrucción única al shutdown
```

Esto reduce la latencia de creación y destrucción, evita constructores y destructores repetidos, conserva la localidad NUMA y convierte el coste del TLS en un coste amortizado de inicialización.

# Memory Leak Potencial en Allocators de Arena Lock-Free sin Reset de Época:Busca las mejoras y solucione sota para el siguiente tema

Diagnóstico: Los asignadores de arena avanzan el puntero de compensación (bump pointer) atómicamente sin realizar liberaciones individuales.
Brecha / Bug: Si una excepción o retorno anticipado omite la llamada de reseteo (arena.reset()), la memoria se fuga indefinidamente.
Solución SOTA V904: Envoltorios de tipo RAII ArenaGuard que garantizan el reseteo de la arena al salir del scope del hilo.

La solución SOTA es correcta en principio, pero debe ampliarse: `ArenaGuard` evita que una ruta de excepción o retorno olvide el `reset()`, mientras que un **protocolo de época** evita reutilizar memoria mientras todavía existan lectores. Son dos problemas distintos:

```text
ArenaGuard       → garantiza reset en el scope correcto
Epoch/RCU/HP     → garantiza que reset/reclaim sea seguro frente a otros hilos
```

Una arena monotónica libera todo de una vez; `deallocate()` individual normalmente no hace nada y el consumo crece hasta `release()` o destrucción del recurso. cite[^10_1]

## Diagnóstico preciso

Un bump allocator típico:

```cpp
offset.fetch_add(size, std::memory_order_relaxed);
```

avanza el cursor, pero no recupera objetos individuales. Si el código ejecuta:

```cpp
arena.allocate(...);
return;
arena.reset();
```

la capacidad queda ocupada hasta el siguiente reset o hasta destruir la arena.

Los fallos habituales son:

- `return` anticipado.
- Excepción.
- `break` que sale de la región esperada.
- `continue` con reset omitido.
- `longjmp` o terminación abrupta.
- Worker que abandona la tarea sin marcar quiescencia.
- Reset ejecutado por un hilo mientras otro aún usa objetos.
- Doble reset concurrente.
- Uso de punteros después de que termina la época.
- Excepción lanzada desde un destructor.
- Arena compartida entre hilos sin protocolo de propietario.

RAII vincula el ciclo de vida del recurso al alcance de un objeto automático y garantiza la liberación durante retorno normal o *stack unwinding*. Los destructores deben ser no lanzables. cite cite[^10_2][^10_3]

## 1. Arena con checkpoints

Un `reset()` global no siempre es suficiente. Una mejora más segura es guardar un checkpoint:

```cpp
class Arena {
public:
    using Marker = std::size_t;

    explicit Arena(std::size_t capacity)
        : storage_(capacity) {}

    Arena(const Arena&) = delete;
    Arena& operator=(const Arena&) = delete;

    Marker mark() const noexcept {
        return offset_;
    }

    void rewind(Marker marker) noexcept {
        if (marker <= offset_)
            offset_ = marker;
    }

    void reset() noexcept {
        offset_ = 0;
    }

    void* allocate(
        std::size_t bytes,
        std::size_t alignment = alignof(std::max_align_t)
    ) {
        const std::size_t mask = alignment - 1;
        const std::size_t begin =
            (offset_ + mask) & ~mask;

        if (begin > storage_.size() ||
            bytes > storage_.size() - begin) {
            throw std::bad_alloc{};
        }

        void* result = storage_.data() + begin;
        offset_ = begin + bytes;
        return result;
    }

private:
    std::vector<std::byte> storage_;
    std::size_t offset_ = 0;
};
```

Para un arena monotónico propiedad de un único hilo, `offset_` no necesita ser atómico. Un bump pointer atómico es más costoso y no convierte automáticamente el reset en una operación segura.

## 2. `ArenaGuard` básico

```cpp
class ArenaGuard {
public:
    explicit ArenaGuard(Arena& arena) noexcept
        : arena_(&arena),
          marker_(arena.mark()) {}

    ~ArenaGuard() noexcept {
        if (arena_)
            arena_->rewind(marker_);
    }

    ArenaGuard(const ArenaGuard&) = delete;
    ArenaGuard& operator=(const ArenaGuard&) = delete;

    ArenaGuard(ArenaGuard&& other) noexcept
        : arena_(other.arena_),
          marker_(other.marker_),
          active_(other.active_) {
        other.active_ = false;
    }

    ArenaGuard& operator=(ArenaGuard&&) = delete;

    void commit() noexcept {
        active_ = false;
    }

private:
    Arena* arena_;
    Arena::Marker marker_;
    bool active_ = true;
};
```

El destructor debe comprobar `active_`:

```cpp
~ArenaGuard() noexcept {
    if (active_ && arena_)
        arena_->rewind(marker_);
}
```

Versión completa:

```cpp
class ArenaGuard {
public:
    explicit ArenaGuard(Arena& arena) noexcept
        : arena_(&arena),
          marker_(arena.mark()) {}

    ~ArenaGuard() noexcept {
        if (active_)
            arena_->rewind(marker_);
    }

    ArenaGuard(const ArenaGuard&) = delete;
    ArenaGuard& operator=(const ArenaGuard&) = delete;

    void commit() noexcept {
        active_ = false;
    }

private:
    Arena* arena_;
    Arena::Marker marker_;
    bool active_ = true;
};
```

Uso:

```cpp
void process(Job job, Arena& arena) {
    ArenaGuard guard(arena);

    auto* temporary =
        static_cast<float*>(
            arena.allocate(job.bytes, 64)
        );

    if (!temporary_ready(job))
        return;                 // rewind automático

    if (invalid_input(job))
        throw InvalidInput{};   // rewind automático

    compute(job, temporary);

    guard.commit();             // conservar asignaciones
}
```

Para una arena temporal por tarea, normalmente no se necesita `commit()`: el guard siempre debe volver al checkpoint.

## 3. Reset completo al terminar una fase

Si el scope del guard representa toda la tarea:

```cpp
void execute_job(Job job, WorkerContext& context) {
    ArenaGuard guard(context.arena);

    process_stage_a(job, context.arena);
    process_stage_b(job, context.arena);
}
```

Incluso si `process_stage_a` lanza una excepción, el destructor del guard restaura el cursor.

Si la arena vive durante todo el worker:

```cpp
void worker_loop(WorkerContext& ctx) {
    while (auto job = next_job()) {
        ArenaGuard guard(ctx.arena);
        process(*job, ctx.arena);
    }
}
```

Esto ofrece dos garantías:

```text
cada tarea libera sus temporales
el worker conserva su buffer físico
```

La segunda propiedad evita devolver memoria al sistema en cada job.

## 4. Constructor de guard y fallo de asignación

El guard debe construirse antes de la primera asignación:

```cpp
ArenaGuard guard(arena);
auto* p = arena.allocate(bytes);
```

No hacer:

```cpp
auto* p = arena.allocate(bytes);
ArenaGuard guard(arena);
```

porque si `allocate()` falla o se lanza una excepción antes de crear el guard, esa asignación no queda protegida.

## 5. `std::pmr::monotonic_buffer_resource`

Cuando el comportamiento requerido coincide con una arena estándar, `std::pmr::monotonic_buffer_resource` ofrece `release()` y libera todos los bloques en su destructor. La biblioteca especifica que el recurso solo crece hasta `release()` o destrucción. cite cite[^10_4][^10_1]

```cpp
std::array<std::byte, 64 * 1024> initial;

std::pmr::monotonic_buffer_resource resource(
    initial.data(),
    initial.size()
);

std::pmr::vector<int> values(&resource);

{
    // uso temporal
}

resource.release();
```

Guard:

```cpp
class PmrReleaseGuard {
public:
    explicit PmrReleaseGuard(
        std::pmr::monotonic_buffer_resource& resource
    ) noexcept
        : resource_(resource) {}

    ~PmrReleaseGuard() noexcept {
        resource_.release();
    }

private:
    std::pmr::monotonic_buffer_resource& resource_;
};
```

Uso:

```cpp
void process(ArenaContext& ctx) {
    PmrReleaseGuard guard(ctx.resource);

    std::pmr::vector<float> values(&ctx.resource);
    build(values);
}
```

Limitación importante: `release()` no debe ejecutarse mientras existan objetos vivos que todavía usen memoria del recurso. La propia `pmr::memory_resource` no gestiona automáticamente la sincronización entre lectores.

## 6. Guard con generación

Para detectar uso de punteros después del reset:

```cpp
class GenerationalArena {
public:
    struct Allocation {
        void* ptr;
        std::uint64_t generation;
    };

    void reset() noexcept {
        offset_ = 0;
        ++generation_;
    }

    std::uint64_t generation() const noexcept {
        return generation_;
    }

private:
    std::size_t offset_ = 0;
    std::uint64_t generation_ = 0;
};
```

Un objeto temporal puede guardar:

```cpp
struct ArenaReference {
    void* ptr;
    std::uint64_t generation;
};
```

En modo debug:

```cpp
assert(ref.generation == arena.generation());
```

Esto no reemplaza la sincronización, pero detecta muchos *use-after-reset*. En producción, la comprobación puede desactivarse o sustituirse por un contador de estadísticas.

## 7. Guard con estado de fallo

Si el objetivo es recuperar siempre memoria, el guard no debe depender de que el usuario llame explícitamente a `commit()`:

```cpp
class ScopeReset {
public:
    explicit ScopeReset(Arena& arena) noexcept
        : arena_(arena) {}

    ~ScopeReset() noexcept {
        arena_.reset();
    }

private:
    Arena& arena_;
};
```

Uso:

```cpp
void process(Arena& arena) {
    ScopeReset reset(arena);

    allocate_temporaries(arena);

    if (error_condition())
        return;

    compute(arena);
}
```

Esta variante es preferible cuando la arena pertenece exclusivamente a la tarea y no hay necesidad de conservar allocations anteriores.

## 8. El problema de la concurrencia

Un `ArenaGuard` no soluciona este código:

```cpp
Arena shared;

#pragma omp parallel
{
    ArenaGuard guard(shared);
    void* p = shared.allocate(bytes);
    use(p);
}
```

Problemas:

- Los guards toman checkpoints simultáneos.
- El cursor requiere sincronización.
- Un hilo puede hacer rewind mientras otro todavía usa memoria.
- El orden de destrucción no representa la dependencia entre tareas.
- El reset puede invalidar punteros vivos.

La arquitectura correcta es:

```cpp
thread 0 → arena 0
thread 1 → arena 1
thread 2 → arena 2
```

```cpp
std::vector<WorkerContext> contexts;

#pragma omp parallel
{
    WorkerContext& ctx =
        contexts[omp_get_thread_num()];

    ArenaGuard guard(ctx.arena);
    process(ctx.arena);
}
```

Cada arena tiene un propietario claro. Si se necesita una arena compartida, debe existir una época común o un protocolo de reclamación.

## 9. Arena lock-free con reserva atómica

Un bump allocator concurrente puede reservar bloques mediante CAS:

```cpp
class AtomicBumpArena {
public:
    AtomicBumpArena(std::byte* base, std::size_t capacity)
        : base_(base), capacity_(capacity) {}

    void* allocate(std::size_t bytes,
                   std::size_t alignment = 64) {
        std::size_t current =
            offset_.load(std::memory_order_relaxed);

        for (;;) {
            std::size_t aligned =
                (current + alignment - 1) &
                ~(alignment - 1);

            if (aligned > capacity_ ||
                bytes > capacity_ - aligned) {
                throw std::bad_alloc{};
            }

            std::size_t next = aligned + bytes;

            if (offset_.compare_exchange_weak(
                    current,
                    next,
                    std::memory_order_relaxed,
                    std::memory_order_relaxed)) {
                return base_ + aligned;
            }
        }
    }

private:
    std::byte* base_;
    std::size_t capacity_;
    std::atomic<std::size_t> offset_{0};
};
```

Pero el reset de esta arena necesita una condición adicional:

```text
no debe haber lectores que conserven punteros de la época anterior
```

No hacer:

```cpp
arena.reset();  // peligroso
```

mientras otros hilos puedan estar dentro de:

```cpp
use(arena_object);
```


## 10. Epoch-based reclamation

Para arenas compartidas, introducir épocas:

```cpp
struct EpochState {
    std::atomic<std::uint64_t> global_epoch{0};
    std::vector<std::atomic<std::uint64_t>> announced;
};
```

Cada worker entra en una época:

```cpp
class EpochGuard {
public:
    EpochGuard(EpochState& state,
               std::size_t worker)
        : state_(state),
          worker_(worker) {
        const auto epoch =
            state_.global_epoch.load(
                std::memory_order_acquire
            );

        state_.announced[worker_].store(
            epoch,
            std::memory_order_release
        );
    }

    ~EpochGuard() noexcept {
        state_.announced[worker_].store(
            inactive,
            std::memory_order_release
        );
    }

    static constexpr std::uint64_t inactive =
        std::numeric_limits<std::uint64_t>::max();

private:
    EpochState& state_;
    std::size_t worker_;
};
```

Uso:

```cpp
{
    EpochGuard epoch(state, worker_id);
    ArenaGuard arena_scope(arena);

    read_shared_objects();
    create_temporaries();
}
```

El reclaimer solo puede reciclar la época anterior cuando ningún worker anuncie que todavía está dentro de ella.

Una regla práctica:

```text
ArenaGuard → delimita uso y reset local
EpochGuard → impide reclamación prematura global
```

Epoch-based reclamation suele tener menor coste por acceso que hazard pointers cuando las secciones críticas son cortas y los threads alcanzan puntos quiescentes regularmente. Pero una época puede quedar retenida indefinidamente si un thread se bloquea o nunca anuncia salida. cite[^10_5]

## 11. Quiescent-state reclamation

Si los workers son persistentes, una solución eficiente es declarar explícitamente puntos quiescentes:

```cpp
for (;;) {
    wait_for_job();

    enter_epoch();

    process_job();

    leave_epoch();
    quiescent_state();
}
```

El reclaimer espera a que todos los workers hayan pasado por un punto quiescente antes de reciclar la arena. Esta opción es especialmente apropiada para:

- Thread pools persistentes.
- Fases discretas.
- Barreras globales.
- Jobs de duración acotada.

No es segura si un worker puede conservar un puntero de la arena mientras espera en la cola.

## 12. Hazard pointers para referencias individuales

Si los objetos escapan del scope de una tarea y se leen desde una estructura lock-free, usar hazard pointers o un esquema equivalente. El protocolo es:

1. Leer el puntero.
2. Publicarlo en un hazard slot.
3. Volver a leer y validar.
4. Usar el objeto.
5. Limpiar el hazard slot.
6. Reclamarlo solo cuando ningún hazard lo proteja.

Un hazard pointer impide reclamar un objeto mientras algún lector lo anuncia; esta técnica está propuesta para C++ y se usa para reclamación diferida en estructuras lock-free. cite[^10_6]

No usar `ArenaGuard` como sustituto de hazard pointers si un objeto puede sobrevivir al scope del guard.

## 13. Reclamación por lotes y límites

Incluso con epochs, hay que impedir crecimiento ilimitado si un worker queda bloqueado.

Configurar:

```text
arena_capacity
max_retired_bytes
max_epochs_retained
max_job_duration
```

Política:

```cpp
if (retired_bytes > limit) {
    attempt_reclaim();
}

if (retired_bytes > hard_limit) {
    fallback_to_blocking_reclaim();
}
```

En una aplicación de baja latencia, el fallback puede:

- Bloquear nuevas asignaciones.
- Crear una arena de emergencia.
- Cancelar la tarea que retiene la época.
- Registrar el worker causante.
- Activar backpressure.

No permitir crecimiento silencioso indefinido.

## 14. Evitar `reset()` si hay objetos con destructores

Una arena solo gestiona almacenamiento bruto. Si se construyen objetos C++ no triviales con placement new:

```cpp
T* object = std::construct_at(
    static_cast<T*>(arena.allocate(sizeof(T), alignof(T)))
);
```

`arena.reset()` no llama automáticamente a `T::~T()`.

Usar un destructor registry:

```cpp
class DestructionStack {
public:
    template<class T>
    void add(T* object) {
        entries_.push_back({
            object,
            [](void* p) noexcept {
                std::destroy_at(
                    static_cast<T*>(p)
                );
            }
        });
    }

    void destroy_all() noexcept {
        for (auto it = entries_.rbegin();
             it != entries_.rend();
             ++it) {
            it->destroy(it->object);
        }

        entries_.clear();
    }

private:
    struct Entry {
        void* object;
        void (*destroy)(void*) noexcept;
    };

    std::vector<Entry> entries_;
};
```

El guard debe destruir objetos antes de hacer rewind:

```cpp
class ObjectArenaGuard {
public:
    explicit ObjectArenaGuard(Context& ctx) noexcept
        : ctx_(ctx),
          marker_(ctx.arena.mark()) {}

    ~ObjectArenaGuard() noexcept {
        ctx_.destructions.destroy_all();
        ctx_.arena.rewind(marker_);
    }

private:
    Context& ctx_;
    Arena::Marker marker_;
};
```

Los destructores deben ser `noexcept`. Microsoft recomienda que ninguna excepción escape de un destructor, especialmente durante el *stack unwinding*. cite[^10_3]

## 15. Excepciones y workers

En un thread worker, una excepción no capturada puede terminar el proceso. El patrón correcto es:

```cpp
void worker_loop(WorkerContext& ctx) noexcept {
    for (;;) {
        try {
            Job job = wait_job();

            ArenaGuard guard(ctx.arena);
            process(job, ctx);

        } catch (...) {
            record_exception(
                std::current_exception()
            );
        }
    }
}
```

El guard se destruye antes de que el catch registre o propague el error. Si la excepción se almacena para el hilo principal, no almacenar referencias a objetos de la arena ya reseteada.

## 16. Detección de fugas

Añadir estadísticas por arena:

```cpp
struct ArenaStats {
    std::atomic<std::size_t> bytes_reserved{0};
    std::atomic<std::size_t> bytes_rewound{0};
    std::atomic<std::size_t> high_watermark{0};
    std::atomic<std::size_t> active_guards{0};
    std::atomic<std::size_t> generation{0};
};
```

Cada guard:

```cpp
class InstrumentedArenaGuard {
public:
    explicit InstrumentedArenaGuard(
        InstrumentedArena& arena
    ) noexcept
        : arena_(arena),
          marker_(arena.mark()) {
        arena_.stats().active_guards.fetch_add(
            1,
            std::memory_order_relaxed
        );
    }

    ~InstrumentedArenaGuard() noexcept {
        arena_.rewind(marker_);

        arena_.stats().active_guards.fetch_sub(
            1,
            std::memory_order_relaxed
        );
    }

private:
    InstrumentedArena& arena_;
    std::size_t marker_;
};
```

Alertas:

```text
high_watermark crece cada época
active_guards no vuelve a cero
retired_bytes supera el límite
una época permanece anunciada demasiado tiempo
arena nunca alcanza un checkpoint anterior
```

Probar con:

- Excepciones aleatorias.
- Retornos anticipados.
- Cancelación de tareas.
- `break` y `continue`.
- Worker detenido durante una época.
- Presión máxima de memoria.
- Interrupción después de la reserva y antes del uso.
- Sanitizers y Application Verifier donde sea compatible.


## Solución SOTA V904

```text
1. Arena por worker para temporales locales.
2. ArenaGuard construido antes de la primera asignación.
3. Checkpoint/rewind en lugar de reset ciego cuando hay scopes anidados.
4. Destructor noexcept.
5. Destrucción explícita de objetos no triviales antes del rewind.
6. Generation counter en builds de diagnóstico.
7. EpochGuard para arenas compartidas entre workers.
8. Quiescent points en pools persistentes.
9. Hazard pointers si referencias individuales escapan del scope.
10. Límite de memoria retenida y backpressure.
11. Estadísticas por arena y época.
12. Reclamación por lotes, no liberación individual.
```


### Patrón final

```cpp
void worker_job(WorkerContext& ctx, Job job) noexcept {
    try {
        EpochGuard epoch(
            ctx.epoch_state,
            ctx.worker_id
        );

        ObjectArenaGuard arena_scope(ctx);

        process(job, ctx);

    } catch (...) {
        ctx.errors.record(
            std::current_exception()
        );
    }
}
```

Si la arena es exclusivamente local al worker:

```cpp
void worker_job(WorkerContext& ctx, Job job) noexcept {
    try {
        ArenaGuard guard(ctx.arena);
        process(job, ctx);
    } catch (...) {
        ctx.errors.record(
            std::current_exception()
        );
    }
}
```

La primera versión protege frente a reclamación compartida; la segunda basta para una arena estrictamente privada.

La transformación clave es:

```text
No:
bump pointer
→ return temprano
→ reset manual olvidado
→ crecimiento indefinido

Sí:
checkpoint
→ ArenaGuard
→ destrucción de objetos
→ rewind automático
→ EpochGuard si existe acceso compartido
→ límite y métricas de retención
```

`ArenaGuard` es la solución SOTA para la seguridad de scope y excepciones. Pero si la arena es compartida, debe combinarse con una época, estado quiescente o hazard pointers; de lo contrario, se puede eliminar la fuga y crear un *use-after-free* al resetear demasiado pronto.

# Profundiza en mejoras y solucione sota

La mejora SOTA debe separar **rollback local**, **reclamación global** y **control de crecimiento**. `ArenaGuard` resuelve el olvido de `reset()` en retornos y excepciones, pero no resuelve por sí solo la reclamación concurrente ni una época retenida por un worker bloqueado.

## Diseño correcto

```text
ArenaGuard
    └── rollback del scope actual

EpochGuard
    └── impide reclaim mientras existan lectores

Reclaimer
    └── libera/reutiliza épocas antiguas

Memory budget
    └── evita crecimiento ilimitado ante workers bloqueados
```

Una `monotonic_buffer_resource` libera memoria al hacer `release()` o destruirse; las liberaciones individuales no reducen necesariamente el consumo del recurso. `release()` devuelve los bloques al recurso upstream y reinicia el buffer actual. cite[^11_1]

## 1. Cambiar `reset()` por checkpoint

Un `reset()` total es demasiado agresivo para scopes anidados. Usar checkpoints:

```cpp
class Arena {
public:
    using Marker = std::size_t;

    explicit Arena(std::size_t capacity)
        : storage_(capacity) {}

    Marker checkpoint() const noexcept {
        return offset_;
    }

    void rewind(Marker marker) noexcept {
        assert(marker <= offset_);
        offset_ = marker;
    }

    void reset() noexcept {
        offset_ = 0;
    }

    void* allocate(
        std::size_t size,
        std::size_t alignment = alignof(std::max_align_t)
    ) {
        const auto mask = alignment - 1;
        const auto begin =
            (offset_ + mask) & ~mask;

        if (begin > storage_.size() ||
            size > storage_.size() - begin) {
            throw std::bad_alloc{};
        }

        void* ptr = storage_.data() + begin;
        offset_ = begin + size;
        return ptr;
    }

private:
    std::vector<std::byte> storage_;
    std::size_t offset_ = 0;
};
```

Esto permite:

```cpp
ArenaGuard outer(arena);

allocate_outer(arena);

{
    ArenaGuard inner(arena);
    allocate_inner(arena);
} // solo se revierte inner

use_outer_objects();
```


## 2. `ArenaGuard` robusto

El guard debe ser:

- No copiable.
- Movible únicamente si la semántica está clara.
- `noexcept`.
- Construido antes de la primera asignación.
- Capaz de hacer `commit()` solo cuando la memoria deba sobrevivir.

```cpp
class [[nodiscard]] ArenaGuard {
public:
    explicit ArenaGuard(Arena& arena) noexcept
        : arena_(&arena),
          marker_(arena.checkpoint()) {}

    ~ArenaGuard() noexcept {
        if (active_)
            arena_->rewind(marker_);
    }

    ArenaGuard(const ArenaGuard&) = delete;
    ArenaGuard& operator=(const ArenaGuard&) = delete;

    ArenaGuard(ArenaGuard&& other) noexcept
        : arena_(other.arena_),
          marker_(other.marker_),
          active_(other.active_) {
        other.active_ = false;
    }

    ArenaGuard& operator=(ArenaGuard&&) = delete;

    void commit() noexcept {
        active_ = false;
    }

private:
    Arena* arena_;
    Arena::Marker marker_;
    bool active_;
};
```

El destructor no debe lanzar excepciones. La seguridad de excepciones depende de que los destructores sean no lanzables; Microsoft recomienda que los recursos queden ligados a objetos RAII y que ninguna excepción escape de un destructor. cite[^11_2]

## 3. Guard automático para tareas

En un worker persistente:

```cpp
void execute_job(Job job, WorkerContext& ctx) noexcept {
    try {
        ArenaGuard guard(ctx.arena);

        process_stage_a(job, ctx.arena);
        process_stage_b(job, ctx.arena);

    } catch (...) {
        ctx.errors.record(std::current_exception());
    }
}
```

Los siguientes caminos quedan protegidos:

```cpp
if (invalid_input(job))
    return;

if (cancelled(job))
    return;

throw ProcessingError{};

goto error_path;
```

Todos destruyen `guard` durante la salida del scope.

## 4. Preferir un guard estándar cuando sea suficiente

Si el proyecto usa una implementación de `scope_exit`, puede expresar el rollback directamente:

```cpp
auto marker = arena.checkpoint();

auto rollback = make_scope_exit(
    [&arena, marker]() noexcept {
        arena.rewind(marker);
    }
);
```

La familia `scope_exit` está diseñada para ejecutar una acción al salir del scope, tanto por retorno normal como por excepción, y puede desactivarse mediante `release()`. cite[^11_3]

Para una base portable en C++20/21 puede usarse Boost.Scope; para C++23, comprobar la disponibilidad real de `std::scope_exit` en el compilador y biblioteca utilizados. No asumir que todas las toolchains Windows/MinGW ofrecen la misma parte de la biblioteca estándar.

## 5. Destruir objetos antes de hacer rewind

El almacenamiento de arena no conoce la vida de objetos no triviales:

```cpp
auto* object = std::construct_at(
    static_cast<MyObject*>(
        arena.allocate(sizeof(MyObject), alignof(MyObject))
    )
);
```

`rewind()` no ejecuta `MyObject::~MyObject()`. Usar un registro de destructores:

```cpp
class DestructorStack {
public:
    template<class T>
    void add(T* ptr) {
        entries_.push_back({
            ptr,
            [](void* p) noexcept {
                std::destroy_at(static_cast<T*>(p));
            }
        });
    }

    void destroy_to(std::size_t marker) noexcept {
        while (entries_.size() > marker) {
            Entry entry = entries_.back();
            entries_.pop_back();
            entry.destroy(entry.object);
        }
    }

    std::size_t checkpoint() const noexcept {
        return entries_.size();
    }

private:
    struct Entry {
        void* object;
        void (*destroy)(void*) noexcept;
    };

    std::vector<Entry> entries_;
};
```

Guard combinado:

```cpp
class ObjectArenaGuard {
public:
    explicit ObjectArenaGuard(Context& ctx) noexcept
        : ctx_(ctx),
          arena_marker_(ctx.arena.checkpoint()),
          destructor_marker_(
              ctx.destructors.checkpoint()
          ) {}

    ~ObjectArenaGuard() noexcept {
        ctx_.destructors.destroy_to(
            destructor_marker_
        );
        ctx_.arena.rewind(arena_marker_);
    }

private:
    Context& ctx_;
    Arena::Marker arena_marker_;
    std::size_t destructor_marker_;
};
```

El orden es obligatorio:

```text
1. destruir objetos
2. invalidar sus storage
3. hacer rewind
```


## 6. Arena por worker como primera opción

Si la arena es privada de un worker, no necesita un bump pointer atómico:

```cpp
struct alignas(64) WorkerContext {
    Arena arena;
    DestructorStack destructors;
};
```

Uso:

```cpp
#pragma omp parallel
{
    WorkerContext& ctx =
        contexts[omp_get_thread_num()];

    ArenaGuard guard(ctx.arena);
    process(ctx);
}
```

Ventajas:

- Sin CAS en cada asignación.
- Sin epoch global.
- Reset local y determinista.
- Buena localidad NUMA.
- Fácil análisis de ownership.
- Menor coste que una arena compartida lock-free.

Un allocator lock-free compartido solo debe elegirse si compartir la arena aporta una ventaja real. Muchas veces se elimina un mutex y se introduce un coste de CAS, invalidación de caché y reclamación global.

## 7. Si la arena es compartida: `EpochGuard`

Cuando un objeto de la arena puede ser leído por otro worker, `ArenaGuard` no garantiza seguridad. Se necesita una época de lectura:

```cpp
class EpochManager {
public:
    static constexpr std::uint64_t inactive =
        std::numeric_limits<std::uint64_t>::max();

    void enter(std::size_t worker) noexcept {
        const auto epoch =
            global_.load(std::memory_order_acquire);

        announced_[worker].store(
            epoch,
            std::memory_order_release
        );
    }

    void leave(std::size_t worker) noexcept {
        announced_[worker].store(
            inactive,
            std::memory_order_release
        );
    }

    bool can_reclaim(
        std::uint64_t retired_epoch
    ) const noexcept {
        for (const auto& epoch : announced_) {
            const auto active =
                epoch.load(std::memory_order_acquire);

            if (active != inactive &&
                active <= retired_epoch) {
                return false;
            }
        }

        return true;
    }

private:
    std::atomic<std::uint64_t> global_{0};
    std::vector<std::atomic<std::uint64_t>> announced_;
};
```

RAII:

```cpp
class EpochGuard {
public:
    EpochGuard(EpochManager& manager,
               std::size_t worker) noexcept
        : manager_(manager),
          worker_(worker) {
        manager_.enter(worker_);
    }

    ~EpochGuard() noexcept {
        manager_.leave(worker_);
    }

    EpochGuard(const EpochGuard&) = delete;
    EpochGuard& operator=(const EpochGuard&) = delete;

private:
    EpochManager& manager_;
    std::size_t worker_;
};
```

Uso:

```cpp
void read_shared_arena(
    SharedArena& arena,
    EpochManager& epochs,
    std::size_t worker
) noexcept {
    EpochGuard epoch(epochs, worker);

    const Object* object = arena.find();
    consume(object);
}
```

El reclamador solo recicla la arena o la región cuando todos los lectores han abandonado la época correspondiente.

## 8. Evitar el error más grave: epoch fuera de orden

Incorrecto:

```cpp
ArenaGuard arena_scope(arena);
EpochGuard epoch(epochs, worker);
```

Si el `EpochGuard` se destruye primero, el hilo deja de anunciarse mientras todavía existe `arena_scope`. La memoria puede reclamarse antes de que termine el uso.

Correcto:

```cpp
EpochGuard epoch(epochs, worker);
ArenaGuard arena_scope(arena);
```

Orden de destrucción:

```text
arena_scope sale primero
epoch sale después
```

Así, el hilo deja de usar la arena antes de abandonar la época.

## 9. Reclamación por generaciones

Una arena compartida debe asociar cada bloque con una generación:

```cpp
struct RetiredArena {
    Arena* arena;
    std::uint64_t generation;
    std::size_t bytes;
};
```

Flujo:

```text
arena activa G
→ se cierra G
→ pasa a retired[G]
→ se crea G+1
→ se espera una gracia
→ se reclama G
```

No reutilizar inmediatamente el mismo bloque físico si los lectores pueden conservar punteros. Es preferible tener dos o tres arenas rotatorias:

```text
active
retired
reclaimable
```

La cantidad de generaciones retenidas debe limitarse.

## 10. El problema de una época bloqueada

Epoch-based reclamation puede retener memoria indefinidamente si un worker:

- Se bloquea dentro de una lectura.
- Entra en una época y nunca sale.
- Es suspendido.
- Muere sin publicar su estado.
- Ejecuta una operación no acotada.

La retención aproximada crece con:

$$
M_{\text{retenida}} \approx \lambda \cdot T_{\text{stall}}
$$

donde $\lambda$ es la tasa de retiro y $T_{\text{stall}}$ el tiempo que el worker bloqueado impide la reclamación. La literatura sobre EBR destaca precisamente que la reclamación depende del thread más lento y puede producir retención no acotada bajo stalls. cite[^11_4]

Mitigaciones:

- No mantener una época durante I/O.
- No mantenerla mientras se espera otra tarea.
- Dividir operaciones largas en quanta.
- Publicar quiescence en cada fase.
- Límite de tiempo por sección de lectura.
- Límite de bytes retirados.
- Fallback a hazard pointers o referencias contadas para objetos que escapan.
- Bloquear nuevas retiradas cuando se supera el presupuesto.


## 11. Quiescent state para workers persistentes

En un pool persistente:

```cpp
for (;;) {
    Job job = wait_job();

    {
        EpochGuard epoch(epochs, worker_id);
        process(job);
    }

    announce_quiescent(worker_id);
}
```

Nunca hacer:

```cpp
EpochGuard epoch(...);
wait_for_next_job(); // época retenida mientras está ocioso
```

El worker debe abandonar la época antes de volver a la cola de trabajos.

Para tareas largas:

```cpp
for (auto chunk : job.chunks) {
    {
        EpochGuard epoch(epochs, worker_id);
        process_chunk(chunk);
    }

    announce_quiescent(worker_id);
}
```

Esto reduce la ventana de reclamación y limita la memoria pendiente.

## 12. `pmr`: correcto, pero con ownership claro

```cpp
std::pmr::monotonic_buffer_resource resource(
    initial_buffer,
    initial_size,
    upstream
);

{
    std::pmr::vector<Node> nodes(&resource);
    build_graph(nodes);
}

resource.release();
```

No llamar `release()` si:

```cpp
std::pmr::vector<Node> nodes(&resource);
resource.release(); // peligroso
nodes.push_back(...);
```

El vector aún contiene punteros a su almacenamiento anterior. `release()` debe ejecutarse después de destruir los containers y objetos que usan el recurso.

Guard seguro:

```cpp
void run_phase(
    std::pmr::monotonic_buffer_resource& resource
) {
    {
        std::pmr::vector<Node> nodes(&resource);
        build_graph(nodes);
    }

    resource.release();
}
```

Si el recurso es compartido entre hilos, envolverlo con sincronización no convierte automáticamente a los objetos que aloja en seguros para acceso concurrente. Preferir un recurso por worker o por NUMA node.

## 13. Presupuesto y backpressure

Añadir límites explícitos:

```cpp
struct ArenaLimits {
    std::size_t max_active_bytes;
    std::size_t max_retired_bytes;
    std::size_t max_generations;
};
```

Antes de crear una nueva generación:

```cpp
if (retired_bytes + required > limits.max_retired_bytes) {
    reclaim_completed_generations();

    if (retired_bytes + required >
        limits.max_retired_bytes) {
        wait_for_quiescence();
    }
}
```

Políticas posibles:


| Situación | Acción |
| :-- | :-- |
| Arena local llena | Crear bloque upstream |
| Bloques retirados altos | Intentar reclaim |
| Worker reteniendo época | Dividir la tarea |
| Presupuesto excedido | Backpressure |
| Objeto escapa del scope | Migrar a allocator estable |
| Reclamación incierta | No reutilizar; conservar |
| Destrucción de worker | Forzar salida de época |

El peor error es ocultar la presión asignando indefinidamente nuevas arenas.

## 14. Instrumentación

Registrar por arena:

```cpp
struct ArenaStats {
    std::atomic<std::size_t> allocated_bytes{0};
    std::atomic<std::size_t> active_bytes{0};
    std::atomic<std::size_t> retired_bytes{0};
    std::atomic<std::size_t> high_watermark{0};
    std::atomic<std::uint64_t> generation{0};
    std::atomic<std::uint64_t> guard_count{0};
    std::atomic<std::uint64_t> overflow_count{0};
    std::atomic<std::uint64_t> stalled_epochs{0};
};
```

Alertas:

```text
active_bytes no baja al terminar jobs
retired_bytes crece monótonamente
generation avanza sin reclaim
guard_count no vuelve a cero
un worker permanece en una época demasiado tiempo
overflow_count crece
```

En builds de diagnóstico, añadir:

```cpp
struct AllocationHeader {
    std::uint64_t generation;
    std::uint32_t owner;
    std::uint32_t size;
    std::uint64_t canary;
};
```

Validar al consumir el objeto:

```cpp
assert(header->canary == expected_canary);
assert(header->generation == current_generation);
```

Esto ayuda a detectar:

- Use-after-rewind.
- Uso desde otro worker.
- Doble reclaim.
- Tamaño incorrecto.
- Corrupción del cursor.


## 15. Excepciones en destructores

El guard debe hacer rollback, destruir objetos y registrar errores sin lanzar:

```cpp
~ObjectArenaGuard() noexcept {
    try {
        destroy_objects();
    } catch (...) {
        record_destructor_failure(
            std::current_exception()
        );
    }

    arena_.rewind(marker_);
}
```

En general, es mejor que los destructores registrados sean `noexcept`. Si el destructor de un objeto puede fallar, separar la operación fallible antes de entrar al scope protegido.

La seguridad de excepciones debe cubrir también fallos parciales de construcción: los recursos adquiridos antes del fallo deben estar inmediatamente bajo ownership RAII. cite[^11_2]

## 16. Variante recomendada para V904

### Arena local por worker

```cpp
void worker_job(
    WorkerContext& ctx,
    Job job
) noexcept {
    try {
        ObjectArenaGuard arena_scope(ctx);

        process(job, ctx);

    } catch (...) {
        ctx.errors.record(
            std::current_exception()
        );
    }
}
```


### Arena compartida por época

```cpp
void shared_job(
    SharedContext& shared,
    std::size_t worker,
    Job job
) noexcept {
    try {
        EpochGuard epoch(
            shared.epochs,
            worker
        );

        ArenaGuard arena_scope(shared.active_arena);

        process_shared(job, shared);

    } catch (...) {
        shared.errors.record(
            std::current_exception()
        );
    }
}
```

La segunda variante solo es correcta si:

- `ArenaGuard` no hace un reset global mientras otros lectores siguen activos.
- La arena activa pertenece a la época anunciada.
- El reclaimer respeta las épocas.
- Las referencias no sobreviven al `EpochGuard`.


## Solución SOTA final

```text
1. Arena por worker siempre que sea posible.
2. Checkpoint/rewind, no reset global indiscriminado.
3. ArenaGuard construido antes de cualquier allocate.
4. Destructor noexcept.
5. Registro de destructores para objetos no triviales.
6. EpochGuard alrededor de cada acceso a arena compartida.
7. Orden: EpochGuard exterior, ArenaGuard interior.
8. Reclaim solo tras una gracia completa.
9. Quiescent points frecuentes en pools persistentes.
10. Límite de bytes y generaciones retenidas.
11. Backpressure si un worker bloquea la reclamación.
12. Generation counters y canarios en builds de diagnóstico.
13. `pmr::release()` solo después de destruir todos sus containers.
14. Hazard pointers o ownership estable para referencias que escapan.
15. Métricas de active, retired, high-watermark y stalled epochs.
```

El flujo correcto es:

```text
allocate
  ↓
ArenaGuard
  ↓
uso temporal
  ↓
destruir objetos no triviales
  ↓
rewind automático
  ↓
salir de epoch
  ↓
reclaim cuando todos estén quiescentes
```

La mejora decisiva no es simplemente envolver `arena.reset()` en un destructor. Es convertir la arena en un recurso con **ownership, generación, rollback, reclamación segura y presupuesto explícitos**. `ArenaGuard` elimina las fugas por control de flujo; el protocolo de época elimina los `use-after-free`; y el límite de retención evita que un worker bloqueado transforme una reclamación lock-free en una fuga aparentemente infinita.
