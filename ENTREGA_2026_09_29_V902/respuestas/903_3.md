# 4. Dossier Consolidado de Cuellos de Botella, Bugs y Brechas para V903

Basado en la síntesis de 903_2.md y los benchmarks empíricos, los bloqueos que definen la hoja de ruta de V903 son:
A. Abismo Cuadrático de K-NN (O(N2log⁡N)O(N2logN)) busca las mejoras y solucione sota
Cuello de Botella: Para N>10,000N>10,000, la búsqueda de vecinos para la dimensión Two-NN escala como O(N2log⁡N)O(N2logN). En D>20D>20, los kd-trees degeneran a fuerza bruta debido a la maldición de la dimensionalidad.
Mandato V903: Reemplazar el ordenamiento por fuerza bruta con HNSW (Hierarchical Navigable Small World, O(Nlog⁡N)O(NlogN) query time) o FAISS IVF-PQ para N>105N>105.

El cuello de botella cuadrático en la búsqueda Two-NN para $N > 10{,}000$ y $D > 20$ es una manifestación clásica de la “maldición de la dimensionalidad”: los kd-trees degeneran a fuerza bruta y el coste de construir y consultar vecinos escala como $O(N^2 \log N)$ en la práctica. La solución de estado del arte (SOTA) para V903 es reemplazar el ordenamiento exacto por índices de búsqueda aproximada (ANN) como HNSW o FAISS IVF-PQ, que ofrecen tiempos de consulta cercanos a $O(\log N)$ con recall > 95% y escalan a $N > 10^5$–$10^9$.[^1_1][^1_2][^1_3][^1_4][^1_5][^1_6]

## Por qué los kd-trees fallan en $D > 20$

- **Degeneración exponencial**: En dimensiones bajas ($D < 20$), un kd-tree logra $O(D \log N)$ por consulta, pero al crecer $D$ el número de celdas a explorar escala como $\max(2^D, N)$, volviéndose más lento que un barrido lineal.[^1_2][^1_3][^1_1]
- **Concentración de medidas**: A partir de $D \approx 20$, las distancias entre puntos tienden a concentrarse, haciendo que la poda del árbol sea inefectiva y que la búsqueda exacta pierda significado práctico.[^1_7][^1_8]
- **Impacto en Two-NN**: La estimación de dimensión intrínseca vía Two-NN requiere los dos vecinos más cercanos para cada punto; con $N$ grande, hacer esto de forma exacta implica $N$ consultas costosas, llevando a un comportamiento cercano a $O(N^2 \log N)$ en la práctica.[^1_1][^1_2]


## Mandato V903: migrar a ANN (HNSW / FAISS IVF-PQ)

### Opción A: HNSW (Hierarchical Navigable Small World)

- **Complejidad**: Construcción $O(N \log N)$, consulta $O(\log N)$ en promedio.[^1_5]
- **Precisión**: Recall 95–99% con configuración típica (efConstruction ≈ 200, efSearch ≈ 50–100).[^1_5]
- **Memoria**: Alto consumo (~4 KB/vector en RAM), ideal para ≤ 50M vectores.[^1_6]
- **Ventajas**: Consultas sub-10 ms, inserciones dinámicas, excelente para producción RAG y búsqueda semántica.[^1_6][^1_5]
- **Recomendación V903**: Usar HNSW si $N \le 5 \times 10^7$ y hay RAM suficiente; es el “local optimum” bajo 50M vectores.[^1_6]


### Opción B: FAISS IVF-PQ (Inverted File + Product Quantization)

- **Complejidad**: Consulta $O(N / \text{nlist})$ tras particionar en `nlist` celdas; con PQ, cada vector se comprime a códigos cortos.[^1_9][^1_5]
- **Precisión**: Recall 88–96% (ajustable con `nprobe`, número de celdas exploradas).[^1_5]
- **Memoria**: Muy bajo (PQ reduce a ~8–16 bytes/vector), apto para billones de vectores.[^1_9][^1_6]
- **Ventajas**: Escala a $N > 10^8$ con RAM limitada; ideal cuando HNSW no cabe en memoria.[^1_4][^1_6]
- **Recomendación V903**: Usar IVF-PQ si $N > 10^8$ o la RAM es restrictiva; combinar con `nprobe` alto para recuperar recall en Two-NN.[^1_4][^1_5]


## Hoja de ruta técnica para V903

1. **Diagnóstico**: Medir tiempos actuales de Two-NN para $N = 10^4, 10^5, 10^6$ y $D = 10, 20, 50$; confirmar la degeneración a fuerza bruta.[^1_2][^1_1]
2. **Prototipo HNSW**: Implementar con `hnswlib` o `faiss.IndexHNSWFlat`; ajustar `efConstruction` y `efSearch` para maximizar recall en la estimación de dimensión intrínseca.[^1_4][^1_5]
3. **Prototipo IVF-PQ**: Si $N > 10^8$, entrenar un `IndexIVFPQ` con `nlist ≈ 4 \sqrt{N}\)` y PQ de 8–16 bytes; evaluar `nprobe` para equilibrio velocidad/precisión.[^1_9][^1_5]
4. **Validación Two-NN**: Comparar la distribución de ratios Two-NN (exacto vs ANN) para asegurar que la estimación de dimensión intrínseca no se sesga significativamente.[^1_7]
5. **Despliegue**: Reemplazar el módulo de fuerza bruta por el índice ANN seleccionado; documentar umbrales de $N$ y $D$ para cambiar entre HNSW e IVF-PQ.[^1_4][^1_6]

## Referencias clave

- Scikit-learn: kd-tree degenera para $D > 20$, volviéndose más lento que fuerza bruta.[^1_1][^1_2]
- FAISS guidelines: HNSW es óptimo bajo 50M vectores; IVF-PQ para escalas masivas.[^1_6][^1_4]

## Configuración SOTA para HNSW (recomendado para $N \le 5 \times 10^7$)

### Hiperparámetros críticos

| Parámetro | Rol | Valor recomendado V903 | Efecto en recall/latencia |
| :-- | :-- | :-- | :-- |

- **efSearch=64**: recall@10 ≈ 95%, latencia p95 ≈ 2.5 ms[^2_5]
- **efSearch=128**: recall@10 ≈ 97.5%, latencia p95 ≈ 3.8 ms[^2_5]
- **efSearch=256**: recall@10 ≈ 98.8%, latencia p95 ≈ 6.2 ms[^2_5]

**Recomendación V903**: Usar **M=32, efConstruction=256, efSearch=128** como punto de partida; ajustar efSearch a 200–256 si el sesgo en Two-NN supera el 2%.[^2_2][^2_5]

## Configuración SOTA para FAISS IVF-PQ (recomendado para $N > 10^8$)

### Hiperparámetros críticos

| Parámetro | Rol | Valor recomendado V903 | Efecto en recall/latencia |
| :-- | :-- | :-- | :-- |

- **IVF-PQ (nlist=8192, nprobe=100, m=64)**: recall@10 ≈ 94–95%, latencia ≈ 15–20 ms[^2_3]

**Recomendación V903**: Usar **nlist=8192, nprobe=80–100, PQ m=64** para equilibrar recall y latencia en escalas masivas.[^2_3]

## Validación del sesgo en Two-NN

El riesgo principal es que la aproximación ANN introduzca un **sesgo sistemático** en la estimación de dimensión intrínseca vía Two-NN. Para mitigarlo:[^2_10]

1. **Muestreo de validación**: Seleccionar 10,000 puntos al azar y calcular Two-NN exacto (fuerza bruta) vs ANN; comparar la distribución de ratios $r = d_2 / d_1$.[^2_10]
2. **Métrica de error**: Calcular el error relativo medio en la dimensión estimada: $\epsilon = |\hat{d}_{ANN} - \hat{d}_{exacto}| / \hat{d}_{exacto}$. [^2_10]
3. **Umbral aceptable**: Si $\epsilon < 2\%$ con efSearch=128 (HNSW) o nprobe=80 (IVF-PQ), la configuración es válida; si no, aumentar efSearch/nprobe hasta alcanzar $\epsilon < 1\%$.[^2_8][^2_10]

# B. Ineficiencia Asintótica O(DK2)O(DK2) en Retracciones Stiefel (Álgebra de Clifford Cℓ(D)Cℓ(D)) busca las mejoras y solucione sota

Cuello de Botella: La matriz de covarianza densa XTXXTX para D=106D=106 y K=128K=128 requiere transferir ≈500 MB≈500 MB por iteración (≈1000 GB/s≈1000 GB/s de ancho de banda requerido), sobrepasando el techo físico de DDR3/DDR4 (25–50 GB/s).
Mandato V903:
Abandonar representaciones matriciales densas D×KD×K y adoptar bi-vectores antisimétricos empaquetados de tamaño K(K−1)/2K(K−1)/2.
Implementar Sparse Rolling Interaction (estrategia CliffordNet 2026, S=5S=5 shifts) para reducir la complejidad a O(D)O(D) lineal.
Desplegar kernels SIMD con AVX-512 (16-wide float32, \_mm512_fnmadd_ps) logrando speedups esperados de 12×12× a 15×15×.

La solución SOTA para el cuello de botella $O(D K^2)$ en retracciones Stiefel con $D = 10^6$ y $K = 128$ es adoptar la arquitectura **CliffordNet 2026**, que reemplaza la matriz de covarianza densa $X^T X$ por **bi-vectores antisimétricos empaquetados** y aplica **Sparse Rolling Interaction** con $S = 5$ shifts, reduciendo la complejidad a $O(D)$ lineal. Combinado con kernels SIMD AVX-512 (\_mm512_fnmadd_ps), esto logra speedups de **12× a 15×** respecto a implementaciones densas en CPU.[^3_1][^3_2][^3_3][^3_4][^3_5]

## Por qué falla la representación densa $D \times K$

- **Transferencia de memoria insostenible**: Para $D = 10^6$, $K = 128$, la matriz $X^T X$ requiere $\approx 500$ MB por iteración; a 1000 iteraciones/segundo, el ancho de banda necesario es $\approx 1000$ GB/s, muy por encima del límite físico de DDR4 (25–50 GB/s).[^3_1]
- **Complejidad cuadrática**: Calcular el producto geométrico completo en álgebra de Clifford $C\ell(D)$ implica $O(D^2)$ operaciones, volviéndose inviable para $D > 10^5$.[^3_2][^3_1]


## Mandato V903: migrar a bi-vectores + Sparse Rolling Interaction

### 1. Representación empaquetada de bi-vectores antisimétricos

En lugar de almacenar $X \in \mathbb{R}^{D \times K}$ y calcular $X^T X \in \mathbb{R}^{K \times K}$, se representa la interacción como un **bi-vector** en el espacio de Grassmann $Gr(2, K)$, con solo $K(K-1)/2$ coeficientes independientes.[^3_2][^3_1]

- **Tamaño**: Para $K = 128$, el bi-vector empaquetado tiene $128 \times 127 / 2 = 8128$ coeficientes, reduciendo la memoria de 500 MB a $\approx 32$ KB (float32).[^3_1]
- **Estructura**: Cada coeficiente $b_{ij} = x_i \wedge x_j = x_i x_j^T - x_j x_i^T$ captura la orientación geométrica entre pares de canales, preservando la información antisimétrica crítica para retracciones Stiefel.[^3_2]


### 2. Sparse Rolling Interaction (SRI) — estrategia CliffordNet 2026

En vez de calcular el producto geométrico denso para todos los pares de canales, SRI aplica **shifts cíclicos sparse** sobre el vector de características $H \in \mathbb{R}^D$, capturando interacciones locales con complejidad lineal.[^3_1][^3_2]

#### Operador de shift $T_s$

Para un conjunto de offsets $S = \{s_1, s_2, \dots, s_{|S|}\}$, se define:

- **Término escalar (producto punto)**:\

$$
D_s(H, C) = \\text{SiLU}(H \\odot T_s(C))
$$
- **Término bi-vector (producto cuña)**:\

$$
W_s(H, C) = H \\odot T_s(C) - T_s(H) \\odot C
$$

donde $\odot$ es el producto Hadamard y $T_s$ desplaza cíclicamente el vector por $s$ posiciones.[^3_2][^3_1]

#### Complejidad resultante

- **Densa**: $O(D^2)$ por capa.
- **SRI**: $O(D \cdot |S|)$, con $|S| = 5$ shifts típicos → **reducción de 200,000×** para $D = 10^6$. [^3_1][^3_2]


### 3. Kernels SIMD AVX-512 para speedup 12×–15×

AVX-512 permite procesar **16 floats32 por instrucción** con unidades FMA (fused multiply-add), ideal para los términos $H \odot T_s(C)$ y $W_s(H, C)$.[^3_3][^3_4]

#### Instrucciones clave

- **\_mm512_fnmadd_ps**: Fused negative multiply-add ($-(a \times b) + c$), usada para calcular $W_s$ eficientemente.[^3_6][^3_3]
- **\_mm512_mul_ps** + **\_mm512_add_ps**: Para términos escalares $D_s$.[^3_7][^3_6]


#### Benchmarks empíricos

- **N-body solver AVX-512**: 3.4× speedup vs auto-vectorizado, alcanzando ~120 GFLOPS (75% del pico FMA).[^3_5]
- **Matriz-vector AVX-512**: 1.80× vs AVX2; con hand-optimized kernels, se reportan **4×–12×** en workloads densos.[^3_4][^3_8]
- **CliffordNet-SRI**: Al combinar SRI con AVX-512, se esperan **12×–15×** speedups respecto a la implementación densa en CPU, dado que SRI reduce el trabajo a $O(D)$ y AVX-512 maximiza el throughput.[^3_1][^3_2]


## Hoja de ruta de implementación V903

1. **Empaquetar bi-vectores**: Reemplazar $X \in \mathbb{R}^{D \times K}$ por $B \in \mathbb{R}^{K(K-1)/2}$; validar que la retracción Stiefel preserve ortogonalidad ($X^T X = I$).[^3_2][^3_1]
2. **Implementar SRI con $S = 5$**: Usar shifts $s \in \{1, 2, 4, 8, 16\}$ para capturar interacciones multi-escala; medir complejidad $O(D \cdot 5)$.[^3_1][^3_2]
3. **Vectorizar con AVX-512**: Escribir kernels en C++/intrinsics para $D_s$ y $W_s$ usando \_mm512_fnmadd_ps; alinear datos a 64 bytes para evitar penalties.[^3_9][^3_3][^3_6]
4. **Validar speedup**: Comparar latencia por iteración (densa vs SRI+AVX-512) para $D = 10^5, 10^6$;目标是 12×–15× más rápido.[^3_4][^3_5]

## Referencias clave

- CliffordNet 2026: Sparse Rolling Interaction reduce $O(D^2)$ a $O(D \cdot |S|)$ con bi-vectores empaquetados. [^3_1][^3_2]
- AVX-512: 16-wide float32, \_mm512_fnmadd_ps para FMA; speedups 3.4×–12× en workloads vectorizados.[^3_3][^3_5][^3_4]
- Benchmarks SIMD: Hand-optimized AVX-512 logra 95–98% del pico FMA, con 4×–18.7× speedups en kernels densos.[^3_5][^3_9]

Para profundizar en la solución SOTA del cuello de botella $O(D K^2)$ en retracciones Stiefel, la clave está en **optimizar el conjunto de shifts $S$** en Sparse Rolling Interaction (SRI), **empaquetar bi-vectores con estructura antisimétrica explícita** y **vectorizar kernels AVX-512 con FMA y tiling de caché** para alcanzar los 12×–15× de speedup.[^4_1][^4_2][^4_3]

## 1. Optimización del conjunto de shifts $S$ en SRI

CliffordNet 2026 usa shifts cíclicos $S = \{s_1, s_2, \dots, s_{|S|}\}$ para aproximar el producto geométrico denso. [^4_1] El conjunto óptimo balancea **cobertura de interacciones** y **complejidad lineal** $O(D \cdot |S|)$.

### Configuración recomendada V903

| Estrategia | Shifts $S$ | $|S|$ | Cobertura de interacciones | Complejidad |
|------------|--------------|--------|----------------------------|-------------|
| **Powers-of-2** (default) | $\{1, 2, 4, 8, 16\}$ | 5 | Multi-escala (local → medio rango) | $O(5D)$ [^4_1] |
| **Primos pequeños** | $\{1, 3, 5, 7, 11\}$ | 5 | Mejor dispersión espectral | $O(5D)$ [^4_1] |
| **Híbrido** | $\{1, 2, 5, 10, 21\}$ | 5 | Balance local/global | $O(5D)$ [^4_1] |

**Recomendación**: Usar **$S = \{1, 2, 4, 8, 16\}$** como punto de partida; si la retracción Stiefel pierde ortogonalidad ($\|X^T X - I\|_F > 10^{-4}$), cambiar a primos $\{1, 3, 5, 7, 11\}$ para mejorar la cobertura espectral. [^4_1][^4_4]

## 2. Empaquetado de bi-vectores antisimétricos

En lugar de almacenar $B \in \mathbb{R}^{K(K-1)/2}$ como vector plano, se usa una **estructura triangular superior empaquetada** para explotar la antisimetría $b_{ij} = -b_{ji}$.[^4_5][^4_1]

### Formato de almacenamiento

Para $K = 128$, el bi-vector se almacena como:

```python
# Índices (i, j) con i < j, en orden lexicográfico
packed_B = [B[0,1], B[0,2], ..., B[0,127], B[1,2], ..., B[126,127]]
# Longitud: 128*127/2 = 8128 coeficientes (float32 → 32 KB)
```

**Ventajas**:

- **Memoria**: 32 KB vs 500 MB de $X^T X$ denso.[^4_1]
- **Acceso**: Índice directo $idx(i, j) = i \cdot K - i(i+1)/2 + (j - i - 1)$ para $i < j$.[^4_5]
- **Retracción Stiefel**: La polar/QR retraction se aplica sobre $B$ empaquetado, preservando ortogonalidad con error $\|X^T X - I\|_F < 10^{-6}$. [^4_4][^4_5][^4_6]


## 3. Kernels AVX-512 optimizados para $D_s$ y $W_s$

Los términos escalares $D_s(H, C) = \text{SiLU}(H \odot T_s(C))$ y bi-vectores $W_s(H, C) = H \odot T_s(C) - T_s(H) \odot C$ se vectorizan con **FMA (fused multiply-add)** y **tiling de caché** para maximizar el throughput.[^4_2][^4_3]

### Kernel para $W_s$ con \_mm512_fnmadd_ps

```cpp
// W_s = H * T_s(C) - T_s(H) * C
// Asumiendo H, C, T_s(H), T_s(C) alineados a 64 bytes
void compute_Ws_avx512(const float* H, const float* C, 
                       const float* Ts_H, const float* Ts_C,
                       float* Ws, int D) {
    for (int i = 0; i < D; i += 16) {
        __m512 h = _mm512_load_ps(&H[i]);
        __m512 c = _mm512_load_ps(&C[i]);
        __m512 ts_h = _mm512_load_ps(&Ts_H[i]);
        __m512 ts_c = _mm512_load_ps(&Ts_C[i]);
        
        // term1 = H * T_s(C)
        __m512 term1 = _mm512_mul_ps(h, ts_c);
        // term2 = T_s(H) * C
        __m512 term2 = _mm512_mul_ps(ts_h, c);
        // Ws = term1 - term2 (usando FMA negativa)
        __m512 ws = _mm512_fnmadd_ps(ts_h, c, term1); // -(ts_h * c) + term1
        
        _mm512_store_ps(&Ws[i], ws);
    }
}
```

**Optimizaciones clave**:

- **FMA**: \_mm512_fnmadd_ps ejecuta $-(a \times b) + c$ en una instrucción, reduciendo latencia y mejorando precisión.[^4_7][^4_2]
- **Alineación 64 bytes**: Evita penalties de carga/descarga no alineada.[^4_3][^4_2]
- **Loop unrolling**: Procesar 4 bloques de 16 floats por iteración para ocultar latencia de FMA.[^4_2][^4_3]

# C. Asignación Dinámica en Entornos Multihilo (Windows Malloc Lock) busca las mejoras y solucione sota

Brecha: El Heap de Win32 y GCC 14.2 libgomp serializan llamadas concurrentes a malloc/new dentro de \#pragma omp parallel.
Mandato V903: Mantener la regla de higiene estricta: Cero std::vector o new dentro de bucles paralelos. Memoria pre-asignada thread-local con alineación a 64 bytes (CACHE_LINE_PAD) e inicialización First-Touch (NUMA-aware).

La solución SOTA para eliminar el lock contention de `malloc`/`new` en entornos multihilo con OpenMP es combinar **pools de memoria thread-local pre-asignados** (alineados a 64 bytes) con **inicialización First-Touch NUMA-aware** y, opcionalmente, reemplazar el allocator por defecto con **mimalloc** o **jemalloc**, que reducen la contención en 1.5×–1.75× frente a glibc/Windows Heap.[^5_1][^5_2][^5_3][^5_4]

## Por qué falla `malloc`/`new` dentro de `#pragma omp parallel`

- **Serialización del heap**: Tanto el Win32 Heap como `libgomp` (GCC 14.2) usan locks globales para `malloc`/`new`, forzando a los threads a esperar en cola cuando hay asignaciones concurrentes.[^5_5][^5_6]
- **Contención de locks**: En bucles paralelos con miles de iteraciones, la sobrecarga de adquisición/release de locks domina el tiempo de ejecución, degradando el speedup de 8× a 2×–3× en sistemas de 16 cores.[^5_7][^5_5]
- **Falsa compartición (false sharing)**: Si los buffers asignados no están alineados a 64 bytes (CACHE_LINE_SIZE), los writes de threads adyacentes invalidan líneas de caché, multiplicando la latencia.[^5_4][^5_8]


## Mandato V903: pools thread-local + First-Touch NUMA

### 1. Memoria pre-asignada thread-local (TLS)

Cada thread de OpenMP recibe un pool privado de buffers, eliminando locks y false sharing.[^5_3][^5_4]

```cpp
#include <omp.h>
#include <cstdint>

constexpr size_t CACHE_LINE = 64;
constexpr size_t POOL_SIZE = 1024 * 1024; // 1 MB por thread

// Estructura alineada a 64 bytes
struct alignas(CACHE_LINE) ThreadLocalPool {
    alignas(CACHE_LINE) uint8_t buffer[POOL_SIZE];
    size_t offset = 0;
    
    void* allocate(size_t bytes) {
        size_t aligned_bytes = (bytes + CACHE_LINE - 1) & ~(CACHE_LINE - 1);
        if (offset + aligned_bytes > POOL_SIZE) return nullptr; // OOB
        void* ptr = &buffer[offset];
        offset += aligned_bytes;
        return ptr;
    }
    
    void reset() { offset = 0; }
};

// TLS: cada thread tiene su propia instancia
thread_local ThreadLocalPool tls_pool;

#pragma omp parallel
{
    // Inicialización First-Touch: tocar memoria en el thread correcto
    tls_pool.buffer[^5_0] = 1;
    
    #pragma omp for
    for (int i = 0; i < N; ++i) {
        auto* data = static_cast<float*>(tls_pool.allocate(sizeof(float) * K));
        // ... computación sin malloc/new ...
    }
}
```

**Ventajas**:

- **Cero locks**: Cada thread opera sobre su propio buffer.[^5_3][^5_4]
- **Alineación 64 bytes**: Evita false sharing entre threads.[^5_8][^5_4]
- **Reset rápido**: `tls_pool.reset()` al inicio de cada iteración externa.[^5_3]


### 2. Inicialización First-Touch NUMA-aware

En sistemas NUMA (ej. dual-socket Xeon), la política "first touch" asigna páginas de memoria al nodo del primer thread que las accede.[^5_9][^5_10][^5_8]

**Problema**: Si el thread maestro inicializa los pools antes del `#pragma omp parallel`, todos los buffers se asignan en el nodo 0, forzando accesos remotos (2×–3× más lentos).[^5_4][^5_9]

**Solución V903**: Tocar la memoria **dentro** de la región paralela, asegurando que cada thread aloque en su nodo local.[^5_10][^5_8][^5_9]

```cpp
#pragma omp parallel num_threads(numa_nodes)
{
    int node = omp_get_thread_num();
    // First-Touch: tocar buffer en el thread correcto
    tls_pool.buffer[^5_0] = 1;
    tls_pool.buffer[CACHE_LINE] = 1;
    
    // Opcional: pinning explícito con libnuma
    // numa_run_on_node(node);
    // mbind(tls_pool.buffer, POOL_SIZE, MPOL_BIND, ...);
}
```

**Resultado**: Latencia de acceso local (L3 cache) vs remota (cross-socket interconnect).[^5_8][^5_4]

### 3. Reemplazar allocator: mimalloc/jemalloc (opcional)

Si no es viable pre-asignar todo, usar allocators optimizados para multihilo reduce la contención.[^5_2][^5_11][^5_3]


| Allocator | Speedup (16 threads) | P99 latencia | Memoria |

## 2. First-Touch NUMA: patrón correcto vs anti-patrón

El error más común es inicializar buffers **antes** de la región paralela, forzando toda la memoria en el nodo 0.[^6_3][^6_7][^6_2]

### Anti-patrón (incorrecto)

```cpp
// ERROR: malloc fuera del parallel → todos los buffers en nodo 0
ThreadLocalPool* pools = new ThreadLocalPool[num_threads];
memset(pools, 0, sizeof(ThreadLocalPool) * num_threads);

#pragma omp parallel for
for (int i = 0; i < N; ++i) {
    // Acceso remoto (cross-socket) → 2×–3× más lento
    auto* data = pools[omp_get_thread_num()].allocate(size);
}
```

**Problema**: `malloc` y `memset` tocan las páginas en el thread maestro (nodo 0); los threads remotos sufren latencia de acceso cross-socket.[^6_8][^6_2][^6_3]

### Patrón correcto (First-Touch dentro del parallel)

```cpp
// Correcto: tocar memoria dentro de cada thread
#pragma omp parallel
{
    int tid = omp_get_thread_num();
    
    // First-Touch: tocar buffer en el thread correcto
    tls_pool.buffer[^6_0] = 1;
    tls_pool.buffer[CACHE_LINE] = 1;
    tls_pool.buffer[2 * CACHE_LINE] = 1;
    
    // Opcional: pinning explícito con libnuma (Linux)
    // #include <numa.h>
    // numa_run_on_node(tid % numa_num_configured_nodes());
    
    #pragma omp for
    for (int i = 0; i < N; ++i) {
        auto* data = static_cast<float*>(tls_pool.allocate(sizeof(float) * K));
        // ... computación ...
    }
}
```

**Resultado**: Cada página se asigna en el nodo del thread que la toca primero; latencia local (L3) vs remota (QPI/UPI).[^6_7][^6_2][^6_3]

### Pinning explícito con libnuma (Linux)

Para control total, usar `mbind()` + `numa_run_on_node()`:

```cpp
#include <numa.h>
#include <numaif.h>

#pragma omp parallel
{
    int tid = omp_get_thread_num();
    int node = tid % numa_num_configured_nodes();
    
    // Pin thread al nodo NUMA
    numa_run_on_node(node);
    
    // Allocar en nodo específico
    void* ptr = numa_alloc_onnode(POOL_SIZE, node);
    
    // First-Touch: tocar buffer
    memset(ptr, 0, POOL_SIZE);
    
    // Opcional: bloquear política BIND

```

**Ventaja**: Garantiza que memoria y threads estén en el mismo nodo, incluso con load balancing del OS.[^6_9][^6_2][^6_8]

## 3. Eliminar false sharing con `alignas(64)`

El false sharing ocurre cuando threads adyacentes escriben a variables distintas en la misma línea de caché (64 bytes), invalidando la línea en todos los cores.[^6_4]

### Anti-patrón (false sharing)

```cpp
// ERROR: counters adyacentes en misma línea de caché
struct Stats {
    uint64_t count[^6_64]; // 64 threads × 8 bytes = 512 bytes
};
Stats stats; // Sin alineación → false sharing

#pragma omp parallel for
for (int i = 0; i < N; ++i) {
    stats.count[omp_get_thread_num()]++; // Invalida línea en todos los cores
}
```

**Impacto**: Speedup de 8× cae a 2×–3× por invalidaciones de caché.[^6_4]

### Patrón correcto (`alignas(64)` por elemento)

```cpp
// Correcto: cada counter en su propia línea de caché
struct alignas(64) PaddedCounter {
    uint64_t count;
    uint8_t pad[^6_56]; // Padding a 64 bytes
};

PaddedCounter stats[^6_64]; // 64 × 64 bytes = 4 KB

#pragma omp parallel for
for (int i = 0; i < N; ++i) {
    stats[omp_get_thread_num()].count++; // Sin false sharing
}
```

**Resultado**: Speedup lineal (8× en 8 cores).[^6_4]

### Aplicación a ThreadLocalPool

```cpp
struct alignas(64) ThreadLocalPool {
    alignas(64) uint8_t buffer[POOL_SIZE];
    size_t offset = 0;
    uint8_t pad[64 - sizeof(size_t)]; // Padding a 64 bytes
    
    void* allocate(size_t bytes) {
        size_t aligned_bytes = (bytes + 63) & ~63;
        if (offset + aligned_bytes > POOL_SIZE) return nullptr;
        void* ptr = &buffer[offset];
        offset += aligned_bytes;
        return ptr;
    }
    
    void reset() { offset = 0; }
};

// TLS: cada thread tiene su propia instancia (sin false sharing)
thread_local ThreadLocalPool tls_pool;
```
