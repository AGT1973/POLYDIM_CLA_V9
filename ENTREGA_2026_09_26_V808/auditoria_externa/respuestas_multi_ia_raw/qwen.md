O(1)

para transferencia de tensores.

Esto es verdad **solo para el handshake de puntero/handle**, no para el tensor completo.

Si el receptor debe:

- validar el tensor,
- comprobar integridad,
- descifrar,

- normalizar,
- proyectar a \(S^{D-1}\),
- calcular distancias Fréchet/Betti,

entonces el coste real es:

\[
O(D)
\]

o peor.

- FP32: \(10^7 \times 4 = 40\ \text{MiB}\) por tensor.
- FP64: \(10^7 \times 8 = 80\ \text{MiB}\) por tensor.

El contrato `02_SILICON_CONTRACT.md` puede estar vendiendo una garantía falsa:

> Zero-Copy IPC implica O(1) total.

PMTP control-plane transfer: O(1)

donde \(A\) = número de agentes.

## 1.3 Problema: “Hardware agnosticism” con TPU/CUDA/ROCm/OpenMP no es realista sin un modelo de memoria explícito

El documento promete despacho dinámico entre:

- TPU/Pallas,
- CUDA,
- ROCm,
- OpenMP CPU.

### Ataque

Estos backends no exponen el mismo modelo de memoria.

- CUDA puede compartir device pointers dentro de un contexto, pero con restricciones.
- ROCm tiene modelo parecido pero no idéntico.
- TPU/Pallas no suele exponer punteros crudos arbitrarios como CUDA.
- CPU OpenMP puede acceder a RAM normal.
- Python puede tener tensores en GPU, CPU pinned, unified memory, etc.

Pasar un “puntero nativo” sin un descriptor de dispositivo es un fallo potencial.

### Impacto

Si C++ recibe un puntero VRAM creyendo que es host memory:

\[
\text{Segfault}
\]

Si Rust recibe un tensor no contiguo:

\[
\text{UB o lectura incorrecta}
\]

Si TPU no permite zero-copy real:

\[
\text{el contrato PMTP se rompe}
\]

### Solución SOTA

Introducir un descriptor FFI explícito:

```c
typedef enum {
    POLYDIM_DEVICE_CPU = 0,
    POLYDIM_DEVICE_CUDA = 1,
    POLYDIM_DEVICE_ROCM = 2,
    POLYDIM_DEVICE_TPU = 3
} PolydimDevice;

typedef struct {
    uint64_t abi_version;
    uint64_t slab_id;
    uint64_t generation;
    uint64_t offset;
    uint64_t byte_len;
    uint64_t dtype;
    uint64_t rank;
    PolydimDevice device;
    uint64_t flags;
} PolydimTensorHandle;
```

Reglas:

1. Nunca pasar `void*` crudo entre procesos.
2. Pasar `offset` dentro de una región compartida.
3. El receptor resuelve `base_local + offset`.
4. Si `device != CPU`, el núcleo C++ CPU debe rechazar el handle.
5. Si el backend GPU puede consumir el handle, debe validarlo con APIs específicas del dispositivo.

## 2.1 ERROR CRÍTICO: objetivo de error \(4.44 \times 10^{-16}\) incompatible con FP32

El documento exige:

\[
\left| \|y_{\text{final}}\|_2^2 - 1 \right| \le 4.44 \times 10^{-16}
\]

Pero también habla de:

- drift numérico FP32,
- núcleo matemático C++14/17,
- GPU/TPU,
- optimizaciones SIMD,
- operaciones en \(D \ge 10^6\).

### Ataque

FP32 tiene unit roundoff:

\[
\epsilon_{\text{FP32}} \approx 1.19 \times 10^{-7}
\]

FP64 tiene:

\[
\epsilon_{\text{FP64}} \approx 2.22 \times 10^{-16}
\]

La cota:

\[
4.44 \times 10^{-16}
\]

es del orden de \(2\epsilon_{\text{FP64}}\).

Por tanto, si el vector final está almacenado en FP32, esa cota es **matemáticamente imposible en general**.

### Impacto

Esto rompe el contrato de estabilidad.

Si los tests dicen pasar con esa cota usando FP32, hay una de estas:

1. Los tests no verifican la cota real.
2. Los tensores están secretamente en FP64.
3. Se usa una métrica más laxa.
4. Hay condiciones de entrada artificialmente benignas.
5. El log de certificación no demuestra lo que afirma.

### Solución

Hay tres opciones válidas:

#### Opción A — Estado interno FP64

Si se requiere:

\[
\le 4.44 \times 10^{-16}
\]

entonces el estado crítico debe estar en FP64.

#### Opción B — Relajar contrato para FP32

Para FP32, usar una cota realista:

\[
\left| \|y\|_2^2 - 1 \right| \le 10^{-5}
\]

o, con mucho cuidado:

\[
10^{-6}
\]

dependiendo de \(D\), distribución de componentes y acumuladores.

#### Opción C — Representación compensada

Usar double-double, error-free transforms o expansión de precisión, pero eso tiene coste:

\[
O(D)
\]

y mayor complejidad en GPU.

### Fix recomendado

Cambiar el contrato:

```text
FP64 critical state: target residual <= 4.44e-16.
FP32 tensor state: target residual must be explicitly bounded by 
dtype-aware tests; no se acepta una cota FP64 sobre storage FP32.
```

## 2.2 ERROR MATEMÁTICO: `versin(θ)` y `sin(θ)` en la rotación Rodrigues pueden sufrir cancelación catastrófica

La rotación dada es:

\[
\operatorname{Rot}(y,u,v,\theta)
=
y
-
\operatorname{versin}(\theta)
\left[
(y^\top u)u + (y^\top v_\perp)v_\perp
\right]
+
\sin(\theta)
\left[
(y^\top u)v_\perp - (y^\top v_\perp)u
\right]
\]

### Ataque

Para \(\theta \to 0\):

\[
\operatorname{versin}(\theta)
=
1 - \cos\theta
\approx
\frac{\theta^2}{2}
\]

Si se calcula como:

```cpp
double versin = 1.0 - cos(theta);
```

hay cancelación catastrófica para \(\theta\) pequeño.

Aunque se use Kahan/Neumaier en otras partes, esto no arregla la pérdida de precisión en `1 - cos(theta)`.

Además:

- si \(u\) y \(v_\perp\) no son perfectamente ortonormales, la rotación no es ortogonal;
- si \(v_\perp\) se calcula con una sola pasada de Gram-Schmidt, puede perder ortogonalidad;
- si \(\theta\) es menor que ULP del estado, la actualización desaparece;
- si el resultado no se retrae a la esfera, el error se acumula.

### Impacto

En \(S^{D-1}\), una rotación supuestamente geodésica puede convertirse en:

- deriva radial,
- pérdida de ortogonalidad del plano de rotación,
- deformación métrica,
- corrupción del consenso topológico,
- falsos outliers en Fréchet-Betti.

### Solución SOTA

No usar `versin = 1 - cos(theta)` directamente.

Usar:

\[
1 - \cos\theta = 2\sin^2(\theta/2)
\]

y para \(\theta\) pequeño usar expansiones estables o funciones `sinc`.

Forma más estable:

Dado:

\[
u \perp w,\quad \|u\|=\|w\|=1
\]

y:

\[
a = y^\top u,\quad b = y^\top w
\]

entonces:

\[
y' =
y
+
\left[a(\cos\theta - 1) - b\sin\theta\right]u
+
\left[a\sin\theta + b(\cos\theta - 1)\right]w
\]

donde:

\[
\cos\theta - 1 = -2\sin^2(\theta/2)
\]

Para \(\theta\) pequeño:

\[
\sin\theta \approx \theta \operatorname{sinc}(\theta)
\]

\[
\cos\theta - 1
\approx
-\frac{\theta^2}{2}\operatorname{sinc}^2(\theta/2)
\]

### Implementación recomendada

```cpp
// u y w deben ser ortonormales con reortogonalización certificada.
// a = dot(y,u), b = dot(y,w)

double s, c_minus_1;

if (fabs(theta) < 1e-4) {
    double th2 = theta * theta;
    double sinc_half = sinc(theta * 0.5);
    s = theta * sinc(theta);
    c_minus_1 = -0.5 * th2 * sinc_half * sinc_half;
} else {
    s = sin(theta);
    c_minus_1 = -2.0 * sin(theta * 0.5) * sin(theta * 0.5);
}

double du = fma(a, c_minus_1, -b * s);
double dw = fma(a, s, b * c_minus_1);

// y' = y + du*u + dw*w
```

Luego:

```cpp
y_prime = y + du*u + dw*w;
y_final = normalize_compensated(y_prime);
```

### Requisito adicional

La base \(\{u,w\}\) debe ser verificada:

\[
|u^\top w| \le \tau
\]

\[
\left|\|u\|^2 - 1\right| \le \tau
\]

\[
\left|\|w\|^2 - 1\right| \le \tau
\]

Si no, rechazar o reortogonalizar.

## 2.3 ERROR: Gram-Schmidt simple para obtener \(v_\perp\) es insuficiente

Si:

\[
v_\perp = v - (u^\top v)u
\]

y luego:

\[
v_\perp = v_\perp / \|v_\perp\|
\]

### Ataque

En alta dimensión y con \(u^\top v \approx 1\), la resta puede casi anular \(v\). Eso produce:

- pérdida severa de precisión,
- vector casi nulo,
- normalización inestable,
- dirección arbitraria dominada por ruido de redondeo.

### Solución

Usar **Gram-Schmidt con reortogonalización doble**:

\[
v_1 = v - (u^\top v)u
\]

\[
v_2 = v_1 - (u^\top v_1)u
\]

\[
w = \frac{v_2}{\|v_2\|}
\]

Si:

\[
\|v_2\| < \tau
\]

entonces \(u\) y \(v\) son casi colineales. En ese caso:

- rechazar la rotación,
- o construir un vector ortogonal auxiliar estable,
- o elegir otro plano.

Nunca normalizar un vector casi nulo sin flag de error.

## 2.4 ERROR: la norma \(\|y\|_2\) puede desbordarse o subdesbordarse aunque Kahan/Neumaier esté presente

Kahan/Neumaier compensa la suma, pero no resuelve:

\[
x_i^2
\]

si \(x_i\) es muy grande o muy pequeño.

### Ataque

Para \(D = 10^7\), si algunos componentes son grandes:

\[
x_i^2
\]

puede overflow en FP32.

Si componentes son subnormales:

\[
x_i^2
\]

puede underflow a cero.

### Solución SOTA

Usar norma escalada tipo Blue/hypot:

\[
m = \max_i |x_i|
\]

Si \(m = 0\), error.

Si no:

\[
\|x\| = m \sqrt{\sum_i \left(\frac{x_i}{m}\right)^2}
\]

La suma debe hacerse con Neumaier/FP64.

### Implementación conceptual

```cpp
double max_abs = 0.0;

for (i = 0; i < D; ++i)
    max_abs = fmax(max_abs, fabs(x[i]));

if (max_abs == 0.0) return NORM_ZERO_ERROR;

NeumaierAcc acc;

for (i = 0; i < D; ++i) {
    double t = x[i] / max_abs;
    acc.add(t * t);
}

double norm = max_abs * sqrt(acc.result());
```

### Requisito

Prohibir normalizar vectores con:

- NaN,
- Inf,
- norma cero,
- componentes subnormales no controlados,
- dispositivo incorrecto.

## 2.5 ERROR: Shifted CholQR + Tikhonov puede estabilizar pero sesgar la geometría

El reporte dice:

- Shifted CholQR,
- regularización de Tikhonov,
- diagonal \(+ \epsilon I\).

### Ataque

Cholesky-QR es sensible a matrices mal condicionadas. Shifted CholQR ayuda, pero:

- si el shift es demasiado pequeño, no regulariza;
- si es demasiado grande, cambia la geometría;
- si la matriz está casi singular, QR puede producir vectores artificialmente ortogonales pero semánticamente incorrectos;
- si el Gram se acumula en FP32, el error puede dominar.

### Impacto

En el Stiefel manifold:

\[
X^\top X = I
\]

no se preserva si la ortogonalización está mal condicionada.

### Solución SOTA

1. Calcular Gram en FP64:

\[
G = X^\top X
\]

2. Estimar número de condición:

\[
\kappa(G)
\]

3. Si \(\kappa(G)\) es moderado, usar CholQR.

4. Si \(\kappa(G)\) es alto:

   - reortogonalizar dos veces,
   - usar TSQR para distribución por bloques,
   - usar SVD como fallback,
   - o usar Householder QR si el tamaño lo permite.

5. El shift debe ser adaptativo:

\[
G_\epsilon = G + \lambda I
\]

con:

\[
\lambda = \max(\lambda_{\min}, \alpha \cdot \hat{\epsilon} \cdot \|G\|)
\]

No usar un \(\epsilon\) fijo mágico.

### Requisito de test

Para cada ortogonalización, verificar:

\[
\|X^\top X - I\|_F \le \tau
\]

con \(\tau\) dependiente de dtype y \(D\).

# PASS 3 — CONCURRENCIA, IPC ZERO-COPY Y MEMORIA COMPARTIDA

## 3.1 ERROR CRÍTICO: pasar punteros nativos entre procesos es inseguro por diseño

El documento habla de pasar “punteros nativos de memoria” mediante PMTP.

### Ataque

Un puntero virtual es válido solo dentro del espacio de direcciones de un proceso.

Si dos procesos mapean la misma memoria compartida, la dirección base puede ser distinta.

Por tanto, pasar:

```cpp
void* ptr
```

entre procesos puede producir:

- acceso a memoria inválida,
- corrupción,
- use-after-free,
- vulnerabilidad de confundibilidad de objeto,
- crash no reproducible.

### Solución obligatoria

No pasar punteros absolutos.

Pasar:

```text
slab_id + generation + offset + length + checksum
```

El receptor resuelve:

\[
\text{local\_ptr} = \text{base\_local} + \text{offset}
\]

### Estructura recomendada

```cpp
struct PmtpRef {
    uint64_t slab_id;
    uint64_t generation;
    uint64_t offset;
    uint64_t byte_len;
    uint64_t content_hash;
    uint64_t seq;
};
```

Esto convierte el “zero-copy pointer passing” en algo realmente portable.

## 3.2 ERROR CRÍTICO: Seqlock + zero-copy in-place es contradictorio

Un seqlock permite detectar lecturas inconsistentes, pero normalmente exige copiar el payload durante la lectura.

Si el lector no copia, sino que lee directamente el tensor compartido mientras trabaja, el escritor puede mutarlo durante el cómputo.

### Ataque

Escenario:

1. Escritor publica tensor.
2. Lector empieza a leer.
3. Escritor actualiza el mismo slab.
4. Lector calcula sobre datos parcialmente nuevos y parcialmente viejos.
5. El resultado es corrupto aunque el seqlock marque “estable” al inicio.

### Impacto

Data race semántico. El seqlock no protege el uso prolongado del buffer compartido.

### Solución SOTA

Usar uno de estos modelos:

#### Modelo A — Copy-on-read

El lector copia el tensor a memoria privada mientras el seqlock está estable.

Ventaja: simple.  
Desventaja: rompe zero-copy puro, coste \(O(D)\).

#### Modelo B — Double buffering

El escritor escribe en buffer A o B.

Publica índice atómico:

```cpp
atomic<uint64_t> active_index;
```

El lector usa el buffer activo inmutable hasta que el escritor publique el siguiente.

Requisito:

- el escritor no puede reescribir un buffer mientras lectores activos lo usen.

#### Modelo C — Epoch-Based Reclamation / RCU-like

Cada lector entra en una época:

```cpp
enter_epoch();
read();
leave_epoch();
```

El escritor solo recicla slabs después de un periodo de gracia.

#### Modelo D — Slabs inmutables versionados

Cada tensor nuevo se escribe en un slab nuevo.

El control publica:

```text
slab_id + generation
```

Los slabs viejos se destruyen cuando no hay referencias.

### Recomendación

Para POLYDIM, la opción más robusta es:

```text
Slabs inmutables versionados + reference counting interproceso + doble buffer para hot-path.
```

## 3.3 ERROR: `__ulock_wait` y `WaitOnAddress` no son una base portable para IPC multi-proceso

El reporte menciona:

- macOS: `__ulock_wait/wake`
- Windows: fallback adaptativo con spinning y semáforos nombrados

### Ataque

`__ulock_wait` es API privada de macOS/XNU.

Riesgos:

1. Puede cambiar entre versiones.
2. Puede no tener semántica multi-proceso garantizada.
3. Puede requerir que la dirección esperada esté en el mismo espacio virtual.
4. Puede causar rechazo en distribución si se usa en entornos restringidos.
5. Puede producir deadlocks si la dirección de espera no coincide entre procesos.

En Windows, `WaitOnAddress` está pensado principalmente para sincronización intra-proceso. Si se usa entre procesos sin validación, puede fallar silenciosamente.

### Solución

No depender de primitivas privadas o intra-proceso para IPC.

Usar:

- Linux: futex compartido, eventfd, epoll, POSIX semaphores, robust mutexes.
- macOS: Mach ports, kqueue, named POSIX synchronization primitives soportadas.
- Windows: named semaphores, named events, waitable timers.

Patrón recomendado:

```text
Adaptive spin corto -> fallback a primitiva OS multi-proceso
```

### Contrato

```text
Toda espera interproceso debe ser verificada con:
- writer en proceso A
- reader en proceso B
- kill -9 de A durante espera
- restart de A
- seq impar
- slab corrupto
```

## 3.4 ERROR: SPSC wait-free no escala si hay múltiples productores/consumidores

El reporte menciona anillo SPSC wait-free con 62,000 eventos/s.

### Ataque

SPSC significa:

- Single Producer,
- Single Consumer.

Si POLYDIM tiene un swarm de agentes, entonces puede haber:

- múltiples escritores,
- múltiples lectores,
- múltiples agentes publicando tensores,
- múltiples filtros topológicos consumiendo.

Si se fuerza SPSC donde hay múltiples productores, aparecen data races.

### Solución

Elegir explícitamente:

#### Opción A — Canales SPSC por par agente

Cada par de agentes tiene su canal:

\[
A_i \rightarrow B_j
\]

Ventaja: wait-free simple.  
Desventaja: \(O(A^2)\) canales.

#### Opción B — Sharding

Varios buses SPSC, con hash por agente o tensor.

#### Opción C — MPMC lock-free

Más complejo. Requiere:

- ABA counter,
- memory reclamation,
- backpressure,
- bounded capacity.

### Requisito

Documentar:

```text
Número máximo de productores.
Número máximo de consumidores.
Política de backpressure.
Comportamiento si el anillo está lleno.
```

## 3.5 ERROR: el slab allocator puede sufrir ABA, fuga y process-death leakage

Si un slab se libera mientras otro proceso todavía tiene una referencia, hay use-after-free.

Si un proceso muere sosteniendo un reference count, el slab queda bloqueado.

### Ataque

1. Agente A publica slab 42.
2. Agente B empieza a leer slab 42.
3. Agente A libera slab 42.
4. Agente A reasigna slab 42 con nuevo contenido.
5. Agente B mezcla contenido viejo/nuevo.

O:

1. Agente B incrementa refcount.
2. Agente B muere con `SIGKILL`.
3. Refcount nunca decrementa.
4. Slab leak permanente.

### Solución

Cada slab debe tener:

```cpp
struct SlabHeader {
    atomic<uint64_t> generation;
    atomic<uint64_t> state;
    atomic<uint64_t> refcount;
    uint64_t owner_pid_token;
    uint64_t created_seq;
    uint64_t byte_len;
    uint64_t checksum;
    uint64_t poison_canary;
};
```

Mecanismos:

1. Generation counter contra ABA.
2. Leases con PID + token único.
3. Watchdog que limpia procesos muertos.
4. Cuarentena de slabs corruptos.
5. Quotas de memoria por agente.
6. No reutilizar slab hasta que no haya lectores.
7. Canary values para detectar sobrescritura.

## 3.6 ERROR: memory ordering insuficiente en seqlocks y anillos

No basta con usar `volatile`.

### Ataque

Sin barreras correctas, el lector puede ver:

- seq actualizado antes que payload,
- payload parcialmente escrito,
- flags publicados antes que datos,
- reorder en ARM.

### Solución mínima

Escritor:

```text
1. escribir payload
2. fence release
3. publicar seq/flag
```

Lector:

```text
1. leer seq con acquire
2. leer payload
3. fence acquire
4. releer seq
5. validar igualdad y paridad
```

En C++:

- `std::memory_order_release`
- `std::memory_order_acquire`
- `std::atomic_thread_fence`

En shared memory interproceso:

- asegurar que los átomos son lock-free,
- verificar `is_always_lock_free`,
- no depender de `std::atomic` con tipos no garantizados por el estándar para IPC,
- usar intrinsics o wrappers validados por plataforma.

# PASS 4 — FFI RUST/C++/PYTHON, GPU Y CRIPTOGRAFÍA

## 4.1 ERROR CRÍTICO: `catch_unwind` no convierte Rust en FFI-safe

El reporte dice que Rust devuelve `NativeStatus` y atrapa panics con `catch_unwind`.

### Ataque

`catch_unwind` solo atrapa panics unwind. No protege contra:

- undefined behavior,
- dereferencing de punteros nulos,
- slices mal formados,
- alineación incorrecta,
- lifetime violations,
- aborts,
- stack overflow si no está controlado,
- allocator mismatch,
- ABI incorrecto.

Además, si el código Rust entra en UB, el resultado no es recuperable.

### Solución

Toda función FFI debe:

1. Ser `extern "C"`.
2. No exponer tipos Rust ricos (`Vec`, `String`, `Box`) directamente.
3. Usar tipos `#[repr(C)]`.
4. Validar punteros antes de convertirlos en slices.
5. Validar longitud y alineación.
6. No asumir lifetime.
7. No propagar panics.
8. Devolver códigos de error cerrados.
9. Tener `unsafe` mínimo y auditado.
10. Tener tests de fuzzing específicos.

### Ejemplo defensivo

```rust
#[no_mangle]
pub extern "C" fn polydim_betti_filter(
    ptr: *const f32,
    len: usize,
    out: *mut BettiResult,
) -> NativeStatus {
    let result = std::panic::catch_unwind(|| {
        if ptr.is_null() || out.is_null() {
            return NativeStatus::NullPointer;
        }
        if len == 0 || len > MAX_DIM {
            return NativeStatus::InvalidLen;
        }
        if (ptr as usize) % std::mem::align_of::<f32>() != 0 {
            return NativeStatus::BadAlignment;
        }

        let data = unsafe { std::slice::from_raw_parts(ptr, len) };

        // lógica...
        NativeStatus::Ok
    });

    match result {
        Ok(status) => status,
        Err(_) => NativeStatus::Panic,
    }
}
```

Aun así, si `ptr` apunta a memoria inválida, la validación no puede saberlo. Por eso el handle debe venir de un slab validado.

## 4.3 ERROR: Python puede entregar tensores GPU/no contiguos a C++ CPU

El reporte dice que los bindings aseguran contigüidad C y fuerzan `.cpu()`.

### Ataque

Si falta una sola ruta, ocurre:

- segmentation fault,
- bus error,
- garbage data,
- CUDA illegal memory access,
- deadlock por stream no sincronizado.

Casos peligrosos:

- tensor transpuesto,
- tensor con stride,
- tensor view,
- tensor en CUDA,
- tensor en pinned memory,
- tensor con dtype incorrecto,
- tensor liberado por Python mientras C++ lo usa,
- CUDA context inicializado antes de fork.

### Solución

El orquestador Python debe validar:

```python
assert tensor.is_contiguous()
assert tensor.dtype == expected_dtype
assert tensor.device.type in allowed_devices
```

Si backend C++ es CPU:

```python
tensor = tensor.detach().contiguous().cpu()
```

Si backend es CUDA-aware:

```python
# validar device, contexto y stream
torch.cuda.synchronize()
```

Además:

- mantener referencia viva del tensor durante la llamada FFI,
- liberar GIL en llamadas largas,
- no usar `fork()` después de inicializar CUDA,
- usar `spawn` en multiprocessing con GPU.

### Para GPU multi-proceso

No pasar puntero crudo. Usar:

- `cudaIpcGetMemHandle`,
- `cudaIpcOpenMemHandle`,
- o mecanismo equivalente del backend.

## 4.4 ERROR: TPU/Pallas no garantiza zero-copy nativo como CUDA

### Ataque

Pallas/JAX/TPU tiene un modelo de ejecución compilado y gestionado. No es razonable asumir que se puede pasar un puntero arbitrario de TPU a C++ como si fuera CUDA.

### Solución

Crear una matriz de capacidades:

| Backend | Zero-copy intra-proceso | Zero-copy interproceso | Puntero crudo | Acción |
|---|---:|---:|---:|---|
| CPU | Sí | Sí vía SHM | Sí | PMTP normal |
| CUDA | Sí con contexto | Limitado vía IPC handle | Sí con cuidado | CUDA IPC |
| ROCm | Similar a CUDA | Limitado | Sí con cuidado | ROCm IPC |
| TPU | No asumible | No asumible | No | Staging/host o API específica |

El contrato debe decir:

```text
PMTP zero-copy only applies where the backend exposes stable native handles.
TPU backend must declare staging semantics explicitly.
```

## 4.5 ERROR: AES-GCM/HMAC in-memory rompe zero-copy puro y añade coste O(D)

El reporte menciona:

- AES-GCM,
- HMAC-SHA256,
- BCrypt nativo.

### Ataque

Si cada tensor se cifra/descifra y MACea, entonces:

\[
O(D)
\]

por mensaje.

Eso puede dominar el coste de IPC.

Además:

- AES-GCM requiere nonce único por clave.
- Reutilizar nonce en GCM es catastrófico.
- HMAC adicional puede ser redundante si GCM ya autentica.
- BCrypt es Windows-only.
- Linux/macOS necesitan otra implementación.
- Las claves en memoria compartida o en procesos AI son superficie de ataque.

### Riesgo criptográfico concreto

Si se usa AES-GCM con nonce de 96 bits:

```text
nonce = counter
```

hay que garantizar monotonicidad.

Si un atacante puede hacer rollback del contador en shared memory, puede reutilizar nonces o reenviar mensajes antiguos.

### Solución

1. Usar AEAD una sola vez, no AES-GCM + HMAC doble salvo requisito explícito.
2. Preferir:
   - AES-256-GCM con hardware,
   - AES-256-GCM-SIV si hay riesgo de nonce misuse,
   - XChaCha20-Poly1305 si se busca simplicidad y nonce amplio.
3. Incluir en AAD:

```text
slab_id
generation
sequence
writer_pid_token
byte_len
dtype
device
abi_version
```

4. Mantener contador monotónico confiable.
5. Rechazar:
   - nonce repetido,
   - seq menor que última vista,
   - AAD inconsistente,
   - tag inválido.
6. Zeroizar claves al salir.
7. No usar RNG no criptográfico.
8. Usar librería auditada multiplataforma:
   - libsodium,
   - OS CSP,
   - OpenSSL solo si se acepta dependencia,
   - ring/boringcrypto en Rust si aplica.

### Decisión arquitectónica

Si el threat model no incluye atacante con acceso a memoria compartida, la criptografía puede ser opcional.

Si el threat model sí lo incluye, entonces hay que aceptar:

\[
\text{crypto overhead } O(D)
\]

y no llamar al sistema “zero-copy puro”.

- usa handles versionados,

- sobrevive a crash del lector,

- valida contigüidad,
- valida dtype,
- valida device,

- nonce nunca se repite,
- AAD incluye metadata del slab,

# 4. El silicio de 1970 no es el de hoy, y el de 2050 no será el de hoy

Esto que dijiste es clave.

POLYDIM no puede asumir un silicio ideal, secuencial, fuerte, homogéneo.

Tampoco puede asumir que el futuro será x86/CUDA/FP32/PCIe.

Debe diseñarse por contratos de capacidad.

---

## 4.1 Modelo de memoria

El silicio moderno tiene:

- out-of-order execution,
- stores buffers,
- cache hierarchies,
- weak memory models,
- NUMA,
- GPUs con memorias separadas,
- TPUs con memoria gestionada,
- CXL/NVLink/fabric heterogéneo.

### Consecuencia

No puedes usar `volatile` como mecanismo de sincronización.

No puedes publicar un tensor así:

```cpp
data_ready = true;
```

y esperar que otro proceso vea los datos correctamente.

Necesitas:

```cpp
std::memory_order_release
std::memory_order_acquire
atomic_thread_fence
```

o equivalentes de plataforma.

### Requisito SOTA

Para IPC compartido:

1. Publicación de payload antes de publicar generation/seq.
2. Lector adquiere generation/seq antes de leer payload.
3. Revalidación después de leer.
4. Detección de tearing.
5. Detección de crash con estado `WRITING` persistente.
6. No reutilización de slab mientras haya lectores.

---

## 4.2 Atomicidad interproceso

No todo `std::atomic` está garantizado para shared memory interproceso por el estándar C++.

En la práctica, enteros de 64 bits alineados suelen funcionar en x86_64/ARM64, pero no se debe asumir ciegamente.

### Requisito

Verificar:

```cpp
std::atomic<uint64_t>::is_always_lock_free
```

o usar primitivas explícitas de plataforma:

- Linux: `__atomic_*`, futex, shared memory barriers.
- Windows: `Interlocked*`, named synchronization primitives.
- macOS: primitivas soportadas, no APIs privadas como única base.

### Regla

```text
Si un objeto compartido no puede ser operado atómicamente de forma portable,
no debe usarse como mecanismo de publicación crítica.
```

---

## 4.3 Cache lines y false sharing

En silicio moderno, dos variables en la misma cache line pueden destruir performance.

Un seqlock, un refcount, un sequence number y un flag de estado no deben compartir cache line con payload caliente.

### Fix

```cpp
alignas(128) std::atomic<uint64_t> publication_seq;
alignas(128) std::atomic<uint64_t> state;
alignas(128) payload...
```

### Requisito

Detectar cache line size dinámicamente cuando sea posible:

- Linux: `sysconf(_SC_LEVEL1_DCACHE_LINESIZE)`
- macOS: `sysctl hw.cachelinesize`
- Windows: `GetLogicalProcessorInformation`

No hardcodear 64 si el target puede ser 128 o distinto.

---

## 4.4 NUMA

Para \(D \ge 10^6\), la ubicación física de la memoria importa.

Si el writer escribe desde un nodo NUMA y el reader lee desde otro, el ancho de banda puede degradarse.

### Fix SOTA

- first-touch policy,
- `mbind` o equivalente cuando aplique,
- huge pages,
- `MAP_POPULATE` donde sea apropiado,
- monitoreo de NUMA node,
- opcional afinidad de procesos.

### No alucinar

No puedo afirmar que tu implementación sufra NUMA sin código y sin hardware profile.

Pero sí puedo afirmar que un sistema \(D = 10^7\) debe considerar NUMA.

## 4.5 GPUs: no son “punteros universales”

Una GPU moderna no es una CPU con más hilos.

Tiene:

- device memory,
- host memory,
- pinned memory,
- managed memory,
- IPC handles,
- streams,
- contexts,
- virtual memory APIs,
- restricciones de alineación,
- ECC,
- MIG,
- NVLink/PCIe.

### Consecuencia

Pasar un puntero CUDA crudo a C++ CPU es un fallo potencial.

### Fix

El binding debe incluir:

```c
enum Device { CPU, CUDA, ROCM, TPU };
```

Y reglas:

```text
Si device == CPU:
    C++ puede acceder si ptr/host handle es válido.
Si device == CUDA:
    solo backend CUDA-aware puede acceder.
Si device == TPU:
    no asumir puntero crudo; usar API específica o staging.
```

### Zero-copy GPU real

Entre procesos GPU, no basta con pasar un `void*`.

Se necesita:

- CUDA IPC handle,
- contexto compatible,
- sincronización de stream,
- lifetime control,
- device UUID match.

# 5. Profundización SOTA: el verdadero error de memoria PMTP

Voy a atacar ahora uno de los errores más profundos, no como item suelto, sino como contrato completo.

---

## ERROR PROFUNDO: publicar tensores mutables en memoria compartida sin un modelo de inmutabilidad verificable

Esto combina:

- seqlock,
- zero-copy,
- IPC,
- crash recovery,
- ABA,
- false sharing,
- memory ordering,
- process death,
- stale handles.

---

## 5.1 El problema

Si un escritor publica un tensor y luego puede mutarlo mientras un lector lo usa, entonces el lector no tiene garantía de consistencia durante el cómputo.

Un seqlock clásico sirve para detectar lecturas inconsistentes si el lector copia el payload.

Pero si el lector usa el payload in-place durante un cálculo largo, el seqlock no lo protege durante todo el cómputo.

### Ejemplo

1. Escritor publica slab 7.
2. Lector empieza a calcular sobre slab 7.
3. Escritor reescribe slab 7.
4. Lector mezcla valores antiguos y nuevos.
5. El cálculo termina sin error visible.
6. El resultado está corrupto.

Eso es corrupción silenciosa.

---

## 5.2 Contrato SOTA: slabs publicados son inmutables

La forma más robusta de resolverlo es:

```text
Una vez publicado, un slab no se muta.
```

El escritor debe:

1. reservar slab vacío,
2. escribir payload,
3. calcular metadata/hash/crypto,
4. publicar atomáticamente,
5. no tocar el payload publicado.

Si necesita actualizar, publica una nueva generación o nuevo slab.

---

## 5.3 Handle PMTP seguro

No se debe pasar:

```c
void* ptr
```

Se debe pasar:

```c
struct PmtpHandle {
    uint64_t abi_version;
    uint64_t slab_id;
    uint64_t generation;
    uint64_t offset;
    uint64_t byte_len;
    uint64_t dtype;
    uint64_t device;
    uint64_t checksum;
    uint64_t seq;
};
```

El receptor resuelve:

\[
\text{local\_ptr} = \text{base\_local} + \text{offset}
\]

### Ventajas

- válido entre procesos,
- evita punteros absolutos,
- detecta stale handles por generation,
- permite checksum,
- permite validación de longitud,
- permite auditoría.

---

## 5.4 Máquina de estados del slab

Un slab debe tener estados explícitos:

```text
EMPTY
WRITING
COMMITTED
DRAINING
POISONED
```

Transiciones:

```text
EMPTY -> WRITING
WRITING -> COMMITTED
WRITING -> POISONED
COMMITTED -> DRAINING
DRAINING -> EMPTY
```

Invariants:

1. Un lector nunca lee `WRITING`.
2. Un slab `COMMITTED` no muta payload.
3. Un slab no vuelve a `EMPTY` mientras hay lectores activos.
4. Si writer crash en `WRITING`, el slab queda `POISONED` o recuperable con timeout.
5. Generation monotónica evita ABA.

---

## 5.5 Publicación con memory ordering

Conceptualmente:

### Escritor

```cpp
header->state.store(WRITING, relaxed);
write_payload();
compute_checksum();
atomic_thread_fence(release);
header->generation.store(next_generation, release);
header->state.store(COMMITTED, release);
```

### Lector

```cpp
g1 = header->generation.load(acquire);
state = header->state.load(acquire);

if (state != COMMITTED) reject;

read_payload();
validate_checksum();

atomic_thread_fence(acquire);

g2 = header->generation.load(acquire);

if (g1 != g2) reject;
```

Pero esto solo protege la lectura/copia.

Para uso prolongado zero-copy, se necesita pin/refcount/epoch.

---

## 5.6 Zero-copy seguro requiere pinning

Si el lector va a usar el slab directamente, debe registrar intención.

Opciones:

### Opción A — Reference slots

Cada proceso lector tiene un slot:

```text
reader_slot = {
    process_token,
    slab_id,
    generation,
    heartbeat,
    state
}
```

Writer/allocator no recicla un slab si algún slot vivo apunta a él.

### Opción B — Epoch-based reclamation

Lector entra en época:

```text
enter_epoch();
use slab;
leave_epoch();
```

Reclaimer espera periodo de gracia.

### Opción C — Immutable ring

Preallocating N slabs inmutables.

Escritor publica nuevo slab.

Lector usa handle viejo.

Slab viejo se recicla cuando el ring da vuelta y no hay referencias.

---

## 5.7 Crash recovery

Si un writer muere dejando:

```text
state = WRITING
```

el slab no puede quedar usable.

Debe marcarse:

```text
POISONED
```

o ser recuperado por un supervisor con:

- timeout,
- writer liveness check,
- checksum,
- generation bump.

### Regla

```text
Un slab WRITING sin dueño vivo nunca debe ser leído como COMMITTED.
```

---

## 5.8 ABA

Si slab_id = 42 se reutiliza, un handle viejo puede parecer válido.

Solución:

```text
slab_id + generation
```

Cada nueva vida del slab incrementa generation.

Un handle con generation vieja debe rechazarse.

---

## 5.9 Crypto y secuencia

Si el payload va cifrado, el contador de secuencia no puede estar solamente en memoria compartida mutable sin protección.

Debe incluir:

```text
slab_id
generation
sequence
writer_token
abi_version
dtype
device
byte_len
```

en AAD.

Y debe detectarse:

- rollback,
- replay,
- nonce reuse,
- AAD mismatch.

Si no, un atacante con acceso a SHM puede reenviar estados viejos.

## TH-01 — Corregir la afirmación `O(1) tensor transfer`

**Problema:** el handle viaja en `O(1)`, pero tocar/validar/descifrar/normalizar el tensor es `O(D)`.

**Fix SOTA:**

```text
PMTP control/handle transfer: O(1)
PMTP tensor validation/consumption: O(D)
PMTP cryptographic verification: O(D)
PMTP consensus/topological filter: O(A^2 D) o superior según implementación
```

**Actualizar `02_SILICON_CONTRACT.md`:**

```text
Zero-Copy IPC transfiere referencias en O(1).
Toda validación, normalización, cifrado, consenso o consumo del tensor permanece en O(D) o superior.
```

---

## TH-02 — Reformular DPI

**Problema:** “JSON viola DPI” es incompleto. DPI no prohíbe serializar; prohíbe recuperar información después de un canal intermedio. El problema real es el colapso semántico/métrico.

**Fix:**

```text
POLYDIM evita el colapso semántico 1D cuando debe preservarse geometría ND.
No se prohíbe toda serialización; se prohíbe la proyección irreversible de tensores latentes a texto cuando se requiere preservar estructura geométrica.
```

---

## TH-03 — No prometer `FP32` con cota `FP64`

**Problema:** exigir:

\[
|\|y\|^2 - 1| \le 4.44 \times 10^{-16}
\]

sobre estado final FP32 es matemáticamente incompatible.

**Fix:**

```text
FP64 critical state: target <= 4.44e-16
FP32 tensor state: target dtype-aware, por ejemplo 1e-5 o 1e-6 según D y distribución
BF16/FP16: no apto para garantías geométricas estrictas sin master weight FP32/FP64
```

---

## TH-04 — Fréchet-Betti debe declarar coste real

**Problema:** “microsegundos” sin complejidad/benchmark es riesgoso.

**Fix:**

```text
Filtro Fréchet-Betti debe declarar:
A = número de agentes
D = dimensión
dtype
distancia exacta/aproximada
Betti exacto/graph-only/aproximado
hardware
p50/p99/p999
```

Si es exacto sobre tensores completos, asumir como mínimo:

\[
O(A^2 D)
\]

---

## TH-05 — BFT real requiere quorum

**Problema:** descartar outliers geométricos no es BFT completo.

**Fix:**

```text
n >= 3f + 1
quorum mínimo = 2f + 1
umbral de distancia adaptativo
rechazo explícito si quorum insuficiente
registro de agentes descartados
```

---

## TH-06 — Hardware agnosticism debe ser capability contract

**Problema:** CUDA/ROCm/TPU/OpenMP no tienen el mismo modelo de memoria.

**Fix:** crear `HardwareCapabilityManifest`.

```cpp
struct HardwareCapabilityManifest {
    uint64_t abi_version;

    bool host_shared_memory;
    bool interprocess_atomic64;
    bool interprocess_atomic128;

    bool cuda_ipc;
    bool rocm_ipc;
    bool tpu_zero_copy;
    bool tpu_host_staging;

    bool fp64_supported;
    bool fp64_fast;
    bool fp32_denormals;
    bool ftz_enabled;
    bool daz_enabled;
    bool precise_division;
    bool precise_sqrt;

    bool aes_hw;
    bool sha_hw;
    bool chacha_simd;

    uint64_t cache_line_size;
    uint64_t numa_nodes;
    uint64_t max_shm_size;
};
```

Regla:

```text
POLYDIM no hardcodea backend.
POLYDIM degrada explícitamente si una capacidad no existe.
```

# 2. PAQUETE IPC / SHM — PRIORIDAD P0

## IPC-01 — Prohibir punteros absolutos entre procesos

**Riesgo:** `void*` crudo no es portable entre procesos.

**Fix:** usar handles con offset.

```cpp
#define PMTP_ABI_V1 0x80600001ULL

struct PmtpHandle {
    uint64_t abi_version;
    uint64_t slab_id;
    uint64_t generation;
    uint64_t offset;
    uint64_t byte_len;
    uint64_t dtype;
    uint64_t device;
    uint64_t seq;
    uint64_t checksum;
};
```

El receptor resuelve:

```cpp
void* local = base_local + handle.offset;
```

**Cierre:** test con procesos mapeando la región en bases distintas.

---

## IPC-02 — Slab header con estado explícito

```cpp
enum class PmtpSlabState : uint64_t {
    EMPTY     = 0,
    WRITING   = 1,
    COMMITTED = 2,
    DRAINING  = 3,
    POISONED  = 4
};

struct PmtpSlabHeader {
    uint64_t magic;
    uint64_t abi_version;
    std::atomic<uint64_t> state;
    std::atomic<uint64_t> generation;

    uint64_t slab_id;
    uint64_t capacity;
    uint64_t payload_len;
    uint64_t dtype;
    uint64_t device;

    uint64_t writer_token;
    uint64_t checksum;
    uint64_t poison_reason;
    uint64_t reserved[4];
};
```

**Regla:** payload solo se lee si `state == COMMITTED`.

---

## IPC-03 — Slabs publicados inmutables o doble buffer

**Problema:** seqlock no protege uso prolongado si el escritor muta el slab mientras el lector computa.

**Fix recomendado:**

```text
Opción preferida: slabs inmutables versionados.
Opción hot-path: doble buffer con generación.
```

Regla:

```text
Ningún slab COMMITTED puede ser reescrito mientras existan lectores activos.
```

---

## IPC-04 — Publicación con memory ordering correcto

Escritor:

```cpp
header->state.store((uint64_t)PmtpSlabState::WRITING, std::memory_order_relaxed);

write_payload();
header->payload_len.store(len, std::memory_order_relaxed);
header->checksum.store(compute_checksum(), std::memory_order_relaxed);

std::atomic_thread_fence(std::memory_order_release);

header->generation.store(next_generation, std::memory_order_release);
header->state.store((uint64_t)PmtpSlabState::COMMITTED, std::memory_order_release);
```

Lector:

```cpp
uint64_t g1 = header->generation.load(std::memory_order_acquire);
uint64_t st = header->state.load(std::memory_order_acquire);

if (st != (uint64_t)PmtpSlabState::COMMITTED) return ERR_NOT_COMMITTED;

read_payload();
validate_checksum();

std::atomic_thread_fence(std::memory_order_acquire);

uint64_t g2 = header->generation.load(std::memory_order_acquire);

if (g1 != g2) return ERR_TORN_READ;
```

**Cierre:** test en ARM/x86 con TSan y stress de reorder.

---

## IPC-05 — Crash recovery y poison state

**Problema:** writer muere dejando `WRITING`.

**Fix:**

```text
Si writer no confirma en timeout:
    state = POISONED
    poison_reason = WRITER_DEAD_OR_TIMEOUT
```

Nunca leer un slab `WRITING`.

**Cierre:**

```bash
kill -9 writer durante escritura
reader debe rechazar slab
supervisor puede recuperar/quarantine
```

---

## IPC-06 — Anti-ABA con generation

Cada reuso de slab incrementa `generation`.

```text
handle.generation != slab.generation => STALE_HANDLE
```

**Cierre:** test de ABA: liberar, reasignar, reusar handle viejo.

---

## IPC-07 — Reference/pinning para zero-copy real

Si el lector usa el slab in-place:

```text
Debe registrar slab_id + generation + process_token
```

Reclamador no recicla si hay lectores vivos.

Mecanismo SOTA:

- reader slots,
- epoch-based reclamation,
- process token + heartbeat,
- watchdog para procesos muertos.

---

## IPC-08 — No depender solo de `__ulock_wait`

**Riesgo:** API privada de macOS, semántica interproceso no garantizada, inestable entre versiones.

**Fix:**

```text
Adaptive spin corto
fallback a primitiva portable multi-proceso
```

Plataformas:

- Linux: futex compartido / eventfd / semáforos POSIX robustos.
- macOS: primitivas soportadas oficialmente o fallback validado.
- Windows: named semaphores/events para interproceso.

**Cierre:** test con writer/reader en procesos separados y crash de uno.

---

## IPC-09 — SPSC solo si realmente hay 1 productor y 1 consumidor

Si hay swarm multi-agente:

```text
Opción A: canal SPSC por par de agentes
Opción B: sharding SPSC
Opción C: MPMC lock-free verificado/model-checked
```

**No** usar SPSC como si fuera MPMC.

## IPC-10 — Alineación, bounds y overflow

Validar siempre:

```cpp
if (handle.abi_version != PMTP_ABI_V1) return ERR_ABI;
if (handle.offset >= slab.capacity) return ERR_BOUNDS;
if (handle.byte_len > slab.capacity - handle.offset) return ERR_BOUNDS;
if ((handle.offset % required_alignment) != 0) return ERR_ALIGNMENT;
```

Usar aritmética segura para `offset + byte_len`.

# 3. PAQUETE MATEMÁTICO — P0/P1

## MATH-01 — Norma escalada obligatoria

No usar suma directa de cuadrados para `D` grande.

```cpp
double scaled_norm2(const double* x, size_t n) {
    double m = 0.0;
    for (size_t i = 0; i < n; ++i) m = std::fmax(m, std::fabs(x[i]));

    if (m == 0.0) return 0.0;

    NeumaierAcc acc;
    for (size_t i = 0; i < n; ++i) {
        double t = x[i] / m;
        acc.add(t * t);
    }

    return m * m * acc.value();
}
```

**Cierre:** test con overflow/underflow/subnormales.

---

## MATH-02 — Rotación geodésica estable

No usar:

```cpp
versin = 1.0 - cos(theta);
```

Usar:

```cpp
double sinc(double x) {
    if (std::fabs(x) < 1e-8) return 1.0 - x*x/6.0;
    return std::sin(x) / x;
}

double s, c_minus_1;

if (std::fabs(theta) < 1e-4) {
    double th2 = theta * theta;
    double half = theta * 0.5;
    double sinc_half = sinc(half);

    s = theta * sinc(theta);
    c_minus_1 = -0.5 * th2 * sinc_half * sinc_half;
} else {
    s = std::sin(theta);
    double h = std::sin(theta * 0.5);
    c_minus_1 = -2.0 * h * h;
}
```

Aplicar en plano ortonormal:

```cpp
// u y w ortonormales
// a = dot(y,u), b = dot(y,w)

double du = std::fma(a, c_minus_1, -b * s);
double dw = std::fma(a, s, b * c_minus_1);

// y += du*u + dw*w
// luego normalización escalada
```

**Cierre:**

```text
theta = 0
theta = 1e-12
theta = 1e-8
theta = pi/2
theta = pi
vectores casi colineales
vectores casi antipodales
```

---

## MATH-03 — Reortogonalización doble para `v_perp`

```text
v1 = v - (u·v) u
v2 = v1 - (u·v1) u
w  = normalize(v2)
```

Si:

```text
||v2|| < tau
```

rechazar o construir base auxiliar.

Nunca normalizar vector casi nulo.

## MATH-04 — Neumaier paralelo determinista

Reglas:

```text

Reducción por árbol determinista.

```

```text

```

**Cierre:** test con denormals y subnormales.

## MATH-06 — CholQR con shift adaptativo

No usar epsilon fijo mágico.

Pipeline:

```text
1. G = X^T X en FP64 o acumulador FP64
2. estimar condición/kappa
3. si kappa bajo: CholQR
4. si kappa medio: shifted CholQR + reortogonalización doble
5. si kappa alto: TSQR/SVD/fallback robusto
6. verificar ||X^T X - I||_F
```

**Cierre:** matrices casi singulares, columnas casi colineales.

---

## MATH-07 — Distancia esférica estable

Para vectores unitarios, evitar `acos(dot)` crudo.

```cpp
double d = clamp(dot, -1.0, 1.0);

// distancia chordal estable
double chordal_sq = std::fmax(0.0, 2.0 * (1.0 - d));
```

Para ángulo pequeño, usar componente tangente si es posible.

Si existe ambigüedad de signo:

```text
usar |dot| o alinear signos antes de comparar
```

## FFI-02 — Validación defensiva obligatoria

```rust
#[no_mangle]
pub extern "C" fn polydim_filter_f64(
    ptr: *const f64,
    len: usize,
    out: *mut f64,
) -> NativeStatus {
    let result = std::panic::catch_unwind(|| {
        if ptr.is_null() || out.is_null() {
            return NativeStatus::NullPointer;
        }

        if len == 0 || len > MAX_DIM {
            return NativeStatus::BadLen;
        }

        if (ptr as usize) % std::mem::align_of::<f64>() != 0 {
            return NativeStatus::BadAlignment;
        }

        if (out as usize) % std::mem::align_of::<f64>() != 0 {
            return NativeStatus::BadAlignment;
        }

        let input = unsafe { std::slice::from_raw_parts(ptr, len) };
        let output = unsafe { std::slice::from_raw_parts_mut(out, len) };

        // proceso...

        NativeStatus::Ok
    });

    match result {
        Ok(status) => status,
        Err(_) => NativeStatus::Panic,
    }
}
```

**Importante:** `catch_unwind` no elimina UB. La validación previa es obligatoria.

# 5. PAQUETE PYTHON / GPU / TPU — P0

## PY-01 — Validación de tensor antes de FFI

```python
def prepare_tensor(t, expected_dtype, expected_device):
    if t.dtype != expected_dtype:
        raise TypeError("dtype mismatch")

    if not t.is_contiguous():
        t = t.contiguous()

    if expected_device == "cpu":
        if t.device.type != "cpu":
            if t.device.type == "cuda":
                torch.cuda.synchronize()
            t = t.cpu()
        assert t.device.type == "cpu"

    elif expected_device == "cuda":
        assert t.device.type == "cuda"
        torch.cuda.synchronize(t.device)

    else:
        raise RuntimeError("unsupported device")

    return t
```

Mantener referencia viva del tensor durante la llamada FFI.

# 6. PAQUETE CRIPTOGRAFÍA — P1

## SEC-01 — Elegir AEAD único

Si ya usas AES-GCM, no necesitas HMAC-SHA256 adicional salvo requisito específico.

Recomendación:

```text
AES-256-GCM si hay hardware y nonce controlado.
AES-256-GCM-SIV si hay riesgo de nonce misuse.
XChaCha20-Poly1305 si quieres nonce amplio y buen software SIMD.
```

---

## SEC-02 — Nonce único obligatorio

Para AES-GCM 96-bit:

```text
nonce = session_random_32_bits || counter_64_bits
```

o:

```text
nonce = counter_96_bits
```

Regla:

```text
Si counter llega a límite, rekey o abortar.
Nunca reutilizar nonce con la misma clave.
```

---

## SEC-03 — AAD PMTP

Incluir:

```text
abi_version
slab_id
generation
seq
dtype
device
byte_len
writer_token
```

Esto evita mezclar slabs, generaciones o replay simple.

---

## SEC-04 — Anti-rollback

```text
seq debe ser monotónico.
El receptor debe rechazar seq <= last_accepted_seq.
```

Si el contador vive en memoria compartida mutable, un root attacker puede hacer rollback. Declarar threat model.

---

## SEC-05 — Backend portable

```text
Windows: BCrypt
macOS: Security/CoreCrypto
Linux: backend auditado permitido
```

Si no se permite dependencia externa, entonces:

```text
crypto solo disponible donde exista backend nativo validado.
En otros entornos, desactivar crypto o usar modo no cifrado con threat model explícito.
```

---

## SEC-06 — Zeroization

Usar:

```text
SecureZeroMemory / explicit_bzero / memset_s
```

No depender de memset normal si el compilador puede optimizarlo.
